This article covers rxy-web, the universal Bluetooth remote for rxy robots: it knows no robot in advance, it asks whichever one it just found to send its own interface, then draws it. For this app's ancestor — the remote-design workshop that generates its own MakeCode firmware for a micro:bit — see Micro:bit Remote Builder (bit-rxy).

Overview

rxy-web is a Bluetooth remote that runs in the browser: nothing to install, no account, no WiFi. What separates it from every other app in this family fits in one sentence: the robot owns the layout. The app is a renderer — it connects, asks the robot for its configuration, and draws whatever comes back. Point it at a different robot and it shows that robot's controls instead. There is nothing to configure on the browser side, and no per-robot build of this app.

This inverts the approach of bit-rxy, the app it descends from: there you designed a remote in the browser, then generated the matching MakeCode firmware to paste into the board. Here the firmware already exists, it carries its own layout as Base64, and the app simply asks for it on every connect. A child switching robots switches neither tab nor app.

In practice one page serves a Keyes 4WD mecanum driven by a micro:bit, a Maqueen, and an ESP32-C3 Super Mini impersonating the micro:bit's UART protocol — without a single line of the app naming any of them.

RobotFirmware
Keyes 4WD Mecanum (micro:bit)keystudio_4wd_mecanum_rxy
Maqueen (micro:bit)maqueen-rxy
ESP32-C3 Super Miniesp32c3_super_mini_robot-bit-rxy

The app was forked from keystudio_4wd_mecanum_rxy with its full history, because that app was already a strict superset of bit-rxy. The robot-specific parts — the Keyes micro:bit firmware, its example layout and its product manifest — were removed in the commit right after the merge (25bfa76, "Strip the robot-specific parts: rxy_web serves every rxy robot"). Nothing was deleted from the original repositories.

Quick start

  1. Open the live app in Chrome or Edge — Safari and Firefox have no Web Bluetooth at all.
  2. Power the robot on and wait for it to start advertising.
  3. Press Connect in the top right and pick the robot from the browser's list.
  4. The robot's panel appears on its own, and the app switches to the ▶️ Play tab. There is no "choose the right layout" step.
Web Bluetooth needs a secure context. Serve the folder over localhost or HTTPS rather than opening it from a network share or a file:/// path.

Step by step: clone, serve & test

This walkthrough goes from a clean copy of the repository to a verified remote: one command reaching the robot, one value coming back from it.

1. Clone the repository

git clone https://github.com/abourdim/rxy_web.git
cd rxy_web

There is no build step, no npm install, no framework: three files run the app (index.html, script.js, styles.css).

2. Serve the site locally

npx serve .

Open the printed http://localhost:... address in Chrome or Edge. The copy published on GitHub Pages works exactly the same with nothing installed — that is the one to hand to children.

3. Flash a robot

The app is robot-neutral: it embeds no firmware, deliberately. The header's ⚙ Firmware button hides itself as long as the page carries no <script id="fwSource"> block — a robot-specific fork can add it back and the dialog lights up again on its own. So take the firmware from that robot's own repository (see the table above), paste it into makecode.microbit.org in JavaScript mode, and flash over USB.

On a micro:bit, two MakeCode settings are mandatory or the board connects and stays silent: in ⚙ Project Settings → Edit Settings As Text, merge the Bluetooth block below into pxt.json, and enable No Pairing Required.

"bluetooth": {
    "enabled": 1,
    "open": 1,
    "whitelist": 0,
    "security_level": 0,
    "uart": 1,
    "event_service": 1,
    "device_info_service": 1,
    "advertising_interval": 200,
    "advertising_power": 7
}

4. Connect

Press Connect. The browser's chooser lists every Bluetooth device nearby: the app uses acceptAllDevices: true with the UART service in optionalServices, precisely because a name filter was hiding compatible robots that are not called "BBC micro:bit" — an ESP32-C3, for instance.

A loading overlay then shows the layout transfer, with bytes received, throughput and elapsed seconds. On a reconnect it goes by in a flash: the layout is already cached (see the handshake).

5. Verify the round trip

A real test is two gestures, one per direction of travel:

  • Outbound — press one direction on the D-pad. The robot must move while your finger is down, and stop on release. If only one direction works, you have just rediscovered the 20-byte bug described below.
  • Inbound — watch a gauge or a label fed by the robot (distance, battery, heartbeat). Its value must change without you touching anything.

To see raw traffic, the browser console prints every line prefixed [BLE], and a LOGS panel opens with Ctrl+Shift+L.

Understanding the code (for beginners)

  assets/         — screenshot + Workshop-DIY logo.

The connect handshake

A full layout is over two hundred small Base64 chunks sent one at a time over a slow Bluetooth link. Doing that on every connect is pointless: a robot's layout almost never changes, while reconnecting happens constantly. So the app first asks for a tiny fingerprint of the layout, and only requests the full transfer when its cache does not match.

  App  ──▶  Robot     GETCFGVER
  App  ◀──  Robot     CFGVER 56caff8f        one tiny notification

       cache matches ─────▶  App ──▶ Robot  CFGOK 56caff8f   done, panel shown

       cache differs ─────▶  App ──▶ Robot  GETCFG
                             App ◀── Robot  CFGBEGIN 228     228 chunks announced
                             App ◀── Robot  CFG <base64>     ×228
                             App ◀── Robot  CFGEND

Three details are worth the detour:

  • The cache is keyed by BluetoothDevice.id, not by the display name, so two robots both called "BBC micro:bit" do not accidentally share a layout. The robot stays the source of truth: a different revision invalidates the cache by itself. If localStorage is unavailable or corrupt, the code simply falls back to GETCFG — correctness first, speed second.
  • The chunk count is announced on the opening line (CFGBEGIN 228). Before that, the progress bar was "12 + 4 per chunk, capped at 90": it reached the cap at chunk twenty and then sat motionless on 90% for the rest of the transfer. Clients match that line with startsWith(), so firmware that sends a bare CFGBEGIN still works — the bar just falls back to an estimate instead of a true fraction.
  • There is a hard refresh, the header's ↻ Config button. It clears only the layout cache, never language, theme or projects. And it takes the old controls off the screen while the replacement downloads: a moved or renamed widget could otherwise send the wrong command from a stale panel.

The 20 bytes that broke three directions out of four

This is the most instructive bug in the whole project, and the comment explaining it is still in script.js. The micro:bit's BLE connection uses the default ATT MTU of 23, which leaves exactly 20 bytes of payload per write. A longer write does not error: it is silently truncated. The trailing \n therefore never arrives, and the firmware's uartReadUntil(NewLine) waits forever for a line that never completes. The command vanishes, with no error on either side.

  SET dpad_move up 1      = 19 bytes  ──▶  fits       ✔ worked
  SET dpad_move down 1    = 21 bytes  ──▶  truncated  ✘ lost
  SET dpad_move left 1    = 21 bytes  ──▶  truncated  ✘ lost
  SET dpad_move right 1   = 22 bytes  ──▶  truncated  ✘ lost

Every command previously confirmed working was 20 bytes or under; every one that "did nothing" was over. The fix is to split each message into 20-byte packets before writing. The reverse direction had always handled this: notifications arrive pre-split (observed live as UPD lbl_heartbeat 14 then 7) and are reassembled by a receive buffer on the app side. The firmware needed no change at all — the UART service buffers incoming bytes, so uartReadUntil() reassembles those chunks the same way.

Three ways to send, not one

Web Bluetooth permits only one GATT operation at a time, so everything goes through a queue — but the three kinds of traffic have very different requirements, and treating them alike buys either latency or dropped commands.

PathFor whatRule
send()Continuous controls: joystick, sliders, selectsLatest value wins. An overwritten intermediate joystick position is not a bug, it is a skipped frame.
sendReliable()Discrete events: button press and releaseFIFO queue, nothing is lost. Losing a press to coalescing would be a real bug — the button would stay stuck down.
Direct motor writeD-pad stateBypasses the queue entirely. Each complete state fits in one byte.

The third path deserves a word. Rather than sending SET dpad_move up 1, the app encodes the complete state of all four buttons as a bitmask — U=1, D=2, L=4, R=8 — then adds it to 'a' to get a single letter:

  nothing           mask 0   ──▶  'a' + '\n'      2 bytes in total
  up                mask 1   ──▶  'b' + '\n'
  up + right        mask 9   ──▶  'j' + '\n'      a diagonal is not a special case:
  all pressed       mask 15  ──▶  'p' + '\n'      it is two bits set at once

The gain is not only size. Each packet carries the complete current state, so a dropped packet is corrected by the next one instead of leaving a direction stuck on. And because motion must never replay stale history, a new motor packet replaces any motor packet already queued and jumps to the front: at most the write already in progress can be ahead of it.

Remembering values, robot by robot

A MakeCode program has no persistent storage it can reach, so a calibration like wheel trim dies at every power-off. The app carries it instead. Any widget marked restore has its value saved in the browser and replayed on the next connect.

Two decisions there are counter-intuitive and worth noting:

  • This store is keyed by name, not by id — the reverse of the layout cache. BluetoothDevice.id is an opaque per-origin handle the browser is free to mint fresh for a new document, and on a file:// page it does exactly that: an id-keyed record is lost by the very reload it exists to survive. A micro:bit's name, by contrast, is derived from its MAC: stable across reloads, and still different for two robots on the same bench.
  • Values are replayed spaced out, not blasted — one write every 60 ms after an initial delay. They go over the link that just carried the layout, and a burst of writes straight after CFGEND is exactly what used to wedge the BLE stack on reconnect.

Saving is wired at a single choke point, inside the send functions themselves: every message of the form SET <id> <value> passes through it. No widget type needs its own save call, and a type added later is covered for free.

Build, Play, Arrange

The app has two tabs and one mode hidden inside the second:

  • ✏️ Build — the workshop. Drag widgets from the palette, set their properties, and export the result as Layout JSON or a MakeCode CFG snippet to paste into firmware. This is where the ⚡ Flash to micro:bit button still lives, inherited from bit-rxy.
  • ▶️ Play — the runtime. Connected, it shows only the verified layout received from the robot; disconnected, it shows a deep clone of what is in Build.
  • Arrange, inside Play, repositions a live panel and exports the result — the fastest way to improve a layout: fix it where you actually use it, then send the CFG back into the firmware.

The rule holding it all together: Build is the authoritative model, Play renders a deep-cloned snapshot, and only an explicit Tidy or an Arrange edit may change geometry. Tab switches, zoom and fullscreen never rewrite positions — an automatic re-tidy on resize did once exist, and was removed on purpose.

The radar in detail

The radar is the only widget that receives no value of its own: it reads two others. That is what makes it usable on any robot with a distance sensor on a moving head, without adding a single command to the protocol.

PropertyNames the widget carrying…
sourcethe distance, in cm
angleSourcethe head angle, 0–180
maxbeyond this, a reading means "nothing there" (default 200)
modeldots or rays

Rings at 10, 30 and 100 cm, a beam on the live angle, and detections that persist and fade over five seconds: a sweep builds a picture of the room instead of flashing one number. Blips take their colour from the threshold — red under 10 cm, amber under 30, green beyond.

Readings at or past max are not plotted. That value is the robot's "no echo", and drawing it would paint a wall at full range around an empty room.

Finally, the distance scale is deliberately not linear: the first ten centimetres take a quarter of the radius. That is exactly the scope the dfrobot-rover draws on its own OLED, so the two displays agree about what "close" looks like.

Bluetooth protocol reference

A line-oriented protocol over a Nordic-UART-style GATT service. The app never stores a layout; it asks for one on every connect.

RoleUUIDDirection
UART service6e400001-b5a3-f393-e0a9-e50e24dcca9e—
"TX" characteristic6e400002-b5a3-f393-e0a9-e50e24dcca9enotifications: robot → app
"RX" characteristic6e400003-b5a3-f393-e0a9-e50e24dcca9ewrites: app → robot
TX and RX are named from the peripheral's point of view. So ...0002 is the one that notifies and ...0003 the one you write to — swapping them does not produce a mysterious silence but a blunt NotSupportedError on the first send.

The lines exchanged:

  app   ──▶ robot   GETCFGVER                    what is your layout's fingerprint?
  robot ──▶ app     CFGVER <revision>
  app   ──▶ robot   CFGOK <revision>             already cached, send nothing

  app   ──▶ robot   GETCFG                       send the whole thing
  robot ──▶ app     CFGBEGIN <chunkCount>
  robot ──▶ app     CFG <base64 chunk>           … repeated
  robot ──▶ app     CFGEND

  app   ──▶ robot   SET <widgetId> <value…>      the user did something
  robot ──▶ app     UPD <widgetId> <value>       here is a reading

  app   ──▶ robot   'a'..'p'                      complete D-pad state, 1 byte

Firmware may also define the reference canvas geometry in its configuration (width and height). Widget positions and sizes then stay reproducible across clients, instead of each one inferring a different canvas from the occupied extents.

Sharing the app

The header's ⧉ Share button shows a QR code of https://abourdim.github.io/rxy_web/, so in a workshop the next person points a phone at your screen instead of typing a URL on a tablet keyboard.

Two implementation choices, counter-intuitive but deliberate:

  • The QR is baked into index.html, not generated at runtime. The address is a constant, so shipping an encoder would be code to maintain for a fixed picture.
  • It always encodes the published address, never location.href. Demonstrations happen from file:// or a laptop's localhost — a generated code would hand someone a link their phone cannot reach.

Regenerate it only if that address changes:

python tools/make-qr.py

The tool re-splices the SVG between the qr:begin and qr:end markers, and refuses to write if the path it produced does not reproduce the QR matrix exactly.

Troubleshooting

SymptomCause / fix
No Connect button, or "Bluetooth not supported"Safari and Firefox do not implement Web Bluetooth on any platform. On iPhone and iPad every browser is WebKit-based, so none of them work: that is a platform limit, not a bug. Use Chrome or Edge on desktop or Android.
Connection is refused even though the page opens fineWeb Bluetooth needs a secure context. A file:/// path or a network share is not enough — serve the folder with npx serve . or use the GitHub Pages copy.
The robot does not appear in the browser's listCheck power and range (~10 m), and that no other page or app is already connected to that robot — one connection at a time. On a micro:bit, check that "uart": 1 and No Pairing Required are set in MakeCode.
Loading stays stuck at 0%The robot answers neither GETCFGVER nor GETCFG. Firmware too old, or a wedged Bluetooth stack: fully reload the page, then power-cycle the robot.
The panel shown no longer matches the firmwarePress ↻ Config in the header. The layout cache is cleared and the layout re-downloaded in full; language, theme and projects are untouched.
Only one D-pad direction worksThe exact signature of the 20-byte bug on an older client: longer commands are truncated with no error. See above. Update the app.
The robot keeps driving after releaseA packet was dropped. On a current version the next packet corrects the state, since every byte carries the complete state; if it persists, the firmware is not applying the mask it receives.
The ⚙ Firmware button is missingExpected: rxy-web is robot-neutral and embeds no firmware, so the dialog hides itself. The firmware lives in the robot's own repository.
A remembered setting does not come backOnly widgets marked restore in the robot's configuration are remembered, and the store is keyed on the robot's name — a peripheral advertising no name at all falls back to an id the browser may mint fresh.
