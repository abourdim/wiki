Cet article couvre la version à widgets de la télécommande du robot mécanum Keyestudio : la disposition complète vit dans le firmware et est renvoyée à l'application à la connexion. Pour la page simple à disposition fixe, voir Keyes 4WD Mecanum Remote. L'application dérive de bit-rxy, via la variante Maqueen Lab.

Aperçu

Deux onglets : ✏️ Build pour composer une télécommande par glisser-déposer, ▶️ Play pour la piloter. La particularité, héritée de bit-rxy, est que la disposition n'est pas stockée dans le navigateur mais dans le firmware, sous forme de chaîne Base64. Le micro:bit sait donc décrire lui-même sa propre interface : n'importe quelle copie de l'application, sur n'importe quelle machine, redessine la bonne télécommande dès la connexion.

Par rapport à la page simple, on gagne le pavé mécanum 8 directions à masque binaire, la bande NeoPixel avec effets, les modes autonomes Ligne et Évitement, les capteurs embarqués du micro:bit, et un graphe de distance. On perd la simplicité : 31 widgets, un transfert de configuration d'environ quinze secondes, et un firmware de plus de 2 000 lignes.

Démarrage rapide

  1. Ouvre index.html dans Chrome ou Edge.
  2. ⚙ Firmware dans l'en-tête : copie le code, ajoute les trois extensions, flashe.
  3. Onglet ▶️ Play, bouton Connect, choisis la carte.
  4. Attends le transfert de la disposition (~15 s la première fois, mis en cache ensuite), puis conduis.

Étape par étape : cloner, flasher & tester

1. Cloner le dépôt

git clone https://github.com/abourdim/keystudio_4wd_mecanum_rxy.git
cd keystudio_4wd_mecanum_rxy

2. Ouvrir la page

Double-clic sur index.html suffit ; npx serve . fonctionne aussi.

3. Les trois extensions

ExtensionSourcePourquoi
mecanum_robot_v2github.com/keyestudio2019/mecanum_robot_v2Moteurs, servo, phares, capteurs
BluetoothintégréeService UART
NeopixelintégréeBande 4 LED sur P7
Active No Pairing Required dans les paramètres du projet. La fenêtre Firmware contient aussi le bloc bluetooth complet à fusionner dans pxt.json si la liaison reste muette.

4. Flasher

Copy code, coller dans MakeCode en mode JavaScript, Télécharger, déposer le .hex.

5. Première connexion : regarder le transfert

Onglet Play, Connect. L'application demande d'abord une révision courte (GETCFGVER) ; comme rien n'est en cache, elle bascule sur le transfert complet GETCFG, environ 420 blocs à 35 ms. Une dizaine de secondes, une seule fois par disposition.

6. Vérifier chaque sous-système

  1. Entraînement — les huit directions du pavé, roues en l'air. Les diagonales doivent translater, pas tourner.
  2. Servo — le curseur doit balayer la tête ; la jauge suit.
  3. Phares — les deux interrupteurs.
  4. Bande — interrupteur Strip, puis une couleur, puis les effets Rainbow / Chase / Sparkle.
  5. Distance — robot à l'arrêt, la jauge suit la main et le graphe se remplit.
  6. Ligne — les trois voyants s'allument un par un en travers d'une bande noire.
  7. Capteurs — son, température, inclinaison X/Y, boutons A/B, contact logo.
Une installation complète : la disposition apparaît seule après connexion, les huit directions translatent correctement, la bande s'anime, la distance suit la main, les trois capteurs de ligne réagissent séparément, et l'horloge de fonctionnement avance dans l'en-tête.

Comprendre le code (pour débutants)

Le sens de la flèche « CFG chunks » est l'idée centrale : la disposition remonte du robot vers l'application, jamais l'inverse. L'onglet Build sert à fabriquer un CFG qu'on recopie ensuite dans le firmware ; en usage courant, c'est le firmware qui commande l'affichage.

Le cache de configuration : ne pas retransférer 5 Ko à chaque fois

Dix secondes à chaque connexion serait insupportable. À la place, la carte sait d'abord répondre à une question courte :

App ── GETCFGVER ─────────▶ micro:bit
App ◀── CFGVER 47c78c1f ──  (empreinte calculée depuis CFG au démarrage)
     │
     ├─ empreinte connue ─▶ dessine depuis le cache local     (instantané)
     │
     └─ inconnue ─────────▶ GETCFG ──▶ CFGBEGIN / CFG ×420 / CFGEND
                                        (~15 s, une seule fois)

L'empreinte est dérivée du contenu de CFG lui-même, donc elle change automatiquement dès qu'on modifie la disposition : aucun numéro de version à maintenir à la main, et aucun risque de servir un cache périmé.

Le pavé mécanum : huit directions dans un seul octet

Chaque appui envoie un octet, pas une phrase. L'état complet des directions tient dans quatre bits, et l'octet transmis vaut 'a' + masque :

Bit1248
DirectionHautBasGaucheDroite

Une diagonale n'est donc pas un nouveau concept réseau : c'est simplement deux bits allumés. Le firmware additionne les bits en un vecteur, et la même formule sert aux huit directions :

btnFwd  = (mask & 1) != 0
btnBack = (mask & 2) != 0
btnLeft = (mask & 4) != 0
btnRight= (mask & 8) != 0

let ny = 0, nx = 0
if (btnFwd)  ny += 1
if (btnBack) ny -= 1
if (btnLeft) nx -= 1
if (btnRight)nx += 1
runMecanum(nx, ny)
BoutonMasqueOctetnx, ny
↑1b0, +1
↖5f−1, +1
↗9j+1, +1
↙6g−1, −1
↘10k+1, −1
■ STOP0a0, 0

Comme chaque paquet porte l'état complet et non un changement, un paquet perdu se répare tout seul au suivant. Une direction maintenue est réémise périodiquement, ce qui permet au chien de garde du firmware de distinguer « toujours appuyé » de « le relâchement s'est perdu ».

L'arbitrage matériel : pourquoi la matrice 5×5 reste éteinte

C'est la décision la moins évidente du firmware, et elle a été prise deux fois pour de mauvaises raisons avant d'être prise pour la bonne. Sur ce châssis, quatre broches de la matrice LED sont déjà occupées :

Broches pilotées par la matrice 5×5 :  P3  P4  P6  P7  P9  P10
                                        │   │       │       │
                    capteur ligne G ────┘   │       │       │
                    capteur ligne C ────────┘       │       │
                    bande NeoPixel  ────────────────┘       │
                    capteur ligne D ────────────────────────┘

  affichage actif ─▶ ces broches sont multiplexées
                  ─▶ lecture des capteurs = bruit
                  ─▶ la bande ne s'allume pas

  donc :  led.enable(false)   une fois, au démarrage

Le firmware conserve tout son code de glyphes derrière une constante USE_MATRIX plutôt que de le supprimer : la remettre à true restaure l'affichage, au prix du suivi de ligne et de la bande.

Corollaire : la mesure de luminosité est inutilisable sur ce robot. Le micro:bit mesure la lumière avec sa propre matrice, donc input.lightLevel() réactive l'affichage — et reprend P7 à la bande deux fois par seconde. Le symptôme était une bande qui s'allumait au démarrage puis restait éteinte ensuite.

Le suivi de ligne à trois capteurs

La table de vérité est reprise telle quelle du programme Keyestudio, pas déduite : sur ce châssis, 1 signifie « sur la ligne ».

La fenêtre Firmware, et le firmware recopié dans la page

Le bouton ⚙ Firmware réutilise la fenêtre modale existante de l'application et affiche la source complète, la version, les extensions et le bloc Bluetooth. Comme pour la page simple, la source est intégrée plutôt que chargée par fetch(), bloqué sur file://. Ici cela pèse environ 104 Ko dans index.html, d'où l'outil :

node tools/embed-firmware.cjs          # réécrit index.html
node tools/embed-firmware.cjs --check  # sort en erreur si dérive

L'extension .cjs n'est pas un caprice : package.json déclare "type": "module", donc un fichier .js serait interprété comme module ES et require() échouerait.

Tests de mise en route

Une panne dans le firmware complet est difficile à localiser : l’application se connecte, les commandes sont acquittées, et rien ne bouge. Le dépôt contient donc firmware/tests/ — huit programmes MakeCode autonomes, un par sous-système. On en colle un dans un projet vierge, on flashe, on regarde. Pas d’application, pas de Bluetooth, aucun autre fichier.

OrdreFichierRépond à
1test-leds.tsLe pilote I2C est-il vivant et alimenté ?
2test-motors.tsLes quatre roues tournent-elles, dans le bon sens ?
3test-servo.tsLa tête balaie-t-elle ? Quel trim ?
4test-ultrasonic.tsLe capteur répond-il, et quelle routine de lecture lui convient ?
5test-line.tsLes trois capteurs de ligne lisent-ils proprement ?
6test-neopixel.tsLa bande s’allume-t-elle, et sur quelle broche ?
7test-microbit.tsLes capteurs embarqués répondent-ils ?
8test-ble.tsLe Bluetooth fonctionne-t-il, sans aucun robot ?

Commencer par les phares n’est pas arbitraire : ce sont les éléments les moins chers du bus I2C, donc ce test écarte les deux causes les plus fréquentes de « rien ne bouge » — mauvaise extension et rail moteur non alimenté — avant de chercher ailleurs.

Deux de ces tests ne peuvent pas utiliser l’écran et le disent : les capteurs de ligne sont sur P3/P4/P10 et la bande sur P7, toutes des broches de la matrice. Ils appellent led.enable(false) et rendent compte par les phares, le buzzer ou la liaison série.
