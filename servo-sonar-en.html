This article covers the Servo-Sonar, a deliberately reduced version of bit-rxy (“b3”): two drive servos, one distance sensor, and nothing else. No buzzer, no strip, no screen, no battery sensing.

The repository is a fork with the full history of b3, not a copy: fixes move between the two robots by cherry-pick rather than by hand. For the app that drives it, see rxy-web. For the robot it came from, see bit-rxy. For the other port, the one with a turning head, see Robot MV.

Overview

The robot owns its interface. The app knows no robot in advance: it connects, asks for the configuration, and draws whatever comes back. The Servo-Sonar therefore sends its own panels, and the app never needs recompiling for it.

What sets this board apart is what it does not have. b3 drives a buzzer, a NeoPixel strip, two LEDs, an OLED screen and a battery-voltage sense line. Here only drive and distance remain. The firmware was not gutted for that: the absent modules are switched off by a single #define and vanish at compile time, rather than failing silently at runtime.

That reduction has a direct effect on the pinout. GPIO 10 is free here only because the LEDs and the strip are gone — on b3 that pin is CONFIG_PIN_LED_RED and the strip output. It is the one pin difference between the two robots: the HC-SR04 stays on 21 / 20 on both.

With no turning head, there is no radar in the sense of rxy_web's polar widget: that one needs an angle, and this robot publishes none. Distance shows up as a gauge, a graph and an alert. For sweeping, see Robot MV.

Quick start

  1. Power the robot. With no screen and no LED, the only sign of life is the BLE name appearing in the device list.
  2. Open rxy_web in Chrome or Edge, on a phone or a PC.
  3. Press Connect and pick diy_app_s2 from the list.
  4. The panel appears by itself. Choose Expert in the Level selector to see everything.
  5. Drive forward. If it pulls to one side, correct it with the Trim L and Trim R sliders, with no reflashing — see Wheel trim.

Step by step: clone, flash & test

This walkthrough goes from a bare repository to a verified robot: it drives the right way, it drives straight, and it measures.

1. Clone the repository

git clone https://github.com/abourdim/esp32c3_super_mini_servo_sonar-rxy.git
cd esp32c3_super_mini_servo_sonar-rxy/01_software/01_app

2. Build

The project uses PlatformIO. Nothing to configure: the platform and the libraries are pinned in platformio.ini — espressif32 @ 6.7.0, the same as b3, so both robots build against one toolchain.

pio run -e esp32-c3-devkitm-1

3. Flash over USB

pio run -e esp32-c3-devkitm-1 -t upload

The ESP32-C3 SuperMini flashes over its native USB, with no serial adapter. Two settings in platformio.ini exist purely for that, and should not be “optimised”:

  • upload_speed = 115200 — the mid-upload switch to 460,800 crashes the USB-CDC endpoint (“No serial data received”).
  • upload_flags = --no-stub — when the stub takes over, the USB-CDC endpoint re-enumerates and the first command after it falls into a dead window (“Unable to verify flash chip connection”). Staying on the ROM bootloader is slower, roughly 60–90 s, but reliable.

If the upload still fails, hold the BOOT button while you plug the board in.

4. Check the serial monitor

pio device monitor

What matters at startup:

[BLE] init - device_name: diy_app_s2
[BLE] service_uuid: ...
[BLE] advertising: YES
Native USB-CDC means the serial monitor attaches after boot: most of the time you will see nothing at startup. That is normal, not a fault. monitor_dtr = 0 and monitor_rts = 0 are there so that opening the monitor does not reset the board into download mode.

5. Test the drive direction

Connect, switch to Expert, and press up on the pad. The robot should move forward.

If it spins on the spot instead, the two connectors are swapped: exchange CONFIG_PIN_SERVO_LEFT and CONFIG_PIN_SERVO_RIGHT in 00_config.h. Which connector is “left” depends on how the servos are mounted on the chassis, not on the board.

6. Test the sensor

Switch to Distance in the Level selector, then move your hand in front of the HC-SR04. The gauge and the graph should react immediately.

7. Set it straight

Hold forward for a few metres of flat floor. If the robot wanders, correct it with Trim L / Trim R from the Drive or Expert panel, while driving. The serial monitor confirms the save:

[TRIM] saved L=0 R=3
A healthy baseline looks like this: the robot moves forward when you ask for forward, it holds its line over a few metres, and the distance moves when your hand approaches — both subsystems confirmed separately.

The protocol, in three messages

Everything runs over a UART-style BLE service. Three exchanges are enough to understand it:

MessageDirectionRole
GETCFGVERapp → robot“what version is your layout?” The robot answers CFGVER <token>. If the phone already has that layout cached, the whole transfer is skipped — the log then shows Client had this layout cached - transfer skipped.
GETCFGapp → robotsend me your layout. The robot answers with a series of base64 chunks, sized to the negotiated MTU.
SET / UPDboth waysSET = the user touched a widget. UPD = the robot publishes a value (distance, speed, uptime, trim).

The version token is not a hand-maintained number: it is a fingerprint over the layout and over B3_FIRMWARE_VERSION. A panel edit therefore changes the token by itself, and an edit that happens to collide is still told apart by the firmware version.

The files, in the order they matter

FileWhat it does

01_src.inosetup() and loop(). Short and readable on purpose.

gen_layouts.pygenerates the four layouts and splices them into 03_bit-rxy.cpp. See below.

The panels are generated, not hand-written

python 01_software/01_app/gen_layouts.py

The script rebuilds all four layouts and splices them back into the source. More importantly it fails rather than emitting a broken panel, on three checks:

  • two widgets overlapping;
  • a widget escaping its group;
  • a widget id with neither an input handler nor a telemetry sender.

The last is the important one: a control that looks live and does nothing is worse than a missing control. It is also why the test panels were rebuilt here rather than carried over from b3 unchanged — carrying them over unvalidated is exactly how a truncated instruction line shipped.

The PWM timer trap (which does not bite here)

setup() calls ESP32PWM::allocateTimer(0) once, and two servos are attached: an exact fit. It is worth knowing why that detail is written down — if you add a third servo, a turning head for instance, ESP32Servo does not warn you: it prints All PWM timers allocated! and then halts inside attach(), so setup() never returns.

And it is invisible from outside: NimBLE has already started on its own task, so the robot keeps advertising and the app connects. It simply answers nothing. It reads as a protocol bug; it is not one. One more servo, one more allocateTimer().

The board and its pinout

Schematic: 01_kicad/31_richa_c3_move/34_richa_c3_servo_sonar/v1.

GPIOConnectorUse
10J2, pin 3left wheel servo
7J3, pin 3right wheel servo
21—HC-SR04 trig
20—HC-SR04 echo
0module BOOT buttonhold 3 s = OTA, 8 s = forget WiFi

GPIO 6 and 3, which carry the servos on b3, are unused here. Conversely GPIO 10 would not be available on b3: it is the red LED and the strip output.

The servo rail wants bulk capacitance. The two servos share the ESP32's VCC and the v1 board has only 100 nF on that rail. These are the drive servos: they run constantly, not occasionally, and an SG90 pulls about 700 mA stalled, with a larger startup surge. 100 nF does nothing at that current: the rail dips and the C3 browns out mid-drive. Add 470–1000 µF at the servo connectors, and feed servo power straight from the input terminal rather than through the module's 5V pin, so servo current does not run through the module.

The four panels

b3 serves eight. Five of them drive hardware this board does not have, so four remain. Switch between them with the Level selector; the choice is kept in NVS, so a power cycle does not drop you back to Beginner.

PanelWhat it has
BeginnerD-pad, distance gauge, obstacle alert. No speed slider: at this level the pad is the speed control, and a second one only invites “why won't it move”.
ExpertD-pad + joystick + speed + STOP + turn pad + both trims, distance gauge / graph / alert, sound alert, then firmware version, uptime, telemetry level, button state and signal strength.
Driveone subsystem only: pad, speed, STOP, speed gauge, turn pad, both trims, and one instruction line. This is the straight-line calibration panel.
Distancegauge, alert, 30 s graph.

Why a separate turn pad

On a differential drive, left/right with no forward component spins the robot on the spot — the one movement the 4-way pad makes awkward, since it needs a held direction and constant correction. The Turn pad does only that.

Its bits merge with the main pad's in the firmware rather than being handled separately: holding forward on one and left on the other is therefore an arc turn, not two commands fighting over the output.

Wheel trim, and the bug that made it useful

The right wheel is mirrored on the chassis: its pulse range is inverted, map(speed, -100, 100, 180, 0) against 0..180 on the left. Trim, however, is a raw pulse offset, so it lands in each servo's own frame.

The consequence, in the version inherited from b3: adding the same +5 on both sides pushed the two wheels in physically opposite directions.

SituationLeft wheelRight wheelVisible effect
full forward, +5 trim on both180, i.e. +90 from neutral5, i.e. +85 from neutralthe left outruns the right: the robot curves right
at rest, +5 trim on both95: creeps forward95: creeps backwardthe robot slowly turns on the spot while idle
stopServos()9090the two paths did not even agree on where neutral was

Since S2-v3, the right channel subtracts its trim. A positive value therefore means “this wheel drives more forward” on both sides — the only reading that makes these constants usable. Both defaults dropped from 5 to 0: at zero the two wheels get equal and opposite full-scale commands, so whatever veer remains is real mechanical or servo-tolerance error. That is exactly what trim is for. The 5s inherited from b3 were themselves causing the pull they were supposed to correct.

b3 carries the identical code and the identical bug. It was not touched here: the fix is there to cherry-pick if you put a b3 back into service.

Sliders rather than a constant

Until S2-v5, straightening a robot meant editing CONFIG_SERVO_SPEED_STOP_*_OFFSET and reflashing over USB — useless in a classroom. Continuous-rotation servos vary unit to unit: this is per-robot calibration, not a constant.

trim_l and trim_r are therefore sliders, −20 to +20 degrees of servo pulse. They sit next to the drive controls rather than in a settings corner: you tune them while driving, watching which way the robot pulls. Past 20 it is a mechanical fault, not a trim.

Three implementation details are worth knowing:

  • Immediate effect, deferred save. The value applies in RAM on the first packet, so the effect is visible while the slider is still moving. It is committed to NVS only after 1.5 s of stillness: dragging a slider emits one SET per step, and writing flash on each would burn endurance on values the user is only scrubbing past.
  • The robot echoes both values back after every layout transfer. Without that, the sliders would snap to their default on each connect while the robot kept driving with the saved value: the panel would be lying about the robot's calibration.
  • The constants remain the factory default for a fresh chip. Once anything is saved, NVS overrides them.

Updating over WiFi

WiFi is off during normal operation: it has no business running during a BLE-driven session. To enter OTA mode, hold the BOOT button for 3 seconds at any point.

No credentials are written into the code. WiFiManager remembers the last network it joined in its own NVS, and opens a setup access point, WDIY-Robot-Setup, whenever it cannot reconnect. The robot is then reachable as wdiy-servo-sonar. Keep holding to 8 seconds to forget the saved network and force the portal open.

pio run -e esp32-c3-devkitm-1-ota -t upload --upload-port <robot-ip>

b3 reports OTA progress on its NeoPixels and OLED. This robot has neither, so status goes to Serial only — which is enough, because the setup AP name and the hostname are both fixed.

Troubleshooting

The app connects then sits on “Checking layout version”

The robot advertises and accepts the connection, but answers nothing. On this robot the historical cause is firmware that recognised GETCFGVER without answering it: recent app versions no longer fall back to GETCFG on their own, so silence is fatal. Fixed in S2-v2. If you see this on an older build, that is it.

The other possible cause is a setup() halted inside attach() — see the PWM timer trap.

The robot veers right when driving forward

Before S2-v3 this was the signature of trim applied backwards, described above. Since then it is the sliders' job: raise Trim R until it runs straight. That is the sentence printed on the Drive panel itself.

The robot turns slowly on the spot while idle

Same origin, worse: on the mirrored wheel a positive trim pushed backwards. If you see this, you are running something older than S2-v3, or you copied the old constants back in. Set both CONFIG_SERVO_SPEED_STOP_*_OFFSET to zero.

The robot spins on the spot instead of driving forward

The two servo connectors are swapped. Exchange CONFIG_PIN_SERVO_LEFT and CONFIG_PIN_SERVO_RIGHT. This is not the same fault as “it drives backwards”: here both wheels turn the same physical way.

Random reboots while driving

Almost always power, not software. See the servo rail box in The board and its pinout. It is the most likely fault on this board, because the drive servos load the rail continuously.

Nothing appears on the serial monitor

Expected. Native USB-CDC re-enumerates on reset, so the monitor attaches after the boot message. The robot is running; it is simply quiet when idle.
