ESP32-RXY

ESP32-RXY

This article covers ESP32-RXY, ESP32 firmware that speaks the exact same Bluetooth Low Energy protocol as a BBC micro:bit running the rxy MakeCode template — so the unmodified rxy web app can connect to a plain ESP32 and drive widgets exactly as it would a real micro:bit.

Overview

ESP32-RXY lets you drive the rxy remote-control web app with a plain ESP32 board instead of a BBC micro:bit. The rxy app was never modified to make this work: the ESP32 firmware advertises itself as a micro:bit and implements the exact same BLE UART protocol, so from the browser's point of view it is indistinguishable from the real hardware. This is convenient when you want a permanent, wired-power remote receiver rather than a battery-powered micro:bit, or simply don't have a micro:bit on hand.

The target board is the ESP32-C3 Super Mini, a very cheap (a few dollars) ESP32-C3 board with a native USB-C port and an on-board LED and button — but any ESP32 chip with Bluetooth Low Energy works with minor pin adjustments.

Companion project: this firmware is the ESP32-side counterpart to the Micro:bit Remote Builder (bit-rxy) web app. Read that article first if you haven't designed a remote layout yet — the "Customising the layout" section below assumes you already have a CFG string exported from it.

Quick start

PlatformIO (recommended for the ESP32-C3 Super Mini):

cd platformio
pio run -t upload
pio device monitor

Arduino IDE: install the ESP32 by Espressif Systems board package and the NimBLE-Arduino library (2.x), open arduino/microbit_esp32_remote/microbit_esp32_remote.ino, select board ESP32C3 Dev Module, enable Tools > USB CDC On Boot, and upload.

Then open abourdim.github.io/rxy in Chrome or Edge, switch to the Play tab, tap 📡 Connect, and pick BBC micro:bit from the chooser.

Which toolchain should I use? On the ESP32-C3 Super Mini, prefer PlatformIO. Its platformio.ini pins upload_speed = 115200 and sets --no-stub, both required to work around USB-CDC re-enumeration quirks in esptool. Arduino IDE / arduino-cli has no clean way to pass --no-stub through, so uploads may fail with "No serial data received" or "Unable to verify flash chip connection". See Troubleshooting for the full explanation.

Step-by-step: clone, flash & test

This walkthrough takes you from a bare checkout to a firmware that a browser can actually connect to and drive.

1. Clone the repository

git clone https://github.com/abourdim/esp32-rxy.git
cd esp32-rxy

An ESP32-C3 Super Mini (or any ESP32 board with BLE) and a USB-C cable.

2. Install the BLE library

Both toolchains need NimBLE-Arduino 2.x. In Arduino IDE: Library Manager → search "NimBLE-Arduino" → install. In PlatformIO it is pulled automatically — platformio.ini pins h2zero/NimBLE-Arduino @ ^2.2.0 in lib_deps.

3. Build and flash

Option A — PlatformIO (recommended):

cd platformio
pio run                # compile
pio run -t upload      # upload (~60-90s with --no-stub, this is normal)
pio device monitor -b 115200

Or use the interactive menu instead of memorising flags:

./launch.sh

which offers numbered options to check the toolchain, install PlatformIO, compile, flash, monitor, or "do everything" in one go, for either PlatformIO or arduino-cli.

Option B — Arduino IDE: open arduino/microbit_esp32_remote/microbit_esp32_remote.ino, Tools > Board → "ESP32C3 Dev Module", Tools > USB CDC On Boot → Enabled, select the port, click Upload.

4. Watch it boot

Open the serial monitor at 115200 baud. A healthy boot prints a full diagnostic block — chip model, core count, SDK version, free heap, flash size — followed by the BLE setup steps, ending with:

[BLE] advertising as: 'BBC micro:bit'
[BOOT] setup() OK   — free_heap=... bytes
[BLE] Open https://abourdim.github.io/rxy/ and click Connect.

5. Connect from the rxy web app

On a phone or desktop running Chrome, Edge, Opera, or Samsung Internet, open abourdim.github.io/rxy, switch to the Play tab, and tap 📡 Connect. Pick the device named BBC micro:bit from the browser's pairing chooser (the firmware advertises under that exact name so the app's filter accepts it).

You should see a single "Test" button appear — the default minimal layout baked into the firmware. Tapping it toggles the on-board blue LED on the C3 Super Mini (GPIO 8, active low).

If the connect overlay says "Requesting layout (GETCFG)…" and never dismisses, the firmware is reachable but the CFGEND reply never arrived — check the serial monitor for the line [BLE] Sent CFG. If it's missing, the device likely disconnected mid-transfer.

6. Try the debug button

Press the on-board BOOT button (GPIO 9) after the board has finished booting — it dumps a complete state snapshot to the serial monitor: chip info, uptime, free heap, GPIO states, BLE UUIDs, and the current layout config in the exact same CFGBEGIN/CFG/CFGEND framing sent over BLE. Useful to confirm what layout is actually running without needing a phone nearby.

Careful with GPIO 9: it is also the ESP32-C3's BOOT strapping pin. Holding it down while the board is powering on or resetting boots the chip into ROM download mode instead of running the firmware. It is safe to press after boot completes. If you want a dedicated debug button without that gotcha, wire one to GPIO 0 and GND instead and change BUTTON_PIN in the source.
A successful setup looks like this: the serial monitor shows a clean boot with no reset-loop, the app's connect overlay dismisses within a second or two showing your widgets, and the Test button (or your own layout) responds instantly.

Understanding the code (for newbie developers)

This section is for anyone who has flashed the firmware and connected successfully, and now wants to open the source and wire up their own widgets. It assumes no prior embedded/C++ experience. If you only want to use the default one-button layout, you can skip this entirely.

You don't need to understand any of this to build, flash, and connect. Everything in this section is here for when you're ready to make the firmware do something with your own widgets.

The one file that matters

The whole firmware lives in a single file, main.cpp (Arduino IDE users see the identical content as microbit_esp32_remote.ino — the two are kept byte-for-byte in sync). No headers, no libraries beyond NimBLE and the ESP-IDF system calls used for diagnostics.

What happens once, at power-on: setup()

  power on
     │
     ▼
  1 Serial + boot diagnostics  ──▶  2 GPIO init (LED off, button pulled up)
                                              │
                                              ▼
  4 GATT service + characteristics  ◀──  3 NimBLEDevice::init + security (open, no pairing)
     │
     ▼
  5 start advertising as "BBC micro:bit"

1. Boot diagnostics — before anything BLE-related happens, setup() prints chip model, core count, revision, SDK version, Arduino core version, CPU frequency, free heap, and flash size to the serial monitor. This is what you check first if a board misbehaves.

2. GPIO init — the on-board LED (GPIO 8, active low on the C3 Super Mini — writing LOW turns it on) is set to off, and the debug button (GPIO 9) is configured INPUT_PULLUP so it reads LOW when pressed.

3. NimBLE init and security policy — this is the part worth reading carefully:

NimBLEDevice::init(BLE_DEVICE_NAME);
NimBLEDevice::setPower(ESP_PWR_LVL_P9);
NimBLEDevice::setMTU(247);
NimBLEDevice::setSecurityAuth(false, false, false);   // no bonding / MITM / LESC
NimBLEDevice::setSecurityIOCap(BLE_HS_IO_NO_INPUT_OUTPUT);
NimBLEDevice::deleteAllBonds();

setMTU(247) requests a larger Bluetooth packet size than the 23-byte default, so the 23-byte "CFG <18-char>\n" lines fit in one notification instead of fragmenting — centrals still negotiate this down if they don't support it (macOS Chrome typically lands around 185 bytes, phones around 247). The security calls explicitly disable pairing/bonding, matching what a real micro:bit does in MakeCode's "no pairing required" mode: anyone in Bluetooth range can connect and drive widgets. Fine for a desk toy or classroom remote; not something you'd want for anything sensitive.

4. GATT service and characteristics — the firmware creates one BLE service with two characteristics:

NimBLEService* svc = server->createService(UART_SERVICE_UUID);
gTxChar = svc->createCharacteristic(UART_TX_CHAR_UUID, NIMBLE_PROPERTY::NOTIFY);
NimBLECharacteristic* rxChar = svc->createCharacteristic(
            UART_RX_CHAR_UUID, NIMBLE_PROPERTY::WRITE | NIMBLE_PROPERTY::WRITE_NR);
rxChar->setCallbacks(new RxCallbacks());
Naming gotcha: characteristic ...0002 is the one the firmware notifies on (device → app) and ...0003 is the one the app writes to (app → device). This is the opposite of the Nordic UART Service convention used by Adafruit/Bluefruit libraries, because we are impersonating a micro:bit, and MakeCode assigns the roles the other way around. If you ever compare this code to a generic NUS example, remember the roles are swapped.

5. Advertising — the last and most fiddly step. A BLE advertising packet has a hard 31-byte budget. This firmware's device name is short ("BBC micro:bit", 13 characters) specifically so it fits in the primary advertising packet alongside the flags, without needing a scan-response packet at all:

adv->setName(BLE_DEVICE_NAME);
adv->enableScanResponse(false);          // name fits in primary packet
adv->setMinInterval(0x140);              // 320 * 0.625ms = 200ms
adv->setMaxInterval(0x140);

This matters because some BLE centrals (notably Chrome on macOS) handle names carried in a scan-response packet unreliably — the device can become invisible in the browser's pairing chooser even though phones see it fine. Dropping the service UUID from the advertisement (it's still discoverable via GATT after connecting) frees enough of the 31-byte budget for the name to live in the primary packet, which every BLE central scans reliably. The 200 ms advertising interval matches MakeCode's own pxt.json setting, for consistency with a real micro:bit.

How a connection becomes a layout on screen: the GETCFG flow

Once connected, the rxy app writes GETCFG to the RX characteristic. That single incoming line triggers the whole layout hand-off:

  App writes "GETCFG\n" to RX char
       │
       ▼
  RxCallbacks::onWrite() buffers bytes until '\n', then calls handleLine()
       │
       ▼
  handleLine(): line == "GETCFG" → sendCfg()
       │
       ▼
  sendCfg(): sendLine("CFGBEGIN")
             for each 18-char chunk of LAYOUT_CFG_BASE64:
                 sendLine("CFG " + chunk);  delay(15ms)
             sendLine("CFGEND")
       │
       ▼  each sendLine() → gTxChar->notify(...)  over the TX characteristic
  App receives CFGBEGIN, several CFG lines, CFGEND
       │
       ▼
  App concatenates the CFG chunks, base64-decodes, JSON.parses the layout,
  and renders the widgets on screen

Two implementation details here are easy to get wrong, and the source code comments explicitly warn about both:

  • The 18-character chunk size is not arbitrary. It matches the official rxy MakeCode template's own chunking, so the same base64 CFG string round-trips identically whether it came from a real micro:bit or this firmware.
  • sendLine() must pass its own bytes to notify() directly, rather than calling setValue() then notify() as two separate steps. The two-step form races on the characteristic's shared internal buffer when called back-to-back inside the chunk loop: NimBLE's async host task can read the buffer after a newer setValue() call has already overwritten it, silently collapsing several queued notifications down to just the last one. The observed symptom on the rxy side was exactly this: only CFGEND ever arrived, every CFG chunk in between vanished, and JSON.parse('') failed. The fix, gTxChar->notify((const uint8_t*)out.c_str(), out.length()), captures the bytes atomically per call.

Reading incoming lines: the RX callback and handleLine()

BLE writes arrive as raw byte chunks, not neat lines, so the firmware buffers them itself:

void onWrite(NimBLECharacteristic* chr, NimBLEConnInfo&) override {
  std::string v = chr->getValue();
  for (size_t i = 0; i < v.size(); ++i) {
    const char c = v[i];
    if (c == '\r') continue;
    if (c == '\n') {
      if (gRxBuffer.length() > 0) { handleLine(gRxBuffer); gRxBuffer = ""; }
    } else {
      gRxBuffer += c;
      if (gRxBuffer.length() > 256) gRxBuffer = "";  // overflow guard
    }
  }
}

Every byte is appended to gRxBuffer until a \n completes a line (a lone \r is silently dropped, so both Unix and Windows line endings work); the completed line is handed to handleLine(), which recognises exactly two shapes:

if (line == "GETCFG") { sendCfg(); return; }
if (line.startsWith("SET ")) {
  int sp = line.indexOf(' ', 4);
  String id  = line.substring(4, sp);
  String val = line.substring(sp + 1);
  handleWidget(id, val);
}

Anything else is silently ignored — there is no error response for malformed lines, matching how the real micro:bit firmware behaves.

Wiring up your own widgets: handleWidget()

This is the one function you edit for your own project. It receives a widget id (exactly the ID you gave it in the rxy Build tab, e.g. btn_fire, slider_speed) and a val string whose format depends on the widget type (see the protocol reference table below). The shipped default handles only the demo button:

static void handleWidget(const String& id, const String& val) {
  if (id == "btn_test") {
    digitalWrite(LED_PIN, val == "1" ? LED_ON : LED_OFF);
    return;
  }
  // if (id == "slider_speed") {
  //   int s = val.toInt();          // 0..100 by default
  //   analogWrite(MOTOR_PIN, s * 255 / 100);
  //   return;
  // }
  ...
}

The source file ships one commented-out example per widget type (button, slider, toggle, joystick, D-pad, XY pad, timer) as a template to uncomment and adapt. To send data back the other way — updating an LED, label, gauge, graph, or battery indicator on screen — call the small helper sendValue(id, val) from anywhere, which simply emits "UPD <id> <val>":

static inline void sendValue(const String& id, const String& val) {
  sendLine("UPD " + id + " " + val);
}
The rxy web app rate-limits incoming messages to roughly one per 200 ms. Sending sendValue() updates faster than that will not corrupt anything, but excess messages are simply wasted — a 200–500 ms cadence in your own loop() polling code is comfortable and matches the commented-out periodic-update example already in the source.

Customising the layout

  1. Open the rxy web app, switch to the Build tab, and design your remote from its widget palette.
  2. Click 📄 Code. In the generated MakeCode, copy the long base64 string from const CFG = "…".
  3. Paste it into LAYOUT_CFG_BASE64 near the top of main.cpp, replacing the default one-button demo.
  4. Fill in your own logic in handleWidget(), matching the widget IDs you chose in the Build tab.
  5. Re-upload.

The widget IDs you used in the Build tab (btn_fire, slider_speed, …) are exactly the IDs that arrive in SET messages, so you handle them by name in handleWidget() — no separate ID-mapping step is needed.

Troubleshooting

SymptomCause / fix
A fatal error occurred: No serial data received. (right after "Changing baud rate to 460800") The ESP32-C3 Super Mini's native USB-CDC endpoint crashes on the mid-upload baud switch. Fixed by pinning upload_speed = 115200 in platformio.ini (already set in this repo).
Unable to verify flash chip connection (No serial data received.) (right after "Stub running...") When the flasher stub takes over from the ROM bootloader, the USB-CDC endpoint re-enumerates and the first post-stub command lands in a dead window. Fixed by upload_flags = --no-stub (already set), which keeps the ROM bootloader in charge for the whole upload — slower (~60–90s) but reliable.
Uploading from arduino-cli fails with one of the above There is no clean way to pass --no-stub through an Arduino FQBN. Hold the BOOT button while pressing RESET to force ROM-bootloader mode, then immediately upload — or switch to PlatformIO.
Device doesn't appear in the browser's pairing chooser Confirm you're on Chrome, Edge, Opera, or Samsung Internet — Safari and Firefox have no Web Bluetooth support on any platform, and no browser on iOS/iPadOS supports it (Apple restriction).
Connect overlay stuck on "Requesting layout (GETCFG)…" Check the serial monitor for [BLE] Sent CFG. If it never appears, the device disconnected before GETCFG arrived. If it does appear but the app still hangs, reconnect once — a stale characteristic subscription from a previous session can occasionally miss the burst of notifications.
Pressing the debug button (GPIO 9) prevents the board from booting GPIO 9 is the ESP32-C3's BOOT strapping pin. Holding it while powering on or resetting forces ROM download mode. Only press it after boot has completed, or rewire the debug button to GPIO 0 in the source.
Second phone/browser can't connect BLE peripherals hold exactly one central connection at a time. Disconnect the first client before connecting from another device.
No BLE pairing: by design, matching how a real micro:bit behaves in MakeCode's default mode, this firmware accepts connections with no pairing or bonding. Anyone within Bluetooth range can connect and send SET commands. Appropriate for a desk toy or classroom remote; not for anything where that matters.
