This article covers the widget version of the Keyestudio mecanum remote: the whole layout lives in the firmware and is sent back to the app on connect. For the simple fixed-layout page, see Keyes 4WD Mecanum Remote. The app descends from bit-rxy, by way of the Maqueen Lab variant.

Overview

Two tabs: ✏️ Build to compose a remote by drag and drop, ▶️ Play to drive it. The distinctive part, inherited from bit-rxy, is that the layout is not stored in the browser but in the firmware, as a Base64 string. The micro:bit can therefore describe its own interface: any copy of the app, on any machine, redraws the right remote as soon as it connects.

Compared with the simple page, you gain the 8-way bitmask mecanum pad, the NeoPixel strip with effects, autonomous Line and Avoid modes, the micro:bit's own sensors, and a distance graph. You lose simplicity: 31 widgets, a roughly ten-second layout transfer, and a firmware of over 2,000 lines.

Quick start

  1. Open index.html in Chrome or Edge.
  2. ⚙ Firmware in the header: copy the code, add the three extensions, flash.
  3. ▶️ Play tab, Connect, pick the board.
  4. Wait for the layout transfer (~10 s the first time, cached afterwards), then drive.

Step-by-step: clone, flash & test

1. Clone the repository

git clone https://github.com/abourdim/keystudio_4wd_mecanum_rxy.git
cd keystudio_4wd_mecanum_rxy

2. Open the page

Double-clicking index.html is enough; npx serve . works too.

3. The three extensions

ExtensionSourceWhy
mecanum_robot_v2github.com/keyestudio2019/mecanum_robot_v2Motors, servo, headlights, sensors
Bluetoothbuilt inUART service
Neopixelbuilt in4-LED strip on P7
Enable No Pairing Required in Project Settings. The Firmware dialog also carries the full bluetooth block to merge into pxt.json if the link stays silent.

4. Flash

Copy code, paste into MakeCode in JavaScript mode, Download, drop the .hex.

5. First connect: watch the transfer

Play tab, Connect. The app first asks for a short revision (GETCFGVER); with nothing cached it falls back to the full GETCFG transfer, about 280 chunks at 35 ms. Ten seconds or so, once per layout.

6. Verify each subsystem

  1. Drive — all eight pad directions, wheels off the ground. Diagonals must translate, not rotate.
  2. Servo — the slider should sweep the head; the gauge follows.
  3. Headlights — both toggles.
  4. Strip — Strip switch, then a colour, then Rainbow / Chase / Sparkle.
  5. Distance — robot stationary, the gauge tracks your hand and the graph fills.
  6. Line — the three lights come on one at a time across a black stripe.
  7. Sensors — sound, temperature, tilt X/Y, buttons A/B, logo touch.
A complete setup: the layout appears on its own after connecting, all eight directions translate correctly, the strip animates, distance tracks your hand, the three line sensors react separately, and the uptime clock advances in the header.

Assumes basic JavaScript. The firmware section assumes you have seen MakeCode in JavaScript mode before.

The direction of the "CFG chunks" arrow is the central idea: the layout travels from the robot to the app, never the other way. The Build tab exists to author a CFG that you then paste into the firmware; in normal use the firmware drives what you see.

The config cache: not re-sending 5 KB every time

Ten seconds on every connect would be unbearable. Instead the board can answer a short question first:

App ── GETCFGVER ─────────▶ micro:bit
App ◀── CFGVER 47c78c1f ──  (hash computed from CFG at boot)
     │
     ├─ hash known ───────▶ draw from the local cache        (instant)
     │
     └─ unknown ──────────▶ GETCFG ──▶ CFGBEGIN / CFG ×280 / CFGEND
                                        (~10 s, once)

The hash is derived from the contents of CFG itself, so it changes automatically whenever the layout changes: no version number to maintain by hand, and no way to serve a stale cache.

The mecanum pad: eight directions in a single byte

Each press sends one byte, not a sentence. The complete direction state fits in four bits, and the transmitted byte is 'a' + mask:

Bit1248
DirectionUpDownLeftRight

A diagonal is therefore not a new wire concept: it is simply two bits set. The firmware sums the bits into a vector, and the same formula serves all eight directions:

btnFwd  = (mask & 1) != 0
btnBack = (mask & 2) != 0
btnLeft = (mask & 4) != 0
btnRight= (mask & 8) != 0

let ny = 0, nx = 0
if (btnFwd)  ny += 1
if (btnBack) ny -= 1
if (btnLeft) nx -= 1
if (btnRight)nx += 1
runMecanum(nx, ny)
ButtonMaskBytenx, ny
↑1b0, +1
↖5f−1, +1
↗9j+1, +1
↙6g−1, −1
↘10k+1, −1
■ STOP0a0, 0

Because each packet carries the complete state rather than a change, a lost packet repairs itself on the next one. A held direction is re-sent periodically, which lets the firmware's watchdog tell "still held" from "the release packet was dropped".

The hardware trade-off: why the 5×5 matrix stays dark

This is the least obvious decision in the firmware, and it was made twice for the wrong reason before being made for the right one. On this chassis, four matrix pins are already taken:

Pins driven by the 5×5 matrix:  P3  P4  P6  P7  P9  P10
                                 │   │       │       │
              line sensor L ─────┘   │       │       │
              line sensor C ─────────┘       │       │
              NeoPixel strip ───────────────-┘       │
              line sensor R ─────────────────────────┘

  display on  ─▶ these pins are multiplexed
              ─▶ sensor reads return noise
              ─▶ the strip will not light

  therefore:  led.enable(false)   once, at startup

The firmware keeps all its glyph code behind a USE_MATRIX constant rather than deleting it: setting it back to true restores the display, at the cost of line following and the strip.

A corollary: light level is unusable on this robot. The micro:bit senses light with its own matrix, so input.lightLevel() re-enables the display — and takes P7 back from the strip twice a second. The symptom was a strip that lit at boot and then stayed dark.

Three-sensor line following

The truth table is taken verbatim from Keyestudio's own program, not derived: on this chassis 1 means "on the line".

The Firmware dialog, and the firmware copied into the page

The ⚙ Firmware button reuses the app's existing modal and shows the full source, the version, the extensions and the Bluetooth block. As with the simple page, the source is embedded rather than loaded with fetch(), which is blocked on file://. Here that costs about 104 KB inside index.html, hence the tool:

node tools/embed-firmware.cjs          # rewrite index.html
node tools/embed-firmware.cjs --check  # exit non-zero on drift

The .cjs extension is not a whim: package.json declares "type": "module", so a .js file would be treated as an ES module and require() would fail.

Pin map and hardware trade-offs

FunctionPinConsequence
Line sensors L / C / RP3 / P4 / P10Matrix pins → led.enable(false) required
NeoPixel strip (4 LEDs)P7
UltrasonicP15 / P165 V from the battery
ServoP14—
Motors, headlightsI2C 0x30V1 used 0x47

The strip is on P7, which Keyestudio does not document for V2: the V2 extension exposes no RGB function at all, and setLed() only handles the two headlights on/off. The pin was found with a boot-time scan, kept behind the NP_PIN_SCAN constant. Note that P8 is the V1 pin and is wrong here.

Troubleshooting

SymptomCause / fix
Connects, acknowledges, but nothing movesFirmware written for the V1 extension on a V2 board. The namespace must be mecanumRobotV2, and state() takes no argument.
The strip never lightsThree possible causes: wrong pin (P7, not P8), matrix still enabled, or an input.lightLevel() call somewhere — it re-enables the display and takes P7 back.
Line sensors report nonsenseUSE_MATRIX left at true. P3, P4 and P10 belong to the display.
The top half of the speed slider does nothingThe scale is 0–100, not 0–255.
Distance always 0Check the 5 V supply and the sensor connector, mounted on the moving head. The robot must be stationary: polling is suspended while the wheels turn.
The graph shows "waiting for UPD…"A single sample draws no line. On a current build a lone sample renders as a dot, and Auto polls in every mode.
The first connect takes ten secondsExpected: full layout transfer. Later connects use the CFGVER hash and are instant.
Values move on their own with no robotOlder build: the demo simulator ran on top of a live link. Fixed by disabling it as soon as a config comes from the device.
The Firmware dialog shows an old versionRe-run node tools/embed-firmware.cjs.
