This article covers micro:bit Playground, the most feature-complete of the family's micro:bit web apps: an 8-tab BLE control panel with live sensor graphing, five interactive 3D robot models, and a dedicated firmware protocol covering more than 30 distinct commands.

Overview

micro:bit Playground is a web-based control panel for the BBC micro:bit V2 over Bluetooth Low Energy: eight tabs covering LED/text/buzzer control, live sensor readouts with sparklines, two servo channels, a GamePad D-pad, a Chart.js live graph with recording/replay/CSV export, five interactive Three.js 3D robot models synced to real sensor data, a raw-command bench for experts, and a grab-bag "More" tab of extra widgets (joystick, keypad, XY pad, pin control, and more). Unlike its two simpler siblings (Bit-Bot, Talking Robot), it has no AI provider and no speech features at all — its whole focus is turning every micro:bit sensor and output into something you can see, graph, and drive from a browser.

It's also architecturally the most mature of the three: instead of one giant inline <script>, the JavaScript is split into nine focused files under js/, loaded in a fixed dependency order, plus five further files under js/models/ for the 3D robots.

Quick start

  1. Flash makecode.ts to a BBC micro:bit V2 via makecode.microbit.org (see Getting the firmware).
  2. Open the live app in Chrome or Edge.
  3. Click Connect and pick your micro:bit from the Bluetooth device picker — the status chip turns green once connected.
  4. Explore the 8 tabs (or press 1–8 to jump straight to one).

Step-by-step: clone, flash & test

This walkthrough takes a bare checkout to a verified-working dashboard: sensors updating live, LEDs controllable, and one 3D model animating in sync.

1. Clone the repository

git clone https://github.com/abourdim/bit-playground.git
cd bit-playground

2. Flash the firmware

Open makecode.microbit.org, create a project, switch to the JavaScript tab, paste the contents of makecode.ts, then Download and flash it to your micro:bit V2. Power it via USB or batteries — it shows an X icon once it's advertising over Bluetooth and waiting for a connection.

3. Serve the app locally

No build step is required, but Web Bluetooth refuses a bare file:/// path:

npm run serve

(a thin wrapper around npx serve ., already in package.json) and open the printed http://localhost:... URL in Chrome or Edge. The live GitHub Pages copy works identically without any local setup.

4. Connect and confirm telemetry

Click Connect, pick your board. On the Sensors tab, Temperature/Light/Sound/Accelerometer/Compass should all start updating within a second, each with its own live sparkline.

5. Test an output: the LED matrix

On the Controls tab, click a few cells in the 5×5 grid, or tap the ❤️ Heart preset, and confirm the physical board's LEDs match what's drawn on screen.

6. Test a 3D model

Open the 3D Board tab, pick the micro:bit V2 model, and tilt the physical board — the 3D model should tilt to match within a fraction of a second, and its LEDs should mirror whatever pattern is currently shown.

7. Test the graph with no firmware changes needed

On the Graph tab, click 🎲 Simulate — the firmware starts streaming synthetic Sine/Random/Ramp data every 200ms with no sensor or wiring involved, which is the fastest way to confirm the whole BLE→chart pipeline works before trusting a real sensor reading.

A working baseline looks like: five live sensor sparklines, LED clicks reflected instantly on the physical board, the 3D model tilting with the real board, and a moving Simulate-mode graph — all before you've touched a servo, GamePad, or the More tab.

The JS module layout and load order

Nine files under js/, loaded via plain deferred <script> tags in a fixed order because later files assume earlier ones already ran:

#FileResponsibility
1lang.jsi18n: LANG dictionary (en/fr/ar) + t(key) lookup. Loaded first — everything else calls t().
2core.jsDOM refs, event bus, toast notifications, logging, keyboard shortcuts.
3ble.jsConnect/disconnect/reconnect, UART chunked sends, incoming-line dispatch.
4sensors.jsParses telemetry lines, updates sensor UI + sparklines, feeds Graph and 3D.
5controls.jsLED matrix, buzzer, tab switching, bench, theme picker, page init.
6servos.jsServo sliders/gauges/trim, connection-aware enable/disable.
7others.jsThe "More" tab: joystick, timer, presets, debug console, data capture, XY pad.
8graph.jsChart.js setup, datasets, recording/replay, annotations, PNG/CSV export.
9models/*.js, then board3d.jsFive model files register themselves on window.board3dModels; the engine loads last and starts the render loop.

There's no bundler and no module system (no import/export) — every file just declares top-level functions and variables that later scripts read directly, so file order in index.html is the dependency graph.

Sending to the micro:bit: sendLine() and chunking

Every outgoing command funnels through one function in ble.js:

const BLE_MTU_PAYLOAD = 20; // typical BLE ATT payload limit

function sendLine(line) {
    const data = new TextEncoder().encode(line + '\n');
    if (data.byteLength <= BLE_MTU_PAYLOAD) {
        writeChar.writeValue(data);          // fits in one write
    } else {
        // split into 20-byte pieces, write sequentially via a Promise chain
        // so a long command (e.g. a long TEXT: string) can't corrupt mid-flight
    }
}

Auto-reconnect is a small state machine: up to MAX_RECONNECT_ATTEMPTS (3) tries, RECONNECT_DELAY_MS (2000ms) apart, tracked by a reconnectAttempts counter and a userDisconnected flag — the flag is what stops the app from fighting a deliberate disconnect click by immediately trying to reconnect.

The i18n system: lang.js and t()

1,389 lines, almost entirely one big LANG object keyed en/fr/ar, each a flat dictionary of string keys (app_title, connect_btn, dozens more). Every other file calls a single global t(key) to look up the active language's string, falling back to English if a key is missing in the current language — the same pattern used by Bit-Bot and Talking Robot's tr(), independently converged on for the same reason: one lookup function, one source of truth, easy to grep for missing keys. The Arabic flag button reuses the same accurate Algerian-flag SVG (green/white halves, red crescent and star) as the other two apps in this family.

The micro:bit firmware: prefix-matched commands

With over 30 distinct commands, this firmware doesn't use one long chain of exact-match if (cmd == "...") checks like the simpler sibling firmwares — it matches by prefix, since most commands carry a parameter after a colon:

bluetooth.onUartDataReceived(serial.delimiters(Delimiters.NewLine), function () {
    let line = bluetooth.uartReadUntil(serial.delimiters(Delimiters.NewLine)).trim()
    bluetooth.uartWriteLine("ECHO:" + line)        // every line is echoed for debugging

    if (line.substr(0, 5) == "TEXT:") { basic.showString(line.substr(5)); return }
    if (line.substr(0, 3) == "LM:")   { handleLedMatrixHex(line.substr(3)); return }
    if (line.substr(0, 4) == "TAB:")  { currentTab = line.substr(4).toLowerCase(); ... return }
    if (line == "SERVO1:OFF")         { pins.analogWritePin(AnalogPin.P1, 0); ... return }
    // ...continues for SERVO1:<angle>, SERVO2:*, BUZZ:*, CMD:*, OTHER:*, BENCH:*, JSON:*, ...
})

Every branch returns immediately once matched, so the list acts like a lookup table even though it's written as sequential ifs — order mostly doesn't matter since each prefix is unique.

Decoding the LED matrix: LM:<hex10>

The browser encodes the whole 5×5 grid as 10 hex characters (one byte per row, 5 rows), and the firmware decodes it bit-by-bit:

function handleLedMatrixHex(hex2: string) {
    if (hex2.length != 10) { bluetooth.uartWriteLine("LOG:LM_BAD_LENGTH:" + hex2.length); return }
    for (let row = 0; row <= 4; row++) {
        let value = hexPairToByte(hex2.substr(row * 2, 2))   // "1F" → 31
        for (let col = 0; col <= 4; col++) {
            const mask = 1 << col
            if ((value & mask) != 0) led.plot(col, row)
            else led.unplot(col, row)
        }
    }
    bluetooth.uartWriteLine("LOG:LM_OK:" + hex2)
}

Each row-byte's 5 low bits map one-to-one onto the 5 LED columns in that row via a bitmask — the same encoding the LEDS:<r0>,<r1>,<r2>,<r3>,<r4> telemetry line uses in reverse to report the LED state back to the browser for the 3D model to mirror.

Pin conflict guards

Servos and the buzzer share physical pins with the touch sensors (P1/P2/P0). Rather than letting them fight, the firmware sets a boolean flag (servo1Active, servo2Active, buzzerActive) whenever that feature is in use, and the touch-polling loop checks the flag before reading — sending SERVO1:OFF clears the flag and hands the pin back to touch sensing. It's a small but instructive example of one micro:bit peripheral needing to explicitly yield a shared resource to another.

BLE protocol reference

Nordic UART over BLE, 20-byte MTU with auto-chunking, device name filter BBC micro:bit. A representative slice of the full command set (see the README for the complete table of ~30 OTHER:* commands):

DirectionMessageMeaning
micro:bit → browserTEMP:<C>, LIGHT:<0-255>, SOUND:<0-255>, ACC:<x>,<y>,<z>, COMPASS:<0-360>Live telemetry, each throttled and only sent on change.
micro:bit → browserLEDS:<r0>,<r1>,<r2>,<r3>,<r4>Actual LED state (each row 0–31), keeps the 3D model in sync.
browser → micro:bitLM:<hex10>Set the whole 5×5 LED matrix in one message.
browser → micro:bitSERVO1:<angle> / SERVO1:OFFMove servo 1 (0–180°, smooth stepping) or release its PWM.
browser → micro:bitSIMULATE:ON/OFFFirmware streams synthetic Sine/Random/Ramp graph data every 200ms.
browser → micro:bitCAL:COMPASSTriggers the built-in tilt-to-fill-screen calibration game.

Calibration system

All calibration is user-triggered — nothing runs automatically at startup, and every result persists to localStorage:

CalibrationHowStored where
🧭 CompassClick Calibrate → sends CAL:COMPASS → firmware's built-in tilt game → CAL:COMPASS:DONEFirmware side; compass polling stays off until this runs.
⚖️ Accelerometer zeroLay the board flat → "Set Level" captures X/Y/Z as an offset subtracted from future readingsBrowser localStorage only.
🔊/💡 Sound & light baseline"Set Ambient" in current conditions → subsequent readings shown as a deltaBrowser localStorage only.

Themes & languages

Four visual themes (Stealth dark default, Neon cyberpunk, Arctic light, Blaze warm light) built on 30+ CSS custom properties, saved to localStorage. Full English/French/Arabic UI translation via lang.js, with the same accurate Algerian flag used across this app family for Arabic and right-to-left layout support.

Getting the firmware

Unlike Bit-Bot and Talking Robot, this project doesn't yet have a dedicated copy-paste flash.html page — the firmware lives directly in makecode.ts at the repository root, with the full protocol documented in its own header comment. Open it on GitHub, copy the contents, and paste into a new makecode.microbit.org JavaScript project as described in Step-by-step above.

Troubleshooting

SymptomCause / fix
Connect button does nothingNeeds Chrome or Edge and a secure context (HTTPS or localhost) — Safari and Firefox don't support Web Bluetooth at all.
Servo fights with touch on the same pinExpected while the servo is active; send SERVO1:OFF/SERVO2:OFF to release the pin back to touch sensing.
Compass never updatesBy design — polling is off until you run Calibrate once from the Sensors tab.
3D model doesn't moveCheck "Live Sync" is enabled on the 3D Board tab, and that the correct model is selected for the sensor you're watching (e.g. the Buggy model ignores Compass).
Reconnect keeps failingFirmware may have changed since pairing; re-flash makecode.ts and forget/re-pair the device in your OS Bluetooth settings if it still won't connect after 3 auto-retry attempts.
