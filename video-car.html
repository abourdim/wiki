Overview

VideoCar is an enhanced firmware and web control page for the keyestudio ESP32-CAM Video Smart Car. It builds on keyestudio's stock sketch, adding a virtual joystick, a connection-loss failsafe, snapshot/video capture, a redesigned control UI, and a PlatformIO build system alongside the original Arduino IDE sketch.

Hardware assembly: the official keyestudio KS5017 tutorial covers the kit list, assembly steps, pinout, and the original stock code this project builds on. Start there for physical assembly; this repo picks up once the car is built and the stock sketch runs.
Vision features need internet: the default AP mode (ap = 1) hosts an isolated keyes1 network with no internet. Pose, Hand tracking, Facial expression, Plates, AI Vision, and the jsQR fallback all download models from a CDN on first use, so they fail to start on the car's own AP. Driving, video streaming, snapshots, and recording all work fine there. To use the model-backed features, set ap = 0 with your router's SSID/password and reflash. The exception is QR / Barcode on Chrome/Edge/Android Chrome, which uses the browser's built-in BarcodeDetector and needs no network at all.

Quick start

Arduino IDE (known-good baseline): open Codes/4_VideoCar/4_VideoCar.ino, select your esp32 board package version under Tools > Board > Boards Manager, enable Tools > PSRAM: Enabled, select the AI-Thinker ESP32-CAM board, and flash as usual.

PlatformIO:

./launch.sh

Walks you through checking/installing PlatformIO, building, flashing, and opening a serial monitor.

Once flashed, connect to the keyes1 WiFi network (password 88888888) and open http://192.168.4.1 in a browser.

New to this, or want to drive the car from your own scripts? ports.html in the repo is a step-by-step guide to both servers — what port 80 and port 81 each do, every endpoint with its value ranges, and the 500ms failsafe that catches people out the first time they try to drive it with curl. The full walkthrough below is adapted from it.

Step-by-step: clone, flash & test

This walkthrough takes you from a bare checkout to a car driving on the desk and both web servers verified working. No prior knowledge of HTTP assumed; nothing here requires editing or recompiling the firmware.

Put the car on blocks before any of the driving steps. A book under each side, wheels clear of the desk. You are about to send it commands by hand, and it is easy to send "forward" and then go looking for the stop command while it drives off the table.

1. Clone the repository

git clone https://github.com/abourdim/video-car.git
cd video-car

A car with the KS5017 kit already assembled per the official keyestudio tutorial, and a USB cable to the ESP32-CAM's FTDI adapter.

2. Pick a build system and flash

Option A — Arduino IDE (known-good baseline): open Codes/4_VideoCar/4_VideoCar.ino, select your esp32 board package version under Tools > Board > Boards Manager, enable Tools > PSRAM: Enabled, set Tools > Partition Scheme to one with enough app space (e.g. "Huge APP (3MB No OTA/1MB SPIFFS)"), select the AI-Thinker ESP32-CAM board, and click Upload.

Option B — PlatformIO:

./launch.sh

Walks you through checking/installing PlatformIO, selecting the 4_videocar app, building, flashing, and opening a serial monitor (menu options 0 through 8).

Watch the serial monitor (115200 baud) while it boots. A healthy boot looks like:

VideoCar v1.5.0  |  built Jul 26 2026 12:47:05  |  33fd730
Starting web server on port: '80'
Starting stream server on port: '81'
Camera Ready! Use 'http://192.168.4.1' to connect

3. Get on the same network as the car

Default (access point mode). The car makes its own WiFi network. On your phone or laptop, join:

network:  keyes1
password: 88888888

The car is then always at 192.168.4.1. It has no internet connection — it is a network of exactly two devices, you and the car. On a phone, expect (and ignore) a warning that the network has no internet.

If you reflashed with station mode (ap = 0), the car joins your router instead and the router decides its address — read the boot message on the serial console for the actual IP and use that in place of 192.168.4.1 below.

4. Open the control page — port 80

http://192.168.4.1/

No port number needed; the browser fills in 80 silently. You should see the dark control page, live video within a second or two, and a build stamp in the footer.

Blank page or a spinner forever? Confirm you typed http:// and not https:// — the car speaks plain HTTP only, and some browsers try HTTPS first and give up quietly.

5. Watch the raw video — port 81

Open a new tab and go to:

http://192.168.4.1:81/stream

You get the video on its own, filling the window, with no page around it — the same MJPEG data the control page wraps in an <img> tag. If this tab shows video, the camera and both servers are fine and any problem is in the page. The tab spinner never stops — that's correct, the response never finishes. Close this tab before driving; every open stream consumes one of the camera's limited frame buffers.

6. Take a single photo

http://192.168.4.1/capture

One JPEG taken the moment you ask, then the connection closes normally — the opposite of the stream. From a terminal:

# save one frame as shot.jpg
curl http://192.168.4.1/capture -o shot.jpg

7. Ask the car what it is doing

http://192.168.4.1/status

Returns JSON with every current setting plus firmware version, build time, and git revision:

{"framesize":5,"quality":10,"vflip":1,"hmirror":1,
 "speed":8,"trim":0,"flash":0,
 "version":"1.5.0","build":"Jul 26 2026 12:47:05","gitrev":"33fd730"}

This is what the control page itself calls on load to restore your sliders, and every two seconds after as a connection check.

8. Change a setting by hand

Settings use one endpoint with two parameters: var (what to change) and val (the new value). Try the headlight, which is harmless and obvious:

# half brightness
http://192.168.4.1/control?var=flash&val=128

# off again
http://192.168.4.1/control?var=flash&val=0

From a terminal, note the quotes — & means something special to most shells, so the URL must be quoted:

curl "http://192.168.4.1/control?var=flash&val=128"

The white LED on the front should come on, then off. Settings are saved to the car's flash and survive a reboot.

9. Drive it — and meet the failsafe

Driving uses the same endpoint with var=car:

val=1  forward     val=4  turn right
val=2  backward    val=5  stop
val=3  turn left
curl "http://192.168.4.1/control?var=car&val=1"

The wheels turn for about half a second and stop — nothing is broken. The firmware stops the motors if 500ms pass with no new command, so a dropped WiFi connection or a closed laptop can't leave it driving forever. One command is a lease, not an instruction — to keep moving, keep renewing it, which is exactly what the control page does every 100ms. To drive forward for three seconds from a terminal:

# macOS / Linux
end=$((SECONDS+3))
while [ $SECONDS -lt $end ]; do
  curl -s "http://192.168.4.1/control?var=car&val=1" > /dev/null
  sleep 0.1
done
curl -s "http://192.168.4.1/control?var=car&val=5" > /dev/null   # stop

10. Steer smoothly instead of in four directions

/control?var=car only knows four directions and stop. For proportional control — any direction, any speed — use the joystick endpoint (both values -100 to 100; x is steering, y is throttle):

http://192.168.4.1/joystick?x=0&y=100      full speed ahead
http://192.168.4.1/joystick?x=100&y=0      spin right on the spot
http://192.168.4.1/joystick?x=-50&y=60     forward, curving left
http://192.168.4.1/joystick?x=0&y=0        stop

The same 500ms failsafe applies — repeat it roughly ten times a second for as long as you want to move.

11. Run the quick test script

Checks both servers and reports what it finds (wheels on blocks — it drives briefly):

#!/bin/bash
CAR=http://192.168.4.1

echo "--- port 80: status ---"
curl -s $CAR/status || echo "NO RESPONSE on port 80"
echo

echo "--- port 80: still photo ---"
curl -s $CAR/capture -o /tmp/shot.jpg && ls -l /tmp/shot.jpg

echo "--- port 81: stream (first 2 seconds) ---"
curl -s --max-time 2 $CAR:81/stream -o /tmp/stream.bin
echo "received $(wc -c < /tmp/stream.bin) bytes of video"

echo "--- drive forward 1s, then stop ---"
end=$((SECONDS+1))
while [ $SECONDS -lt $end ]; do
  curl -s "$CAR/control?var=car&val=1" > /dev/null; sleep 0.1
done
curl -s "$CAR/control?var=car&val=5" > /dev/null
echo "done"

A healthy car gives you a line of JSON, a shot.jpg of a few kilobytes, tens of kilobytes of video, and one second of wheel movement. If the JSON arrives but the video doesn't, the stream server failed to start — check the serial console at boot for both port: '80' and port: '81' lines.

Full endpoint reference — port 80

RequestReturnsNotes
GET /HTML The control page. Sent with Cache-Control: no-store, so you always get the page belonging to the firmware that is actually running.
GET /statusJSON All current settings plus firmware version, build time and git revision.
GET /captureJPEG One still frame at the current resolution and quality.
GET /control?var=…&val=…empty Settings and basic driving. See the values table below.
GET /joystick?x=…&y=…empty Proportional driving. Both −100 to 100; out-of-range values are clamped, not rejected.

Values for /control:

varvalEffect
car1–5 1 forward, 2 backward, 3 left, 4 right, 5 stop. Subject to the 500ms failsafe — repeat to keep moving.
speed0–8 Overall speed cap. Multiplied by 31 internally, so 8 means a PWM ceiling of 248 out of 255.
trim−32–32 Corrects a car that drifts when it should go straight. Negative favours one motor, positive the other.
flash0–255 Front LED brightness.
framesize0–6 Resolution. 0 = 96×96, 1 = QQVGA, 2 = QCIF, 3 = HQVGA, 4 = 240×240, 5 = QVGA 320×240 (default), 6 = CIF. Bigger is slower.
quality10–63 JPEG quality, runs backwards: lower numbers look better and produce bigger frames.
vflip0 or 1Flip the picture vertically.
hmirror0 or 1Mirror the picture horizontally.

Everything except car is saved to the car's flash memory and survives a power cycle. Only car and /joystick reset the failsafe timer — changing a setting does not count as "I am still here".

Full endpoint reference — port 81

RequestReturnsNotes
GET :81/stream multipart/x-mixed-replace Endless JPEG frames. The only endpoint on this port.

Frames are separated by a fixed boundary marker, each with its own Content-Type: image/jpeg and length, and the server sends Access-Control-Allow-Origin: * so a web page on port 80 is allowed to read the pixels — which is how the vision features work.

Things that will trip you up

  • Only one device can join the car's WiFi. The access point is configured for a single client. An ungraceful disconnect can hold the slot for a minute or two — if you can't reconnect, wait, or power-cycle the car.
  • One stream viewer at a time, in practice. Nothing stops you opening two, but they compete for camera buffers and both suffer.
  • There is no password on any of this. Anyone on the network can drive the car, and every command is a plain URL. Treat the car's network as untrusted and don't leave it running unattended.
  • & needs quoting in a shell. An unquoted & tells most shells to run the command in the background, so only the first parameter arrives. Always quote the whole URL.
  • Don't write :80 explicitly. Some of the page's JavaScript builds the stream URL from the current address, and an explicit :80 turns into a broken :80:81. Just omit it.
  • Higher resolution is not free. framesize=6 quadruples the data over the same WiFi. If the stream turns into a slideshow, go back to 5.
  • Settings persist, so surprises persist too. If the car boots with the light on or the picture upside down, that's a saved setting from last time, not a fault.

Features (vs. the stock keyestudio sketch)

FeatureDescription
Joystick controlDraggable on-screen joystick (/joystick?x=&y=), arcade-mixed to per-wheel PWM, alongside the original D-pad/keyboard controls.
Connection-loss failsafeAuto-stops if no command is received for 500ms. WiFi auto-reconnect, MJPEG stream auto-recovery, live connection indicator.
Settings persistenceSpeed, Trim, Lights, Quality, Resolution, Flip, and Mirror remembered on-device (NVS flash) and in the browser (localStorage).
Live flip/mirror togglesFix camera orientation live via set_vflip/set_hmirror, no reflash needed.
Pose detectionMoveNet skeleton tracking over up to a few people at once.
Hand trackingMediaPipe Hands via TF.js, 21 keypoints per hand plus left/right handedness.
Facial expressionhappy/sad/angry/surprised/etc. via @vladmandic/face-api.
QR / BarcodeBrowser's native BarcodeDetector where available (no network needed); jsQR fallback otherwise.
PlatesExperimental license-plate reader: COCO-SSD car/truck/bus boxes + Tesseract.js OCR on the cropped region. Heuristic, not a trained detector.
AI VisionToggleable overlay detecting objects (COCO-SSD) and faces (BlazeFace) live over the viewfinder, entirely in-browser.
Build stampFirmware version, build timestamp, and git revision reported in the control page footer, /status, and serial console (with a -dirty suffix for uncommitted changes).
Classic CV (no models, no internet)Motion (frame differencing), Line follower (adaptive threshold, dark-on-light or light-on-dark), and Colour chase (rg-chromaticity blob tracking) — all plain pixel maths, running at full frame rate.
Offline model cacheVision features cache CDN scripts/models in IndexedDB after first use over a network with internet, then work from the car's own AP afterward.
Follow-me (autonomous)Proportional controller drives the car toward a chosen COCO-SSD target (person, ball, dog, cat, bottle, chair) via the same /joystick endpoint manual driving uses, so the 500ms failsafe covers it too. Disarmed by default; any manual input takes over instantly.
Snapshot & video recordingCapture panel downloads a still JPEG or records .webm/.mp4 client-side (Canvas + MediaRecorder).
Redesigned control pageDark mission-control / camera-viewfinder HUD theme, grouped panels, live slider readouts, responsive layout.
Camera init resilienceRetries at a lower XCLK before giving up, blinks a visible LED error pattern, enables the brownout-detector workaround.

Line and Colour chase drive the car and share Follow-me's arbiter and safety rules: manual input always wins, only one autonomous mode runs at a time, and a lost target stops the car and then disarms. Motion is passive and keeps running alongside whatever else is steering.

Codes/4_VideoCar and firmware/4_videocar/src are kept in sync — same source, two build systems. The other three sketches (1_blink, 2_breathing_light, 3_motor) are simple unmodified demos included for a complete workshop package.

Build systems

PlatformIO (firmware/)

Each sketch is its own PlatformIO project under firmware/<name>/, all targeting env:esp32cam (AI-Thinker pinout).

SettingValueWhy
platformespressif32@6.5.0Pinned so PlatformIO doesn't silently pull a different esp32-camera driver version than Arduino IDE has, which changes camera sensor-probe behavior.
board_build.partitionshuge_app.csvThe camera+WiFi+webserver binary doesn't fit the default partition table.
build_flags-DBOARD_HAS_PSRAM, -mfix-esp32-psram-cache-issueArduino IDE's PSRAM: Enabled menu sets these behind the scenes; PlatformIO's generic board definition does not. Root cause of "works in Arduino IDE, camera fails in PlatformIO" (Camera init failed with error 0x106).
upload_speed460800Safer default than 921600 for boards flashed through a bare FTDI adapter with no auto-reset circuit.

launch.sh menu:

0) Select app               5) Build + Flash + Monitor
1) Check installation       6) Serial monitor
2) Install PlatformIO       7) List serial ports
3) Build firmware           8) Clean build
4) Flash firmware

Arduino IDE (Codes/4_VideoCar/)

Standard Arduino IDE flow. Make sure Tools > PSRAM is set to Enabled and Tools > Partition Scheme is set to a scheme with enough app space (e.g. "Huge APP (3MB No OTA/1MB SPIFFS)").

Troubleshooting

SymptomCause / fix
Camera init failed with error 0x106 (PlatformIO only, works in Arduino IDE) ESP_ERR_NOT_SUPPORTED from the camera sensor probe — a toolchain/build-flag mismatch, not hardware. Run ./launch.sh option 8 (Clean) and confirm the pinned platform version roughly matches your Arduino IDE's esp32 core version.
Repeated resets right after a camera error Usually a marginal power supply — camera + WiFi init draws a current spike many FTDI adapters can't supply cleanly. Use a proper 5V/2A source.
Car doesn't stop when the browser tab closes / WiFi drops Shouldn't happen — check the build stamp in the footer; nogit or an unexpected commit means you may be running stock keyestudio firmware with no failsafe.
A Vision feature can't load, on the car's own WiFi Expected the first time — the car's AP has no internet. Join a router, enable the feature once so it caches, then return to the car's AP.
Video feed dies when a Vision/autonomy feature starts CORS mismatch between the page and port 81's stream. The page detects this and reconnects without CORS after two failures, falling back to /capture polling.
Line follower doesn't move at all Put the Speed slider at maximum — it multiplies with the mode's own cap. Raise LINE_SPEED in app_server.h if still stuck.
Line follower weaves or loses the line Lower LINE_KP rather than raising it (latency-dominated loop). Raise LINE_TURN_CUT if it misses corners.
No authentication on the control endpoints: known, unaddressed limitation carried over from the original sketch. Anyone on the keyes1 WiFi network (default password 88888888) can drive the car.
