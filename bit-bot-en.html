Overview

Bit-Bot is a zero-install, single HTML file web app: an animated robot face you talk to by voice or text, which answers using an AI provider of your choice (or a fully offline demo mode). It optionally pairs with a BBC micro:bit over Web Bluetooth, mirroring emotions and commands onto the micro:bit's 5×5 LED display and reading back its sensors during games.

The whole app — UI, translation system, AI calls, Bluetooth handling — lives in one index.html, plus a separate flash.html page for getting the companion micro:bit firmware and a few microbit_makecode_*.js files with that firmware's source.

Quick start

  1. Open the live app in Chrome or Edge (Web Bluetooth and Speech APIs are required, so Safari/Firefox won't fully work).
  2. Walk through the 4-step onboarding: name your robot, pick a personality, optionally connect a micro:bit.
  3. Tap the 🎤 microphone or type a message, then hit send. The robot answers in the chat bubble and speaks it out loud.

Step-by-step: clone, flash & test

This walkthrough takes a bare checkout to a fully working robot — text chat, voice, and (optionally) a paired micro:bit — with nothing assumed beyond having Chrome or Edge installed.

1. Clone the repository

git clone https://github.com/abourdim/bit-bot.git
cd bit-bot

2. Serve it locally

There's no build step — it's plain HTML/CSS/JS — but the Web Speech and Web Bluetooth APIs both refuse to run from a bare file:/// path, so serve the folder over HTTP:

python3 -m http.server 8000

Then open http://localhost:8000 in Chrome or Edge.

3. Get the micro:bit firmware (optional)

Skip this step entirely if you just want to test text/voice chat. Otherwise, open flash.html, tap Copy micro:bit Code, paste it into a new makecode.microbit.org project's JavaScript tab, add the bluetooth extension, set Project Settings → "No Pairing Required", and flash it to the board.

4. Test text chat

With no API key configured, the app runs in 🎮 Demo mode automatically — type a message and press send; you should get a canned but on-personality reply with no network calls at all. This confirms the UI and state machine work before involving any real AI provider.

5. Test voice

Tap the 🎤 button, allow the microphone, and speak. A healthy run shows the transcribed text appear, then a spoken reply with the robot's mouth/eyes animating while it talks.

6. Test the micro:bit connection

Tap the connection badge in the header, pick your board from the Bluetooth device picker, and wait for a happy face — both on screen and on the micro:bit's own LED grid. If it never appears, see Troubleshooting.

7. Test a game

Open the 🎮 panel and start Smart Tilt Quiz. Even with no AI key and no micro:bit connected, it should still ask a question from the built-in fallback bank (tap the on-screen A/B labels, or tilt the micro:bit if paired) — confirming the game logic and fallback content work independently of any network call.

A working baseline looks like: Demo-mode replies with no key, voice in and out, a happy face on the micro:bit after pairing, and a quiz question you can answer either way. Only after that works is it worth troubleshooting a specific AI provider's key.

Understanding the code (for newbies)

This section is for anyone who has the app running and wants to open index.html and start changing something. It assumes basic JavaScript but no prior knowledge of this codebase. Skip it entirely if you only want to use the app.

The shape of the file

Everything — markup, CSS, and JavaScript — lives in one index.html, several thousand lines long, in three blocks: a <style> block, the HTML body (header, onboarding card, chat UI, settings panel, help modal, games/commands panels), and one big <script> at the end with no module system — every function is a plain top-level function declaration, callable directly from inline onclick="..." attributes in the HTML.

The state object

One plain object holds everything that needs to persist or drive the UI: connection status, the current AI provider and its keys, the robot's name and personality, chat history per personality, and UI preferences like language and theme. It's saved to localStorage as JSON on every relevant change (saveSettings()) and restored on load (loadSettings()) — there's no other persistence layer.

The translation system: I18N → tr() → data-i18n

Every user-facing string lives in an I18N object keyed by language (en/fr/ar), then by a short key:

const I18N = {
  en: { onb_welcome_title: "Welcome!", ... },
  fr: { onb_welcome_title: "Bienvenue !", ... },
  ar: { onb_welcome_title: "مرحباً!", ... }
};
function tr(key) { return I18N[state.lang][key] ?? I18N.en[key] ?? key; }
function trg(key, vars) { /* tr() plus {placeholder} substitution */ }

Static HTML elements are tagged data-i18n="onb_welcome_title"; applyLang(lang) walks every tagged element and sets its text from tr(). Dynamic strings (toasts, log lines, AI-game narration) call tr()/trg() directly from JavaScript instead. Switching language is one function call, setLanguage(lang), which re-runs applyLang() and persists the choice.

How a chat message flows: user input → AI → robot

  user types/speaks
       │
       ▼
  sendMessage()  ──▶  addBubble('user', text)
       │
       ▼
  callAI(text)  ──▶  branches on state.provider:
       │                     Demo → getDemoResponse() (canned, offline)
       │                     Groq / Gemini / Cohere / Mistral / OpenRouter
       │                       → fetch() to that provider's REST API
       ▼
  parse reply, strip [command] tags
       │
       ▼
  addBubble('robot', text)  +  speak(text)  +  sendCommand(emotion)

The AI's system prompt always ends with a language directive built from tr('ai_lang_directive'), so the model itself replies in the currently selected UI language rather than only the fixed interface text being translated. sendCommand() both updates the on-screen face and, if a micro:bit is connected, writes the same command over Bluetooth.

Talking to the micro:bit: connect(), sendCommand(), handleRx()

connect() calls navigator.bluetooth.requestDevice() filtered to the Nordic UART service, then discovers the TX (notify, micro:bit→browser) and RX (write, browser→micro:bit) characteristics. Every outgoing command — an emotion, a game input, a servo move — goes through one function, sendCommand(cmd), which writes it as a UTF-8 line to the RX characteristic. Anything the micro:bit sends back (button presses, sensor readings) arrives as a characteristicvaluechanged event handled by handleRx(), which parses the line and dispatches it — e.g. into processScienceReading() during the Science Detective game.

The onboarding step machine

Onboarding is four HTML cards, only one visible at a time, driven by a single currentOnboardingStep integer. nextOnboardingStep()/prevOnboardingStep() just increment/decrement it and toggle which card has the .active class; completeOnboarding() sets state.onboardingComplete = true, saves it, and hides the whole overlay so it never shows again on that browser.

System architecture, illustrated

Two independent, optional round-trips meet in the middle of one browser tab — the AI call and the micro:bit link never talk to each other directly, only through the app's own state:

                        ┌─────────────────────────┐
                        │   index.html (browser)  │
                        │  ─────────────────────  │
   🎤 mic / ⌨ keyboard ─▶│  sendMessage()          │
                        │       │                 │
                        │       ▼                 │
   AI provider API   ◀──▶  callAI(text)           │
   (Groq/Gemini/...)     │       │                 │
                        │       ▼                 │
                        │  addBubble()+speak()    │
                        │       │                 │
                        │       ▼                 │
   BBC micro:bit     ◀──▶  sendCommand(emotion)   │
   (Bluetooth LE)        │  handleRx() ◀── sensors│
                        └─────────────────────────┘

The AI leg is HTTP over WiFi/data (skipped entirely in Demo mode); the micro:bit leg is Bluetooth LE, paired once per browser session. Either can be absent — the app is fully usable with neither, one, or both connected.

The HTML layout, illustrated

Inside <body>, the markup is a flat stack of independently-shown/hidden overlays plus the always-visible chat screen underneath:

  <body>
   ├─ #onboarding        first-run wizard, 4 cards, one .active at a time
   ├─ #helpOverlay        ❓ quick-reference modal
   ├─ header              lang flags · robot/AI badges · connect · firmware · help · ☰
   ├─ main                robot face + chat bubbles + text/mic input
   ├─ #settingsPanel      slide-in: Fun / Setup / Advanced tabs
   ├─ #commandsPanel      📋 quick-command cheat sheet, by category
   └─ #gamesPanel         🎮 Smart Tilt Quiz / Adventure / Science Detective

Every one of those panels/overlays is just a <div> that toggles an .open (or .active) CSS class via a small toggleX() function — there's no routing, no virtual DOM, no framework. <head> holds one big inline <style> block with CSS custom properties (--primary, --surface, etc.) that [data-theme="dark"] overrides — that's the entire theming system.

The micro:bit firmware: microbit_makecode_v3.js

This is the program you flash onto the board itself — a separate, much smaller world than the web app, written in MakeCode's JavaScript/TypeScript-like dialect. It has no concept of "AI" or "chat"; all it knows is a flat vocabulary of one-word text commands arriving over Bluetooth UART, and how to react to each one on the 5×5 LED grid.

LED pictures are just text

Every face/icon is an images.createImage() call over a 5×5 grid of . (off) and # (on):

const HAPPY = images.createImage(`
    . . . . .
    . # . # .    ← eyes
    . . . . .
    # . . . #
    . # # # .    ← smile
    `)

There are 15 of these bitmaps in the file — emotions (HAPPY, SAD, ANGRY, SURPRISED, LOVE, SLEEPY, SILLY, WOW, HAHA, COOL), two animals (CAT, DOG), and five game icons (arrows, question mark, check, cross, thermometer, light bulb). Want a new face? Copy the pattern of dots and hashes for any existing one and change the shape — nothing else in the file needs to know about it until you also add it to the command handler below.

Keeping the browser's LED mirror in sync

Every time the micro:bit changes what it's showing, it also streams the full 25-pixel grid back over Bluetooth as one text line, which is what powers the ⚫ LED-mirror widget in the web app:

function sendLEDState() {
    let state = "LED:"
    for (let y = 0; y < 5; y++)
        for (let x = 0; x < 5; x++)
            state += led.point(x, y) ? "1" : "0"
    bluetooth.uartWriteString(state + "\n")
}
function showAndSync(img: Image) {
    img.showImage(0)
    basic.pause(50)   // let the image actually latch before reading it back
    sendLEDState()
}

Almost every animation calls showAndSync() rather than the raw MakeCode showImage(), specifically so the browser's mirror never drifts out of sync with the physical board.

The command dispatch table

One function, handleCommand(cmd), receives every line the browser sends and runs it through a long if / else if chain matched by exact lowercase string — there's no JSON, no structured protocol, just plain words:

Command(s)What happens on the board
happy, sad, angry, surprised/wow, love, sleepy, silly, haha, cool, cat, dogShow the matching static face/icon.
wave, dance, spin, party, magicRun a short multi-frame animation, then settle back on HAPPY.
quiz / correct,yes / wrong,no / thinkingGame-state faces: question mark, check + party, cross + sad, "confused" icon.
read_temp / read_lightShows an icon, reads the real sensor with input.temperature()/input.lightLevel(), sends it back as TEMP:<n>/LIGHT:<n>, and displays the number on the LEDs.
left/right/forward/backward, count, dice, rainbowMisc. game/utility visuals (arrows, counting 1–5, a random die roll, a flashing full-grid rainbow).
anything unrecognisedShows a QUESTION mark — the firmware never errors out on an unknown word.

Sensing the world: tilt, shake, buttons

Three input sources run independently of the command handler and only ever send data, never receive it — this is how the browser-side games get real sensor input:

basic.forever(function () {   // polled every loop, ~cooldown-gated
    let x = input.acceleration(Dimension.X)
    if (x < -TILT_THRESHOLD) bluetooth.uartWriteString("TILT_LEFT\n")
    else if (x > TILT_THRESHOLD) bluetooth.uartWriteString("TILT_RIGHT\n")
})
input.onGesture(Gesture.Shake, function () {
    bluetooth.uartWriteString("SHAKE\n")
})
input.onButtonPressed(Button.A, function () {
    bluetooth.uartWriteString("BTN_A\n")
    // ...also shows an icon locally
})

A shared INPUT_COOLDOWN (500ms) and per-input "last fired" timestamps stop a single physical tilt or shake from flooding multiple duplicate events — the same debouncing idea as the browser's 500ms driving failsafe in the sibling VideoCar project, just applied to gestures instead of motor commands.

The full round trip

  browser: sendCommand("happy")
       │
       ▼  bluetooth write (UART RX characteristic)
  micro:bit: onUartDataReceived
       │
       ▼
  handleCommand("happy")  ──▶  showAndSync(HAPPY)
       │                            │
       │                            ▼
       │                      sendLEDState()
       ▼                            │
  (nothing sent back for            ▼  bluetooth notify (UART TX characteristic)
   plain emotions — LED            │
   state is the only reply)   browser: handleRx()  ──▶  updates LED-mirror widget

  ── meanwhile, independently ──
  micro:bit: tilt/shake/button  ──▶  bluetooth notify  ──▶  browser: handleRx()
                                                                  │
                                                                  ▼
                                                          routed into the active
                                                          game's input handler

First launch: onboarding

New visitors see a 4-step onboarding card before the main app:

StepWhat happens
1. WelcomeIntro to the three headline features: Voice Chat, Micro:bit, Personalities.
2. PersonalizeType a robot name and pick one of 12 personalities.
3. Connect Micro:bitOptional Bluetooth pairing, or "Skip for now".
4. All doneA tip card, then "Start Chatting" drops you into the main app with a spoken welcome message.

Completion is saved to localStorage, so onboarding only runs once per browser.

Robot name & personality

Available personalities: Playful (default), Helpful, Pirate, Space, Hero, Dino, Fairy, Ninja, Wizard, Cowboy, Alien, Mermaid. Each has its own system prompt tone and its own separate chat history (up to the last several messages per personality), so switching personality doesn't lose the conversation you were having with another one.

The robot's name is editable any time in Settings (☰) → Fun. The name field saves on every keystroke (not just on blur) and shows a confirmation toast, so it can never silently fail to persist.

Every AI prompt — the main chat and all three mini-games — has a language directive appended based on the currently selected UI language, so the model's own generated replies come back in English, French, or Arabic rather than only the fixed interface text being translated.

Connecting a micro:bit

Tap the connection badge in the header (or during onboarding step 3) to pair over Web Bluetooth. Once connected, the robot's emotions and spoken commands are mirrored live onto the micro:bit's 5×5 LED grid, and the micro:bit's accelerometer/buttons/sensors can drive the games (see below).

Web Bluetooth requires a secure context: https:// or localhost. It will not work opened as a bare file:/// HTML file.

Getting the firmware code

The micro:bit side needs a small MakeCode program flashed once. Rather than sending people to GitHub to copy raw source by hand, flash.html is a dedicated page that:

  • Fetches the current microbit_makecode_v3.js at load time and displays it in a scrollable code block.
  • Has a single big Copy micro:bit Code button (clipboard API with an execCommand fallback).
  • Lists the six steps to paste it into makecode.microbit.org, add the bluetooth extension, enable "No Pairing Required", and flash.

It's linked from the main app's Settings → Setup tab and from a dedicated Firmware badge in the header.

Commands & AI-powered games

The 📋 button above the message box opens a categorized command cheat-sheet (Emotions, Animals, Actions, Sounds, Party, Powers) — tap any word to trigger it instantly.

The 🎮 button opens three AI-powered mini-games, all playable with a connected micro:bit's tilt/shake/buttons as input:

GameWhat it does
🎯 Smart Tilt QuizAI-generated multiple-choice quiz questions (with a hardcoded fallback bank if the AI call fails); tilt left/right to answer; difficulty adapts to your streak.
🗺️ Adventure ExplorerAn AI-narrated branching story in a randomly chosen theme (forest, space, ocean, castle, jungle); shake to look around, tilt to choose.
🔬 Science DetectiveReal sensor readings (temperature or light) from the micro:bit, explained by the AI in kid-friendly language, with a fallback explanation if the AI call fails.

Languages & translation system

The UI, all toast/status/log messages, and all game narration are fully translated across English, French, and Arabic (with right-to-left layout for Arabic) via an in-app I18N object and tr()/trg() helper functions keyed by data-i18n attributes. French is the default language. A flag-based switcher sits in the header; the choice persists to localStorage.

In-app Help

A ❓ button in the header opens a quick-reference modal (Talk to your robot, Name & personality, Connect a micro:bit, Commands & games, Tips), translated the same as the rest of the UI. Closes via the × button, Escape, or clicking outside the card.

Privacy by design: in Demo mode nothing leaves the browser. In any other AI mode, only your typed/spoken messages are sent to that provider's API — settings, robot name, and chat history stay in localStorage only.

Data & privacy

  • Demo mode works entirely offline.
  • AI modes send your messages to the selected provider's servers (Groq/Google/Cohere/Mistral/OpenRouter).
  • Settings, robot name/personality, and chat history are stored only in the browser's localStorage — nothing is uploaded anywhere else.
  • No analytics, no tracking scripts.

Troubleshooting

SymptomCause / fix
Mic or Bluetooth don't workNeeds Chrome or Edge, and a secure context (https:// or localhost) — not file:///.
Robot name doesn't seem to saveFixed: the name field now saves on every keystroke with a confirmation toast, so this shouldn't reoccur on current builds.
App stuck in English after choosing another flagCheck that JavaScript isn't blocked; the flag buttons call setLanguage(), which also persists the choice to localStorage.
micro:bit not reactingReflash with the code from flash.html — make sure the bluetooth extension and "No Pairing Required" are both set in MakeCode.
