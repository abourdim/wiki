WDIY Robot (esp32c3_super_mini_robot-bit-rxy)

WDIY Robot b3
BoardESP32-C3 Super Mini (RISC-V, native USB-CDC)
Chassis2-wheel differential drive, continuous-rotation servos
Controlbit-rxy web app over Bluetooth Low Energy (unmodified)
Build systemPlatformIO
BLE libraryNimBLE-Arduino 2.x
Built onESP32-RXY reference pattern
Repositorygithub.com/abourdim/esp32c3_super_mini_robot-bit-rxy

This article covers the esp32c3_super_mini_robot-bit-rxy firmware: a small differential-drive robot originally built around the paid RemoteXY app, converted to speak the free, unmodified bit-rxy web app's Bluetooth protocol by following the ESP32-RXY reference pattern — a BLE UART service that impersonates a BBC micro:bit closely enough that the app never needs to know it isn't talking to one.

Why a separate repo instead of editing the original: esp32c3_super_mini_robot (the RemoteXY original) is left untouched. This repo is a full clone that replaces only the control layer — everything else (servos, buzzer, NeoPixels, OLED, ultrasonic sensor, battery monitor) is unchanged. This is the sole working directory for all further robot firmware work.

Overview

The robot drives with a virtual joystick or D-Pad, honks a horn button, and reports live speed/distance/battery gauges — all through widgets built in the bit-rxy drag-and-drop builder and rendered by its Play tab, exactly as if the robot were a real BBC micro:bit running the rxy MakeCode extension. No custom app, no App Store review, no paid tier: any phone or laptop with a Bluetooth-capable browser works.

The BLE control layer (03_bit-rxy.cpp/.h) is a near-verbatim port of the ESP32-RXY reference firmware's protocol handling, adapted to drive this robot's existing servo/sensor/sound subsystems instead of a bare demo LED. Function names were kept identical to the old RemoteXY adapter (remotexy_get_joystick_01_x(), remotexy_set_sound_01(), etc.) specifically so the rest of the firmware — 04_tasks.cpp, the servo driver, the sound task — never had to change.

Quick start

git clone https://github.com/abourdim/esp32c3_super_mini_robot-bit-rxy.git
cd esp32c3_super_mini_robot-bit-rxy/01_software/01_app
./launch.sh flash

Then open abourdim.github.io/bit-rxy, tap Connect, and pick diy_app_b3 (or uBit-prefixed, depending on firmware revision) from the device chooser. The app auto-loads the robot's layout and switches to Play mode.

Step-by-step: clone, flash & test

This guide takes you from a freshly cloned repo to a robot driving on the desk with every widget verified working. No prior BLE/embedded knowledge assumed.

Put the robot on blocks before any driving step. A book under each side, wheels clear of the desk. It is easy to send "forward" and then go looking for the stop control while it drives off the table.

1. Clone the repo

git clone https://github.com/abourdim/esp32c3_super_mini_robot-bit-rxy.git
cd esp32c3_super_mini_robot-bit-rxy/01_software/01_app

A robot chassis with two continuous-rotation servos, an ESP32-C3 Super Mini, and a USB-C cable. No external USB-serial adapter is needed — the C3 uses its native USB-CDC peripheral.

2. Flash the firmware

./launch.sh flash

One-shot: compiles, uploads, and opens a serial monitor. Behind the scenes this targets env:esp32-c3-devkitm-1 with three settings that exist specifically to work around ESP32-C3 native-USB quirks:

SettingValueWhy
upload_speed115200A mid-upload baud-rate switch (the usual 115200→460800 jump) crashes the native USB-CDC endpoint with "No serial data received".
upload_flags--no-stubHanding off from the ROM bootloader to the flasher stub re-enumerates the USB-CDC endpoint mid-upload, dropping the first post-stub command ("Unable to verify flash chip connection"). Staying on the ROM bootloader avoids the re-enumeration entirely — slower (60–90s) but reliable.
monitor_dtr / monitor_rts0Native USB-CDC on the C3 misreads DTR/RTS toggles as "enter download mode" — opening a monitor with the defaults can reset or disconnect the board instead of just observing it.

A healthy boot on the serial monitor (115200 baud) ends with:

[BLE] init - device_name: diy_app_b3
[BLE] service_uuid: 6e400001-b5a3-f393-e0a9-e50e24dcca9e
[BLE] tx_char_uuid: 6e400002-b5a3-f393-e0a9-e50e24dcca9e (notify)
[BLE] rx_char_uuid: 6e400003-b5a3-f393-e0a9-e50e24dcca9e (write)
[BLE] advertising: YES

3. Connect from the bit-rxy app

Open abourdim.github.io/bit-rxy on a phone or a Bluetooth-capable desktop browser (Chrome/Edge), tap the big Connect button, and pick the robot from the device chooser — it advertises as diy_app_b3. Some firmware revisions also answer to a uBit-prefixed name, because a handful of BLE dongles refuse to filter/discover devices unless the advertised name matches the exact prefix a real micro:bit uses.

Within a second or two of connecting, the app requests the layout (GETCFG), the robot streams it back in base64 chunks, and the app renders the robot's custom widgets — joystick, D-Pad, horn, two gauges, a battery bar, and a sound alert icon — then switches to the Play tab automatically.

A successful connect looks like this: the app's connect overlay dismisses within ~1–2 seconds, the Play tab shows all six widgets (not a blank canvas or a stuck spinner), and the serial monitor prints [BLE] Sent CFG (dropped=0).

4. Drive it

Drag the joystick, or tap the D-Pad arrows — both drive the same underlying steering state, so whichever you touched most recently wins. Angle 0° is right, 90° is up, 180° is left, 270° is down (standard math convention). Forward on the joystick/D-Pad drives the robot physically forward; releasing (or centering) stops it.

5. Test the horn

Tap the Horn button. The robot beeps its buzzer, blinks the NeoPixels green, and pushes a sound_alert event back to the app, which plays a matching tone effect on your phone/laptop speaker — restoring the sound feedback the original RemoteXY UI had (sound_01), which had no equivalent in bit-rxy until the Sound widget was added specifically for this.

6. Watch the gauges

Speed, distance (ultrasonic), and battery percentage update live on their gauge/battery widgets as the robot drives — these are output-only: the robot pushes UPD messages on a throttled interval, the app never sends anything back for them.

7. Test reconnect

Close the browser tab (or walk out of range) and reopen it. The robot's onDisconnect() callback zeroes the steering state (so it can never keep driving unattended) and immediately restarts advertising — the app should find and reconnect to the same device within a few seconds, re-fetching the layout from scratch.

Understanding the code (for newbies)

This section is for anyone who has flashed and driven the robot and now wants to open the source and change something. It assumes no prior embedded/C++ experience. If you only want to drive the robot, you can skip this entirely.

The files that matter

  01_src.ino            — setup()/loop(), wires every subsystem together.
        │
        ├──▶  03_bit-rxy.cpp/.h  — the BLE control layer. Everything about talking to
        │       the bit-rxy app lives here: the GATT service, the GETCFG/CFG handshake,
        │       parsing incoming SET lines, and the remotexy_get_*/remotexy_set_*
        │       functions the rest of the firmware calls.
        │
        └──▶  04_tasks.cpp     — the robot's own logic. Reads joystick/dpad state
                via remotexy_get_joystick_01_x/y(), computes left/right servo speeds,
                and pushes speed/distance/battery back out on a throttled interval.

This split is deliberate: 03_bit-rxy.cpp knows nothing about servos or sound, and 04_tasks.cpp knows nothing about Bluetooth — they only ever talk through the small remotexy_get_*()/remotexy_set_*() function API, kept identical to the old RemoteXY adapter so that porting the transport didn't require touching the robot logic at all.

The layout: readable JSON, shipped as base64

The app's GETCFG/CFG protocol only understands base64-encoded, minified JSON — but hand-editing a base64 blob is a bad time. 03_bit-rxy.cpp keeps the actual, readable JSON as a comment directly above the encoded constant it describes:

// {
//   "schemaVersion": 1,
//   "title": "WDIY Robot b3",
//   "widgets": [
//     {"id":"joy_drive","t":"joystick","x":20,"y":20,"w":140,"h":140,"label":"Drive","model":"classic"},
//     {"id":"btn_horn","t":"button","x":200,"y":50,"w":100,"h":100,"label":"Horn","model":"neo"},
//     {"id":"dpad_drive","t":"dpad", ...},
//     {"id":"gauge_speed","t":"gauge", ...},
//     {"id":"gauge_distance","t":"gauge", ...},
//     {"id":"battery_level","t":"battery", ...},
//     {"id":"sound_alert","t":"sound", ...}
//   ]
// }
static const char* LAYOUT_CFG_BASE64 =
  "eyJzY2hlbWFWZXJzaW9uIjoxLCJ0aXRsZSI6IldESVkgUm9ib3QgYjMiLCJ3aWRnZXRzIjpb"
  ...

Edit the JSON, then regenerate the base64 constant with layout_cfg.sh (see Customising the layout) rather than editing the base64 by hand.

How a connection becomes a layout on screen

Identical hand-off to the ESP32-RXY reference firmware, because this code was ported directly from it:

  App writes "GETCFG\n" to the RX characteristic
       │
       ▼
  onWrite() (NimBLE's own host task) buffers bytes until '\n', calls handleLine()
       │
       ▼
  handleLine(): line == "GETCFG" → s_getCfgRequested = true;  return immediately
       │           (no burst runs here — see the post-mortem below for why that matters)
       ▼
  remotexy_handler(), called every loop(): if (s_getCfgRequested) sendCfg();
       │           (runs on the ordinary Arduino main task)
       ▼
  sendCfg(): delay(300ms) so the fast-connection-interval request has landed,
             sendLine("CFGBEGIN"),
             for each 18-char chunk of LAYOUT_CFG_BASE64: sendLine("CFG " + chunk); delay(50ms)
             sendLine("CFGEND")
       │
       ▼
  App concatenates the CFG chunks, base64-decodes, JSON.parses, renders the widgets

Two details differ from the plain reference firmware, both because this robot also runs FastLED/OLED/Servo alongside NimBLE, leaving less buffer headroom:

  • 50 ms between chunks instead of 15 ms. The reference firmware's faster rate starved this robot's NimBLE notify buffer pool (rc=6 / BLE_HS_ENOMEM) because of the extra peripherals competing for CPU time.
  • A 300 ms delay at the start of sendCfg(). onConnect() requests a fast connection interval via updateConnParams(), but that negotiation with the phone/laptop takes a round trip or more to actually land. The app sends GETCFG almost immediately after connecting, so without this delay the ~60-chunk burst starts on the slower default interval, which can't drain the notify buffer pool fast enough.

Reading incoming lines & wiring up widgets

handleLine() recognises two shapes — the bare string GETCFG, and lines starting with SET <id> <value>, which it splits and passes to handleWidget(id, val):

static void handleWidget(const String& id, const String& val) {
  if (id == "joy_drive")   { handleJoystick(val); return; }
  if (id == "dpad_drive")  { handleDpad(val); return; }
  if (id == "btn_horn")    { s_button_01 = (val == "1") ? 1 : 0; return; }
}

Unlike the reference firmware's prefix-matching demo (any btn_* drives the same LED), this robot matches exact widget IDs, because each one drives a specific, different piece of hardware. Add a new input widget in the Build tab, and you must also add an exact-ID branch here to wire it to something.

The joystick/D-Pad angle convention

The joystick sends "<angle> <distance>", angle in standard math convention (0°=right, 90°=up, 180°=left, 270°=down — confirmed by reading the app's own script.js, not assumed):

float rad = angleDeg * PI / 180.0f;
s_joy_x = constrain(round(dist * cos(rad)), -100, 100);
// Negated: forward/back on this chassis turned out to be the mirror of
// the joystick's up/down sense — turning (x) was already correct.
s_joy_y = constrain(round(-dist * sin(rad)), -100, 100);

The D-Pad has no angle/distance — it sends discrete "<up|down|left|right> <0|1>" press/release events, so handleDpad() tracks which of the four directions are currently held and combines them into the same x/y pair at a fixed magnitude, applying the identical y-axis mirror.

From steering state to servo pulses

tasks_joysticks() in 04_tasks.cpp runs every loop() iteration, reads s_joy_x/s_joy_y through the remotexy_get_*() API, and arcade-mixes them into per-wheel speed:

int leftSpeed  = y + x;  // forward/back + turn
int rightSpeed = y - x;
int leftPulse  = map(leftSpeed,  -100, 100, 0, 180);
// Right wheel is mounted as a mirror image of the left one, so the same
// rightSpeed sign needs an inverted pulse range to spin the same physical way.
int rightPulse = map(rightSpeed, -100, 100, 180, 0);
moveServos(leftPulse + CONFIG_SERVO_SPEED_STOP_LEFT_OFFSET,
           rightPulse + CONFIG_SERVO_SPEED_STOP_RIGHT_OFFSET);

Post-mortem: the joystick flood (fixed)

Getting BLE working reliably took three separate fix attempts, because the actual root cause was mis-diagnosed twice before it was found.

AttemptTheoryResult
1The GETCFG-burst-inside-onWrite() bug, ported from the ESP32-RXY reference firmware's own documented post-mortem.A real bug, correctly fixed (see the s_getCfgRequested flag above) — but not sufficient on its own. rc=6/BLE_HS_ENOMEM kept happening.
2Continuously-running servo PWM hardware starving the radio.Wrong — disabling servo attach() entirely did not fix it either.
3Line-by-line re-read of 04_tasks.cpp found it: tasks_joysticks() called remotexy_set_onlineGraph_02_speed() — a BLE notify() send — on every single loop() iteration, completely unthrottled.Confirmed root cause. loop() runs thousands of times per second; flooding notify() at that rate starves NimBLE's own mbuf pool regardless of what else is or isn't happening.

The fix: tasks_joysticks() now only stashes the computed value in a global, g_joystick_speed_pct; the actual BLE send moved to tasks_remotexy(), which already runs on an explicitly throttled interval alongside the distance and battery updates:

// tasks_joysticks() — every loop(), no BLE call:
g_joystick_speed_pct = max_x_y;

// tasks_remotexy() — throttled interval, does the actual sending:
void tasks_remotexy(void) {
  remotexy_set_onlineGraph_01_distance(g_ultrasonic_distance_cm);
  remotexy_set_onlineGraph_02_speed(g_joystick_speed_pct);
  remotexy_set_onlineGraph_03_battery(g_battery_percentage);
}
The general lesson: the "never call a BLE send synchronously from a fast-running task" rule from the reference firmware's own post-mortem isn't just about onWrite() — it applies to any unthrottled call site, including the ordinary Arduino loop(). If you add your own periodic sendValue() call, throttle it explicitly (a millis()-gated interval, or piggyback on tasks_remotexy()'s existing one) rather than calling it every iteration.

Sound mapping: RemoteXY's catalog → bit-rxy's 5 effects

The original RemoteXY UI used a large library of named sound-effect IDs (REMOTEXY_SOUND_ALARM, _CONFIRM, _CHIME, and so on, from 07_sounds.h). bit-rxy's Sound widget only knows 5 short tone effects, so remotexy_set_sound_01() groups the old catalog down to the closest match:

bit-rxy effectOld RemoteXY IDs it replaces
successSUCCESS, SUCCESS_ALT, SUCCESS_BEEP, POWER_ON, CONFIRM, CHIME
warnWARNING, TIMER, COUNTDOWN
dangerERROR, CRITICAL, ALARM, FAILURE, ERROR_BEEP
toggleDOUBLE_BEEP, SELECT
beep (default)everything else — BEEP, BEEP_SHORT, BEEP_LONG, CLICK, TAP, etc.

p_sound_01 == 0 is tasks_rmotexy_sound()'s own periodic "no sound" reset value and must not itself trigger a tone — guarded with an early return at the top of the function.

Customising the layout

Never hand-edit the base64 constant. Instead, use layout_cfg.sh in 01_software/01_app/:

# extract the current layout as pretty-printed JSON
./layout_cfg.sh decode 01_src/03_bit-rxy.cpp

# after editing the JSON, re-encode and get the base64 back
./layout_cfg.sh encode my_layout.json

decode pulls the LAYOUT_CFG_BASE64 string literal straight out of the .cpp file (no need to keep the JSON comment and the base64 constant in sync by hand while iterating), base64-decodes it, and pretty-prints it with python3 -m json.tool. encode does the reverse: minifies the JSON (matching the app's own separator convention, separators=(',',':')), base64-encodes it, and folds the output into 72-character lines ready to paste back into the source as chunked string-literal rows — the same shape as the existing constant.

After changing the layout, update both the readable JSON comment above LAYOUT_CFG_BASE64 and the constant itself, and add a matching exact-ID branch in handleWidget() for any new input widget — the layout and the code that reacts to it are two separate places that must be kept in sync by hand.

OTA firmware updates

Once the robot has been flashed once over USB, every update after that can go over WiFi instead — no cable, no disassembling the chassis to reach the USB-C port.

Entering OTA mode

Hold the debug button (the same one used as an in-game action button during play — see Hardware reference) at any point while the robot is running:

Hold durationResult
~3 secondsEnters OTA mode and reconnects to whatever WiFi network it last joined successfully.
~8 seconds (keep holding past the 3s point)Forgets the saved network first, then opens a setup access point — use this the first time, or whenever you want to switch networks.

Checked continuously during normal loop() execution, not right after boot — GPIO0 (the debug button's pin) is also the ESP32-C3's BOOT strapping pin, so sampling it near a reset would fight the bootloader instead of triggering this cleanly.

First-time setup: the captive portal

No WiFi SSID or password is compiled into the firmware. The first time (or after an 8-second "forget" hold), the robot opens its own access point:

WDIY-Robot-Setup

Join it from a phone or laptop — both the OLED and a purple NeoPixel blink confirm the portal is open. Most phones prompt automatically ("Sign in to network"); on a laptop, open a browser to:

http://192.168.4.1

Tap Configure WiFi, pick your real network from the scanned list, enter its password, and save. The robot connects, remembers that network from then on (this uses WiFiManager's own storage, independent of the compiled firmware), and shows its IP address on the OLED. The setup portal times out after 3 minutes if left untouched, rebooting back to normal BLE-driven play.

Pushing an update

With the robot showing OTA ready and an IP address on its OLED:

cd 01_software/01_app
./ota_flash.sh <robot-ip>

Builds from the current source and pushes it over WiFi. To flash an exact pre-built .bin instead (no rebuild — useful for a file downloaded from CI, or a known-good previous build):

./ota_flash.sh <robot-ip> path/to/firmware.bin

Progress shows on both the NeoPixels (a white pixel advances per chunk) and the OLED (live percentage). A successful update blinks green and reboots into the new firmware; a failure blinks red with an error code, without bricking the board — the previous working firmware stays in the other OTA app-partition slot untouched.

Why two .pio/build/ folders after building? platformio.ini defines two environments — esp32-c3-devkitm-1 (USB, upload_protocol = esptool) and esp32-c3-devkitm-1-ota (WiFi, upload_protocol = espota, no serial-specific upload_flags). PlatformIO always gives each environment its own isolated build cache, even when one extends the other and only overrides a couple of settings — that's normal, not a sign anything's wrong.

Troubleshooting

SymptomCause / fix
Upload fails with "No serial data received"A mid-upload baud-rate switch crashed the native USB-CDC endpoint. Confirm upload_speed = 115200 in platformio.ini — do not raise it.
Upload fails with "Unable to verify flash chip connection"The flasher stub hand-off re-enumerated the USB-CDC endpoint mid-upload. Confirm upload_flags = --no-stub is present.
pio device monitor resets or drops the board on openDTR/RTS toggles are being misread as "enter download mode". Confirm monitor_dtr = 0 / monitor_rts = 0.
Connects, shows the device name, but the layout never loads / disconnects shortly afterClassic rc=6/BLE_HS_ENOMEM symptom — some code path is flooding notify() faster than the connection interval can drain it. See Post-mortem above; check any new periodic sendValue() call you may have added for missing throttling.
Joystick "up" turns the robot instead of driving straight, or forward/back feels reversedAngle convention or the y-axis mirror was undone by an edit. Re-check the joystick/D-Pad angle convention section — 0°=right/90°=up is standard math convention, not the "90°=down" some older reference comments claim.
Horn button does nothing on the phone speakerConfirm the layout JSON's sound_alert widget is actually present in what the app rendered (not clipped off-canvas) — bit-rxy versions before the DOM-dependency fix silently dropped Sound/Notification updates for widgets with no visible on-canvas element.
Board resets into ROM download mode unexpectedlyGPIO 9 is also the C3's BOOT strapping pin on some board variants — avoid wiring anything that could pull it low during power-on/reset.
Holding the button does nothing at allThe hold is checked every loop() iteration, not only right after boot — make sure you're holding it while the robot is already running (not through a reset), for the full 3 (or 8) seconds continuously.
"Open browser and connect" opens the wrong page after joining the setup APOS captive-portal detection can misfire. Navigate directly to http://192.168.4.1 instead of relying on the automatic prompt.
OTA upload can't reach the robot / times outThe robot only listens for OTA while its OLED shows OTA ready — it reboots back to normal BLE mode after every successful update or on a WiFi/portal timeout. Re-trigger the button hold and confirm the IP shown on the OLED before retrying ota_flash.sh.
Live site (flash.html, etc.) 404s even though the Pages workflow reports successThe repo's GitHub Pages source is set to legacy (deploy from the main branch root) instead of workflow (GitHub Actions) — pages.yml uses actions/deploy-pages, which only takes effect if Pages is configured to receive it. Check with gh api repos/abourdim/esp32c3_super_mini_robot-bit-rxy/pages --jq '.build_type'; fix with gh api -X PUT repos/abourdim/esp32c3_super_mini_robot-bit-rxy/pages -f build_type=workflow, then re-run the workflow.
