Cet article couvre ESP32-RXY, un firmware ESP32 qui parle exactement le même protocole Bluetooth Low Energy qu'un BBC micro:bit exécutant le modèle MakeCode rxy — de sorte que l'appli web rxy non modifiée peut se connecter à un simple ESP32 et piloter les widgets exactement comme elle le ferait avec un véritable micro:bit.

Aperçu

ESP32-RXY vous permet de piloter l'appli web de télécommande rxy avec une simple carte ESP32 au lieu d'un BBC micro:bit. L'appli rxy n'a jamais été modifiée pour que cela fonctionne : le firmware ESP32 se présente comme un micro:bit et implémente exactement le même protocole BLE UART, si bien que du point de vue du navigateur il est indiscernable du matériel réel. C'est pratique quand vous voulez un récepteur de télécommande permanent, alimenté par câble, plutôt qu'un micro:bit sur batterie, ou simplement quand vous n'avez pas de micro:bit sous la main.

La carte cible est l'ESP32-C3 Super Mini, une carte ESP32-C3 très bon marché (quelques dollars) avec un port USB-C natif et une LED & un bouton intégrés — mais n'importe quelle puce ESP32 avec Bluetooth Low Energy fonctionne avec des ajustements mineurs de broches.

Projet compagnon : ce firmware est le pendant côté ESP32 de l'appli web Micro:bit Remote Builder (bit-rxy). Lisez cet article d'abord si vous n'avez pas encore conçu de mise en page de télécommande — la section « Personnaliser la mise en page » ci-dessous suppose que vous avez déjà une chaîne CFG exportée depuis celle-ci.

Démarrage rapide

PlatformIO (recommandé pour l'ESP32-C3 Super Mini) :

cd platformio
pio run -t upload
pio device monitor

Arduino IDE : installez le package de carte ESP32 by Espressif Systems et la bibliothèque NimBLE-Arduino (2.x), ouvrez arduino/microbit_esp32_remote/microbit_esp32_remote.ino, sélectionnez la carte ESP32C3 Dev Module, activez Outils > USB CDC On Boot, et téléversez.

Ouvrez ensuite abourdim.github.io/rxy dans Chrome ou Edge, passez à l'onglet Jouer, appuyez sur 📡 Connexion, et choisissez BBC micro:bit dans la liste.

Quelle chaîne d'outils utiliser ? Sur l'ESP32-C3 Super Mini, préférez PlatformIO. Son platformio.ini fixe upload_speed = 115200 et définit --no-stub, tous deux nécessaires pour contourner les problèmes de réénumération USB-CDC dans esptool. Arduino IDE / arduino-cli n'a pas de moyen propre de faire passer --no-stub, donc les téléversements peuvent échouer avec « No serial data received » ou « Unable to verify flash chip connection ». Voir Dépannage pour l'explication complète.

Étape par étape : cloner, flasher & tester

Ce guide vous emmène d'un dépôt tout juste cloné à un firmware auquel un navigateur peut réellement se connecter et qu'il peut piloter.

1. Cloner le dépôt

git clone https://github.com/abourdim/esp32-rxy.git
cd esp32-rxy

Un ESP32-C3 Super Mini (ou toute carte ESP32 avec BLE) et un câble USB-C.

2. Installer la bibliothèque BLE

Les deux chaînes d'outils nécessitent NimBLE-Arduino 2.x. Dans Arduino IDE : Gestionnaire de bibliothèques → recherchez « NimBLE-Arduino » → installez. Dans PlatformIO elle est tirée automatiquement — platformio.ini fixe h2zero/NimBLE-Arduino @ ^2.2.0 dans lib_deps.

3. Compiler et flasher

Option A — PlatformIO (recommandé) :

cd platformio
pio run                # compiler
pio run -t upload      # téléverser (~60-90s avec --no-stub, c'est normal)
pio device monitor -b 115200

Ou utilisez le menu interactif plutôt que de mémoriser les options :

./launch.sh

qui propose des options numérotées pour vérifier la chaîne d'outils, installer PlatformIO, compiler, flasher, surveiller, ou « tout faire » en une fois, pour PlatformIO ou arduino-cli.

Option B — Arduino IDE : ouvrez arduino/microbit_esp32_remote/microbit_esp32_remote.ino, Outils > Carte → « ESP32C3 Dev Module », Outils > USB CDC On Boot → Enabled, sélectionnez le port, cliquez sur Téléverser.

4. Observer le démarrage

Ouvrez le moniteur série à 115200 bauds. Un démarrage sain affiche un bloc de diagnostic complet — modèle de puce, nombre de cœurs, version SDK, tas libre, taille de la flash — suivi des étapes de configuration BLE, se terminant par :

[BLE] advertising as: 'BBC micro:bit'
[BOOT] setup() OK   — free_heap=... bytes
[BLE] Open https://abourdim.github.io/rxy/ and click Connect.

5. Se connecter depuis l'appli web rxy

Sur un téléphone ou un ordinateur exécutant Chrome, Edge, Opera, ou Samsung Internet, ouvrez abourdim.github.io/rxy, passez à l'onglet Jouer, et appuyez sur 📡 Connexion. Choisissez l'appareil nommé BBC micro:bit dans le sélecteur de jumelage du navigateur (le firmware s'annonce sous ce nom exact pour que le filtre de l'appli l'accepte).

Vous devriez voir apparaître un seul bouton « Test » — la mise en page minimale par défaut intégrée au firmware. Appuyer dessus bascule la LED bleue intégrée sur la C3 Super Mini (GPIO 8, active à l'état bas).

Si l'overlay de connexion affiche « Requesting layout (GETCFG)… » et ne se ferme jamais, le firmware est joignable mais la réponse CFGEND n'est jamais arrivée — vérifiez la ligne [BLE] Sent CFG dans le moniteur série. Si elle est absente, l'appareil s'est probablement déconnecté en cours de transfert.

6. Essayer le bouton de débogage

Appuyez sur le bouton intégré BOOT (GPIO 9) après que la carte a fini de démarrer — il envoie un instantané complet de l'état au moniteur série : informations sur la puce, temps de fonctionnement, tas libre, états des broches GPIO, UUID BLE, et la configuration de mise en page actuelle dans exactement le même formatage CFGBEGIN/CFG/CFGEND envoyé via BLE. Utile pour confirmer quelle mise en page tourne réellement sans avoir besoin d'un téléphone à proximité.

Attention au GPIO 9 : c'est aussi la broche de strapping BOOT de l'ESP32-C3. Le maintenir enfoncé pendant que la carte s'allume ou se réinitialise fait démarrer la puce en mode téléchargement ROM au lieu d'exécuter le firmware. Il est sûr de l'appuyer après la fin du démarrage. Si vous voulez un bouton de débogage dédié sans ce piège, câblez-en un sur GPIO 0 et GND à la place et changez BUTTON_PIN dans le code source.
Une configuration réussie ressemble à ceci : le moniteur série montre un démarrage propre sans boucle de réinitialisation, l'overlay de connexion de l'appli se ferme en une seconde ou deux en affichant vos widgets, et le bouton Test (ou votre propre mise en page) répond instantanément.

Comprendre le code (pour développeurs débutants)

Cette section s'adresse à quiconque a flashé le firmware et s'est connecté avec succès, et veut maintenant ouvrir le code source et câbler ses propres widgets. Elle ne suppose aucune expérience préalable en embarqué/C++. Si vous voulez seulement utiliser la mise en page à un bouton par défaut, vous pouvez sauter entièrement cette section.

Vous n'avez pas besoin de comprendre quoi que ce soit ici pour construire, flasher, et vous connecter. Tout dans cette section est là pour quand vous serez prêt à faire faire quelque chose au firmware avec vos propres widgets.

Le seul fichier qui compte

Tout le firmware tient dans un seul fichier, main.cpp (les utilisateurs d'Arduino IDE voient le contenu identique sous microbit_esp32_remote.ino — les deux sont maintenus synchronisés octet pour octet). Pas d'en-têtes, pas de bibliothèques au-delà de NimBLE et des appels système ESP-IDF utilisés pour le diagnostic.

Ce qui se passe une fois, à la mise sous tension : setup()

  power on
     │
     ▼
  1 Serial + boot diagnostics  ──▶  2 GPIO init (LED off, button pulled up)
                                              │
                                              ▼
  4 GATT service + characteristics  ◀──  3 NimBLEDevice::init + security (open, no pairing)
     │
     ▼
  5 start advertising as "BBC micro:bit"

1. Diagnostics de démarrage — avant qu'aucune opération BLE ne se produise, setup() affiche le modèle de puce, le nombre de cœurs, la révision, la version du SDK, la version du cœur Arduino, la fréquence CPU, le tas libre, et la taille de la flash sur le moniteur série. C'est ce que vous vérifiez en premier si une carte se comporte mal.

2. Initialisation GPIO — la LED intégrée (GPIO 8, active à l'état bas sur la C3 Super Mini — écrire LOW l'allume) est mise à off, et le bouton de débogage (GPIO 9) est configuré en INPUT_PULLUP pour lire LOW quand il est pressé.

3. Initialisation NimBLE et politique de sécurité — c'est la partie qui mérite une lecture attentive :

NimBLEDevice::init(BLE_DEVICE_NAME);
NimBLEDevice::setPower(ESP_PWR_LVL_P9);
NimBLEDevice::setMTU(247);
NimBLEDevice::setSecurityAuth(false, false, false);   // no bonding / MITM / LESC
NimBLEDevice::setSecurityIOCap(BLE_HS_IO_NO_INPUT_OUTPUT);
NimBLEDevice::deleteAllBonds();

setMTU(247) demande une taille de paquet Bluetooth plus grande que les 23 octets par défaut, afin que les lignes de 23 octets "CFG <18 caractères>\n" tiennent dans une seule notification au lieu de se fragmenter — les centraux négocient toujours à la baisse s'ils ne le supportent pas (Chrome sur macOS atterrit généralement autour de 185 octets, les téléphones autour de 247). Les appels de sécurité désactivent explicitement le jumelage/liaison, correspondant à ce que fait un vrai micro:bit dans le mode « aucun jumelage requis » de MakeCode : n'importe qui à portée Bluetooth peut se connecter et piloter les widgets. Correct pour un gadget de bureau ou une télécommande de classe ; pas quelque chose que vous voudriez pour quoi que ce soit de sensible.

4. Service GATT et caractéristiques — le firmware crée un service BLE avec deux caractéristiques :

NimBLEService* svc = server->createService(UART_SERVICE_UUID);
gTxChar = svc->createCharacteristic(UART_TX_CHAR_UUID, NIMBLE_PROPERTY::NOTIFY);
NimBLECharacteristic* rxChar = svc->createCharacteristic(
            UART_RX_CHAR_UUID, NIMBLE_PROPERTY::WRITE | NIMBLE_PROPERTY::WRITE_NR);
rxChar->setCallbacks(new RxCallbacks());
Piège de nommage : la caractéristique ...0002 est celle sur laquelle le firmware notifie (appareil → appli) et ...0003 est celle à laquelle l'appli écrit (appli → appareil). C'est l'opposé de la convention Nordic UART Service utilisée par les bibliothèques Adafruit/Bluefruit, car nous imitons un micro:bit, et MakeCode attribue les rôles dans l'autre sens. Si vous comparez un jour ce code à un exemple NUS générique, souvenez-vous que les rôles sont inversés.

5. Publicité (advertising) — la dernière étape et la plus délicate. Un paquet d'annonce BLE a un budget strict de 31 octets. Le nom d'appareil de ce firmware est court ("BBC micro:bit", 13 caractères) spécifiquement pour qu'il tienne dans le paquet d'annonce primaire aux côtés des drapeaux, sans avoir besoin du tout d'un paquet de réponse de balayage :

adv->setName(BLE_DEVICE_NAME);
adv->enableScanResponse(false);          // name fits in primary packet
adv->setMinInterval(0x140);              // 320 * 0.625ms = 200ms
adv->setMaxInterval(0x140);

Cela compte parce que certains centraux BLE (notamment Chrome sur macOS) gèrent les noms transportés dans un paquet de réponse de balayage de manière peu fiable — l'appareil peut devenir invisible dans le sélecteur de jumelage du navigateur même si les téléphones le voient bien. Supprimer l'UUID du service de l'annonce (il reste découvrable via GATT après la connexion) libère assez du budget de 31 octets pour que le nom tienne dans le paquet primaire, que tout central BLE scanne de manière fiable. L'intervalle d'annonce de 200 ms correspond au propre réglage pxt.json de MakeCode, pour la cohérence avec un vrai micro:bit.

Comment une connexion devient une mise en page à l'écran : le flux GETCFG

Une fois connectée, l'appli rxy écrit GETCFG sur la caractéristique RX. Cette seule ligne entrante déclenche tout le transfert de mise en page :

  App writes "GETCFG\n" to RX char
       │
       ▼
  RxCallbacks::onWrite() buffers bytes until '\n', then calls handleLine()
       │
       ▼
  handleLine(): line == "GETCFG" → sendCfg()
       │
       ▼
  sendCfg(): sendLine("CFGBEGIN")
             for each 18-char chunk of LAYOUT_CFG_BASE64:
                 sendLine("CFG " + chunk);  delay(15ms)
             sendLine("CFGEND")
       │
       ▼  each sendLine() → gTxChar->notify(...)  over the TX characteristic
  App receives CFGBEGIN, several CFG lines, CFGEND
       │
       ▼
  App concatenates the CFG chunks, base64-decodes, JSON.parses the layout,
  and renders the widgets on screen

Deux détails d'implémentation ici sont faciles à mal faire, et les commentaires du code source mettent explicitement en garde contre les deux :

  • La taille de bloc de 18 caractères n'est pas arbitraire. Elle correspond au découpage propre du modèle MakeCode officiel de rxy, de sorte que la même chaîne base64 CFG fait l'aller-retour de manière identique qu'elle provienne d'un vrai micro:bit ou de ce firmware.
  • sendLine() doit passer ses propres octets directement à notify(), plutôt que d'appeler setValue() puis notify() comme deux étapes séparées. La forme en deux étapes crée une course sur le tampon interne partagé de la caractéristique lorsqu'elle est appelée dos à dos dans la boucle de découpage : la tâche hôte asynchrone de NimBLE peut lire le tampon après qu'un appel setValue() plus récent l'a déjà écrasé, effondrant silencieusement plusieurs notifications en file d'attente en une seule, la dernière. Le symptôme observé côté rxy était exactement cela : seul CFGEND arrivait jamais, chaque bloc CFG entre les deux disparaissait, et JSON.parse('') échouait. La correction, gTxChar->notify((const uint8_t*)out.c_str(), out.length()), capture les octets de manière atomique à chaque appel.

Lire les lignes entrantes : le rappel RX et handleLine()

Les écritures BLE arrivent sous forme de blocs d'octets bruts, pas de lignes propres, donc le firmware les met lui-même en tampon :

void onWrite(NimBLECharacteristic* chr, NimBLEConnInfo&) override {
  std::string v = chr->getValue();
  for (size_t i = 0; i < v.size(); ++i) {
    const char c = v[i];
    if (c == '\r') continue;
    if (c == '\n') {
      if (gRxBuffer.length() > 0) { handleLine(gRxBuffer); gRxBuffer = ""; }
    } else {
      gRxBuffer += c;
      if (gRxBuffer.length() > 256) gRxBuffer = "";  // overflow guard
    }
  }
}

Chaque octet est ajouté à gRxBuffer jusqu'à ce qu'un \n complète une ligne (un \r isolé est silencieusement abandonné, donc les fins de ligne Unix et Windows fonctionnent toutes les deux) ; la ligne complétée est transmise à handleLine(), qui reconnaît exactement deux formes :

if (line == "GETCFG") { sendCfg(); return; }
if (line.startsWith("SET ")) {
  int sp = line.indexOf(' ', 4);
  String id  = line.substring(4, sp);
  String val = line.substring(sp + 1);
  handleWidget(id, val);
}

Tout le reste est silencieusement ignoré — il n'y a pas de réponse d'erreur pour les lignes malformées, correspondant au comportement du vrai firmware micro:bit.

Câbler vos propres widgets : handleWidget()

C'est la seule fonction que vous modifiez pour votre propre projet. Elle reçoit un id de widget (exactement l'ID que vous lui avez donné dans l'onglet Build de rxy, par ex. btn_fire, slider_speed) et une chaîne val dont le format dépend du type de widget (voir le tableau de référence du protocole ci-dessous). La valeur par défaut fournie ne gère que le bouton de démo :

static void handleWidget(const String& id, const String& val) {
  if (id == "btn_test") {
    digitalWrite(LED_PIN, val == "1" ? LED_ON : LED_OFF);
    return;
  }
  // if (id == "slider_speed") {
  //   int s = val.toInt();          // 0..100 by default
  //   analogWrite(MOTOR_PIN, s * 255 / 100);
  //   return;
  // }
  ...
}

Le fichier source fournit un exemple commenté par type de widget (bouton, curseur, bascule, joystick, D-pad, pavé XY, minuteur) comme modèle à décommenter et adapter. Pour renvoyer des données dans l'autre sens — mettre à jour une LED, une étiquette, une jauge, un graphique, ou un indicateur de batterie à l'écran — appelez le petit assistant sendValue(id, val) depuis n'importe où, qui émet simplement "UPD <id> <val>" :

static inline void sendValue(const String& id, const String& val) {
  sendLine("UPD " + id + " " + val);
}
L'appli web rxy limite le débit des messages entrants à environ un toutes les 200 ms. Envoyer des mises à jour sendValue() plus vite que cela ne corrompra rien, mais les messages excédentaires sont simplement perdus — une cadence de 200 à 500 ms dans votre propre code de scrutation loop() est confortable et correspond à l'exemple de mise à jour périodique commenté déjà présent dans le code source.

Personnaliser la mise en page

  1. Ouvrez l'appli web rxy, passez à l'onglet Build, et concevez votre télécommande à partir de sa palette de widgets.
  2. Cliquez sur 📄 Code. Dans le MakeCode généré, copiez la longue chaîne base64 de const CFG = "…".
  3. Collez-la dans LAYOUT_CFG_BASE64 près du haut de main.cpp, en remplaçant la démo par défaut à un bouton.
  4. Remplissez votre propre logique dans handleWidget(), en faisant correspondre les ID de widget que vous avez choisis dans l'onglet Build.
  5. Re-téléversez.

Les ID de widget que vous avez utilisés dans l'onglet Build (btn_fire, slider_speed, …) sont exactement les ID qui arrivent dans les messages SET, donc vous les traitez par nom dans handleWidget() — aucune étape de mappage d'ID séparée n'est nécessaire.

Dépannage

SymptômeCause / solution
A fatal error occurred: No serial data received. (juste après « Changing baud rate to 460800 ») Le point de terminaison USB-CDC natif de l'ESP32-C3 Super Mini plante lors du changement de débit en cours de téléversement. Corrigé en fixant upload_speed = 115200 dans platformio.ini (déjà défini dans ce dépôt).
Unable to verify flash chip connection (No serial data received.) (juste après « Stub running... ») Quand le stub du flasheur prend le relais du bootloader ROM, le point de terminaison USB-CDC se réénumère et la première commande post-stub tombe dans une fenêtre morte. Corrigé par upload_flags = --no-stub (déjà défini), qui garde le bootloader ROM aux commandes pendant tout le téléversement — plus lent (~60–90s) mais fiable.
Le téléversement depuis arduino-cli échoue avec l'une des erreurs ci-dessus Il n'y a pas de moyen propre de faire passer --no-stub à travers un FQBN Arduino. Maintenez le bouton BOOT en appuyant sur RESET pour forcer le mode téléchargement ROM, puis téléversez immédiatement — ou passez à PlatformIO.
L'appareil n'apparaît pas dans le sélecteur de jumelage du navigateur Vérifiez que vous êtes sur Chrome, Edge, Opera, ou Samsung Internet — Safari et Firefox n'ont aucun support Web Bluetooth sur aucune plateforme, et aucun navigateur sur iOS/iPadOS ne le supporte (restriction Apple).
L'overlay de connexion reste bloqué sur « Requesting layout (GETCFG)… » Vérifiez le moniteur série pour [BLE] Sent CFG. S'il n'apparaît jamais, l'appareil s'est déconnecté avant l'arrivée de GETCFG. S'il apparaît mais que l'appli reste bloquée, reconnectez-vous une fois — un abonnement à une caractéristique périmé d'une session précédente peut occasionnellement manquer la rafale de notifications.
Appuyer sur le bouton de débogage (GPIO 9) empêche la carte de démarrer Le GPIO 9 est la broche de strapping BOOT de l'ESP32-C3. Le maintenir enfoncé pendant la mise sous tension ou la réinitialisation force le mode téléchargement ROM. N'appuyez dessus qu'après la fin du démarrage, ou recâblez le bouton de débogage sur GPIO 0 dans le code source.
Un second téléphone/navigateur ne peut pas se connecter Les périphériques BLE ne maintiennent qu'une seule connexion centrale à la fois. Déconnectez le premier client avant de vous connecter depuis un autre appareil.
Aucun jumelage BLE : par conception, correspondant au comportement d'un vrai micro:bit dans le mode par défaut de MakeCode, ce firmware accepte les connexions sans jumelage ni liaison. N'importe qui à portée Bluetooth peut se connecter et envoyer des commandes SET. Approprié pour un gadget de bureau ou une télécommande de classe ; pas pour quoi que ce soit où cela compte.
