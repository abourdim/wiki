This article covers the Robot MV, a port of bit-rxy (“b3”) onto a different carrier board. The two robots share a microcontroller and nothing else — every pin moved. What it adds that b3 does not have is a panning head for the distance sensor, and with it a radar that draws the room instead of flashing a number.

For the app that drives it, see rxy-web. For the robot it came from, see bit-rxy.

Overview

The robot owns its own interface. The app knows no robot in advance: it connects, asks for the configuration, and draws whatever comes back. So the Robot MV sends its own panel — D-pad, joystick, gauges, radar — and the app never needs rebuilding for it.

The firmware is a faithful port of b3: every module b3 has is still there (buzzer, NeoPixels, battery sense, OLED, LEDs). What is not fitted on this board is switched off at a single #define and compiles out, rather than failing quietly at runtime. Attaching a screen later means setting that #define back to 1.

The big trap in this port was not electrical but software: three servos instead of two. See Understanding the code — it is the kind of failure that looks like a protocol bug and is not one.

Quick start

  1. Power the robot and check the green LED is blinking (not connected yet).
  2. Open rxy_web in Chrome or Edge, on a phone or a PC.
  3. Press Connect and pick diy_app_mv from the list.
  4. The panel appears on its own. Choose Expert in the Level selector to see everything.
  5. Press Sweep: the head starts panning and the radar begins drawing the room.

Step by step: clone, flash & test

This walkthrough goes from a bare repository to a verified robot: it drives the right way, it measures, and its radar follows the head.

1. Clone the repository

git clone https://github.com/abourdim/esp32c3_super_mini_robot-move.git
cd esp32c3_super_mini_robot-move/01_software/01_app

2. Build

The project uses PlatformIO. Nothing to configure — the platform and libraries are pinned in platformio.ini.

pio run -e esp32-c3-devkitm-1

A successful build reports around 91% of flash. That is expected: b3's full module set nearly fills the default partition.

3. Flash over USB

pio run -e esp32-c3-devkitm-1 -t upload

The ESP32-C3 SuperMini flashes over its native USB, with no serial adapter. If the upload fails, hold BOOT while plugging the board in.

Native USB-CDC means the serial monitor attaches after boot, so most of the time you will see nothing at startup. That is normal, not a fault.

4. Check the serial monitor

pio device monitor

What matters at startup:

[BLE] init - device_name: diy_app_mv
[BLE] advertising: YES
[OLED] absent - screen disabled on I2C 8/9

And above all, what must not appear: Halting.... See Troubleshooting.

5. Test the drive direction

Connect, switch to Expert, and press the D-pad's up arrow. The robot should move forward. If it reverses, that is not a left/right swap but a polarity inversion: flip CONFIG_SERVO_INVERT_DRIVE in 00_config.h and reflash.

6. Test the sensor

Move your hand in front of the HC-SR04. The Distance gauge and the graph should react immediately.

7. Test the head and the radar

Move the Head slider: the head turns and the radar beam follows. Then switch on Sweep: the head pans on its own and the radar fills with detections that fade over five seconds.

A healthy baseline looks like this: the robot moves forward when you ask for forward, the distance changes when you bring a hand close, and the radar beam moves together with the head — all three subsystems confirmed independently.

The protocol, in three messages

Everything runs over a UART-style BLE service. Three exchanges are enough to understand it:

MessageDirectionPurpose
GETCFGVERapp → robot“what version is your layout?” The robot answers CFGVER <token>. If the phone already has that layout cached, the whole transfer is skipped.
GETCFGapp → robotsend me your layout. The robot answers with a series of base64 chunks.
SET / UPDboth waysSET = the user touched a widget. UPD = the robot publishes a value (distance, voltage, head angle).

The files, in the order they matter

FileWhat it does
00_config.hevery pin and every feature switch. The only file you need to read to understand the board.
01_src.inosetup() and loop(). Deliberately short and readable.
03_bit-rxy.cppthe BLE protocol, the encoded layouts, and widget routing. The big one.
04_tasks.cppthe drive mix: D-pad and joystick → two wheel speeds.
09_servos.cppthe three servos, the head sweep and its centring offset.
12_ultrasonic.cppone HC-SR04 reading, capped at 15 ms.

The PWM timer trap

b3 allocates one LEDC timer and attaches two servos: an exact fit. The head makes three — and when ESP32Servo runs out of timers it does not warn. It prints All PWM timers allocated! and then halts inside attach(). setup() never returns.

And that is invisible from outside. NimBLE has already started on its own task, so the robot keeps advertising and the app connects. It simply never answers anything, because remotexy_handler() lives in loop() and loop() has never run once. It looks like a protocol bug; it is not one.

ESP32PWM::allocateTimer(0);
ESP32PWM::allocateTimer(1);
ESP32PWM::allocateTimer(2);
ESP32PWM::allocateTimer(3);

Why the calibrations survive a power cycle

The wheel trims and the head offset are written to NVS (the ESP32's persistent store), because they describe how the robot was assembled — not how it is being driven this minute. The write is deferred two seconds past the last slider movement, so dragging across the whole range costs one flash write rather than sixty.

The head angle, by contrast, is not kept: it is a live control, and restoring yesterday's bearing at boot would point the sensor somewhere nobody asked for.

The board and its pin map

The pin map was read back from the PCB netlist, not from the schematic — the schematic names every net gpio_NN and says nothing about what it drives.

GPIOConnectorUse
5J5, 3-pin, via TXB0104left wheel servo
10J12, 3-pin, via TXB0104right wheel servo
6 / 7J10, 4-pin, via TXB0104HC-SR04 trig / echo
1J6, 3-pin, raw 3.3 Vhead servo
0J7green LED
21J8red LED
20J9NeoPixel strip (disabled)
3SW1button, long press = OTA
2, 8, 9nowheremodule pads only — which is why there is no screen
Leave J1 to J4 unpopulated. The 3-pin headers J6 to J9 share their nets with the gates of the transistors driving screw terminals J1 to J4. Anything plugged into a 3-pin header therefore switches its paired terminal as well. The compensation: the board's yellow LEDs (D6 to D9) become free activity indicators.
The servo rail needs bulk capacitance. Three servos share the ESP32's supply and the v1 board carries only 100 nF on it. An SG90 pulls about 700 mA stalled. Add 470 to 1000 µF at the connectors, and feed servo power from the input terminal rather than through the module's 5 V pin — otherwise the rail sags while driving and the C3 reboots.

Head, radar and sweep

The app's radar widget carries no value of its own: it reads the distance gauge and the head slider, by id. That is what the head exists for.

The sweep is paced by the measurement

The head steps one notch per telemetry cycle, not on a timer of its own, and the step happens after that cycle's distance and angle have been sent. That ordering is the whole point: the radar plots (angle, distance) pairs, and stepping independently would paint readings at bearings the sensor was not pointing at when they were taken. Each step then gets a full cycle, 500 ms, to settle before the next measurement.

Reversal happens at each limit, not past it: bouncing off the clamp would park the head on its end stop for one extra cycle every sweep — a visible stutter on the scope, and a stalled servo while it lasts.

The centring offset

A head mount is glued or screwed on by hand, so commanding 90° almost never points dead ahead. The Head trim slider (and the H−1 / H+1 buttons) takes up that difference.

The important part: the offset is applied where the servo is written, never to the bearing that gets published. The radar has to plot where the sensor is really aimed, which is the corrected direction. Publishing the raw pulse instead would shift every detection by the trim — exactly the opposite of what centring is for.

Display styles

rxy_web's radar offers five instruments, chosen from the chips under the scope — no reflashing:

StyleWhat you see
Sweepthe classic polar scope, with a fading trail
Batecholocation: a bat, expanding chirps, the return running up its axis
Sonara submarine set: nested arcs and a sweeping arm
LiDARa laser scanner: a point cloud, not a single dot
Heata horizontal proximity bar, with no bearing at all

Only Sweep uses the angle. The other four need distance alone, so they work on a robot whose sensor does not move. In Sweep mode a second row picks the marker shape: dots, rays, sectors, stars or emoji.

Troubleshooting

The app connects then sits on “Checking layout version”

The robot advertises and accepts the connection but answers nothing. Two possible causes, both seen for real:

  • setup() halted. Check the serial monitor for All PWM timers allocated! followed by Halting.... You are short of ESP32PWM::allocateTimer() calls.
  • The firmware does not answer GETCFGVER. b3 recognises that command without replying to it. Recent app versions no longer fall back to GETCFG on their own, so silence is now fatal.

The robot reverses when I ask for forward

Motor polarity, not a left/right swap — swapping the two pins would give a robot that spins on the spot instead. Flip CONFIG_SERVO_INVERT_DRIVE. That fixes the direction and the turning sense, since both follow from the same sign.

The robot slowly rotates while idle

A defect inherited from b3: trim is added to both wheels, but the right wheel's pulse range is inverted, so a positive trim pushes the two wheels in physically opposite directions. Set both CONFIG_SERVO_SPEED_STOP_*_OFFSET to zero.

The radar beam is stuck at 90°

The radar plots at whatever bearing the head widget last published. If the firmware does not republish the angle every cycle, the head moves and the scope does not. Fixed since MV-v4.

Random reboots while driving

Almost always power, not software. See the servo rail box in The board and its pin map.

Nothing appears on the serial monitor

Expected. Native USB-CDC re-enumerates on reset, so the monitor attaches after the startup message. The robot is running; it is simply quiet when idle.
