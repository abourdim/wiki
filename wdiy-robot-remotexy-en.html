This article covers esp32c3_super_mini_robot_remotexy, the original firmware for this ESP32-C3 differential-drive robot: driven over Bluetooth Low Energy through the commercial RemoteXY app, using RemoteXY's own visual GUI editor and Arduino library. It predates and is untouched by the bit-rxy conversion covered in the sibling article — the two are separate repos with separate control layers on the same hardware design.

Why this repo still exists, unmodified: when the robot was converted to speak bit-rxy's free, open BLE protocol, the RemoteXY version was deliberately left alone in its own repo rather than edited in place — see WDIY Robot (bit-rxy) for the reasoning and the actively-developed successor. This article documents the original as a historical/reference version, and for anyone who already owns a RemoteXY license and prefers it.

Overview

RemoteXY is a commercial remote-control platform: a drag-and-drop GUI editor (web-based) lets you design a control panel — joysticks, buttons, gauges — which compiles down to a binary configuration blob embedded directly in your firmware. The official RemoteXY Arduino library then handles the Bluetooth transport and protocol, and the RemoteXY mobile/desktop app renders whatever layout your firmware advertises.

This robot's control panel is a single joystick (steering), a horn button, and three read-only outputs (distance, speed, battery) plus a circular bar and sound events — the same feature set the bit-rxy conversion later reproduced from scratch on a different, free protocol.

Quick start

git clone https://github.com/abourdim/esp32c3_super_mini_robot_remotexy.git
cd esp32c3_super_mini_robot_remotexy/01_software/01_app
./launch.sh flash

Install the RemoteXY app (iOS App Store / Google Play / desktop), open it, and connect over Bluetooth to diy_app_b3. The app renders the joystick/button/gauges layout automatically — no pairing code needed beyond RemoteXY's own connect flow.

Native USB-CDC upload quirks are not worked around here. Unlike the bit-rxy fork, this repo's platformio.ini doesn't pin upload_speed/upload_flags for the ESP32-C3's native USB-CDC endpoint (tracked as the still-open BUG-005 in this repo's own bug tracker). If uploads fail with "No serial data received" or "Unable to verify flash chip connection", see Troubleshooting.

Understanding the code

The entire RemoteXY control layer lives in 03_remotexy.cpp/.h, structured very differently from a hand-written BLE protocol:

#define REMOTEXY_MODE__ESP32CORE_BLE
#include <BLEDevice.h>
#define REMOTEXY_BLUETOOTH_NAME CONFIG_REMOTEXY_BLUETOOTH_NAME
#include <RemoteXY.h>

uint8_t RemoteXY_CONF[] =   // 176 bytes
  { 255,3,0,15,0,169,0,19,0,0,0,0,179,2,130,200,108,200,1,1, ... };

struct {
  int8_t  joystick_01_x;   // -100..100
  int8_t  joystick_01_y;   // -100..100
  uint8_t button_01;       // 1 = pressed
  float   onlineGraph_01_distance;
  float   onlineGraph_02_speed;
  float   onlineGraph_03_battery;
  int8_t  circularBar_01;  // 0..100
  int16_t sound_01;        // 0 = none, else a sound-ID constant
  uint8_t connect_flag;
} RemoteXY;

Two things stand out compared to a hand-rolled protocol like bit-rxy's:

  • RemoteXY_CONF[] is opaque, generated bytes — the actual GUI layout (joystick position, button size, gauge ranges, labels) is encoded in this array by RemoteXY's online editor, not something you hand-edit in the source. Changing the layout means opening the project in the editor, redesigning it there, and re-exporting the generated code — there's no local equivalent of bit-rxy's readable-JSON-comment/layout_cfg.sh workflow.
  • RemoteXY is a plain global struct, not a message protocol you parse — the library's RemoteXY_Handler() (called every loop()) handles all BLE traffic internally and just keeps this struct's fields in sync with whatever the app is showing. Firmware code never sees raw bytes; it just reads/writes struct fields, e.g. remotexy_get_joystick_01_x() is a one-line wrapper returning RemoteXY.joystick_01_x.

Everything downstream of that — 04_tasks.cpp's joystick-to-servo arcade mixing, the sound-ID switch statement, the OLED/battery/ultrasonic code — is identical in spirit to what the bit-rxy fork kept (the fork's function names were deliberately preserved to match this file's API, so porting the transport didn't require touching this logic at all).

The RemoteXY licensing limitation (BUG-004)

RemoteXY's free tier caps a project at 5 GUI elements per interface. This robot's panel — joystick, button, 3 gauges/graphs, a circular bar — sits right at or over that ceiling depending on how elements are counted, which is exactly the friction that motivated the bit-rxy conversion: bit-rxy has no such cap, no paid tier, and is entirely open-source.

This is the underlying reason the sibling project exists at all — not a bug in the code, but a licensing constraint of the platform this repo depends on.

Hardware reference

Identical hardware/pinout to the bit-rxy version, since it's the same physical robot design — see WDIY Robot (bit-rxy) — Hardware reference for the full GPIO table. Both repos share CONFIG_SERVO_SPEED_STOP_LEFT/_RIGHT = 90° with small _OFFSET corrections, and the same BLE device name, diy_app_b3.

Troubleshooting

SymptomCause / fix
Upload fails with "No serial data received" or "Unable to verify flash chip connection"This repo's platformio.ini doesn't pin upload_speed/upload_flags for the ESP32-C3's native USB-CDC quirks (BUG-005, still open here). Either retry a few times, or borrow the fix from the bit-rxy fork's platformio.ini: upload_speed = 115200 + upload_flags = --no-stub.
RemoteXY app says the interface needs a PRO license / some elements are greyed outExpected — see the licensing limitation above. Either purchase a RemoteXY PRO license, trim the GUI layout in RemoteXY's editor to fit the free 5-element cap, or switch to the free bit-rxy fork instead.
Want to change the control layout (add a widget, move the joystick)Can't be done by editing 03_remotexy.cpp directly — the layout is generated by RemoteXY's online editor. Redesign it there and re-export the generated RemoteXY_CONF[]/struct code.
Board resets into ROM download mode unexpectedlyGPIO 9 is also the C3's BOOT strapping pin on some board variants — avoid wiring anything that could pull it low during power-on/reset.
