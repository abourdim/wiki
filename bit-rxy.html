Micro:bit Remote Builder (bit-rxy)

Cet article couvre rxy (Micro:bit Remote Builder), un outil sans code par glisser-déposer pour concevoir des télécommandes Bluetooth personnalisées pour le BBC micro:bit — unique dans cette famille d'applications car il génère lui-même son firmware MakeCode à la volée, et peut flasher ce firmware directement depuis le navigateur via Bluetooth.

Aperçu

bit-rxy permet de concevoir une télécommande Bluetooth personnalisée — boutons, curseurs, joysticks, jauges, tout ce dont on a besoin — en glissant des widgets sur un canevas, puis génère automatiquement le firmware MakeCode correspondant. Contrairement à Bit-Bot, Talking Robot et micro:bit Playground (qui utilisent tous un protocole de firmware fixe), ici le protocole lui-même est généré selon la conception : chaque widget placé devient un bloc de traitement dans le code exporté, et toute la disposition est intégrée au firmware sous forme de chaîne Base64, afin que le micro:bit puisse renvoyer sa propre configuration à n'importe quelle application qui la demande.

L'application va aussi plus loin que les autres de cette famille : au lieu de proposer uniquement « copier ce code dans MakeCode », elle peut compiler le code généré et le flasher directement sur la carte depuis le navigateur, soit via Bluetooth (grâce au service de flashage partiel intégré au micro:bit), soit via WebUSB.

Démarrage rapide

  1. Ouvre l'application en ligne dans Chrome ou Edge.
  2. Sur l'onglet ✏️ Construire, glisse des widgets sur le canevas (ou pars d'un modèle).
  3. Clique sur 📄 Code, copie le code MakeCode généré, colle-le dans makecode.microbit.org, et flashe via USB — ou utilise le bouton de flashage intégré pour le faire via Bluetooth/WebUSB.
  4. Passe à l'onglet ▶️ Jouer, appuie sur 📡 Connecter !, et commence à contrôler ton micro:bit.

Étape par étape : cloner, flasher & tester

Ce parcours part d'une copie vierge du dépôt jusqu'à une télécommande vérifiée et fonctionnelle : un widget envoyé avec succès dans chaque direction.

1. Cloner le dépôt

git clone https://github.com/abourdim/bit-rxy.git
cd rxy

2. Servir le site en local

Aucune étape de build, mais Web Bluetooth/WebUSB refusent un simple chemin file:/// :

npx serve .

Ouvre l'URL affichée http://localhost:... dans Chrome ou Edge (la copie en ligne sur GitHub Pages fonctionne pareil, sans rien installer).

3. Construire une télécommande minimale

Sur l'onglet ✏️ Construire, glisse un widget Bouton et un widget LED sur le canevas. C'est le plus petit test d'aller-retour possible : une entrée, une sortie.

4. Récupérer et flasher le code

Clique sur 📄 Code pour ouvrir le code MakeCode généré. Soit tu le copies dans makecode.microbit.org et tu flashes via USB normalement, soit tu essaies le bouton intégré Flasher, qui tente de compiler le code et de l'envoyer directement à une carte connectée via Bluetooth ou WebUSB (voir Comprendre le code pour le fonctionnement et le repli en cas d'échec de compilation).

5. Tester la direction entrante (app → micro:bit)

Passe à ▶️ Jouer, appuie sur 📡 Connecter !, choisis ta carte, puis appuie sur ton widget Bouton. Le micro:bit doit réagir immédiatement (le gestionnaire généré par défaut affiche une icône cœur).

6. Tester la direction sortante (micro:bit → app)

Dans l'éditeur MakeCode, ajoute une ligne pour renvoyer une valeur : sendValue("your_led_id", "1") dans un bloc d'appui sur bouton ou une boucle, reflashe, et vérifie que ton widget LED s'allume dans l'application quand il est déclenché.

Une base fonctionnelle ressemble à ceci : le micro:bit affiche un cœur quand tu appuies sur le widget Bouton, et le widget LED de l'application s'allume quand le firmware appelle sendValue() — les deux directions du protocole sont confirmées indépendamment.

Comprendre le code (pour débutants)

Pour qui a l'application en marche et veut ouvrir le code source pour commencer à modifier quelque chose. Suppose des bases en JavaScript mais rien de spécifique à ce code. À sauter si tu veux seulement utiliser l'application.

        │                                              │

        │                                              │
        │                      le firmware exécute     │
        │                      handleWidget(), peut    │
        │                      appeler sendValue():    │
        │  UPD led_status 1   ◄─────────────────      │
        │                                              │
        │  À la connexion : GETCFG ───────────►       │

La différence clé avec les trois autres applications de cette famille : le micro:bit n'est pas juste une télécommande fixe — il transporte sa propre configuration. Connecte n'importe quelle copie de cette application à une carte flashée et elle redessinera fidèlement la disposition intégrée au moment du flashage.

Le générateur de code : du canevas au firmware

generateDemoCode(cfg) prend la liste actuelle des widgets et, pour chacun, émet un bloc if (id == "...") correspondant dans un modèle de firmware — un widget Bouton reçoit un bloc « à l'appui, afficher un cœur » ; un Curseur reçoit un bloc « lire la valeur, tracer un graphique en barres » ; et ainsi de suite pour les 12 types de widgets. Chaque gestionnaire généré est volontairement simple et commenté // Add your code here! — il est conçu comme un point de départ à modifier dans MakeCode, pas comme un programme fini.

function generateDemoCode(cfg) {
  const b64 = btoa(unescape(encodeURIComponent(JSON.stringify(cfg))));  // Unicode-safe (handles emoji labels!)
  const buttons = cfg.widgets.filter(w => w.t === 'button');
  const sliders = cfg.widgets.filter(w => w.t === 'slider');
  // ...one filter per widget type...

  let buttonCode = buttons.map(w => `    if (id == "${w.id}" && val == "1") {
        basic.showIcon(IconNames.Heart)
        // Add your code here!
    }`).join('\n');
  // ...same pattern for every other widget type, then stitched into
  // the firmware template alongside the embedded CFG Base64 string...
}

Comment la disposition survit sur le micro:bit lui-même

Toute la disposition des widgets est convertie en JSON, encodée en Base64 (via une chaîne btoa(unescape(encodeURIComponent(...))) compatible Unicode pour que les libellés avec emoji survivent), et intégrée directement dans le firmware généré comme constante de type chaîne. Le firmware sait alors renvoyer cette chaîne via Bluetooth par blocs de 18 octets, sur demande :

const CFG = "${b64}"   // baked in at generation time

bluetooth.onUartDataReceived(serial.delimiters(Delimiters.NewLine), function() {
    let cmd = bluetooth.uartReadUntil(serial.delimiters(Delimiters.NewLine))
    if (cmd == "GETCFG") {
        bluetooth.uartWriteLine("CFGBEGIN")
        for (let i = 0; i < CFG.length; i += 18) {
            bluetooth.uartWriteLine("CFG " + CFG.substr(i, 18))
        }
        bluetooth.uartWriteLine("CFGEND")
    } else if (cmd.indexOf("SET ") == 0) {
        let parts = cmd.substr(4).split(" ")
        handleWidget(parts[0], parts.slice(1).join(" "))
    }
})

18 octets par bloc garde chaque ligne confortablement sous la limite MTU BLE d'environ 20 octets utilisée dans toute cette famille d'applications. Côté navigateur, le Base64 reconstitué est décodé pour retrouver exactement la disposition de widgets construite — c'est ainsi que l'onglet Jouer peut afficher correctement ta télécommande même dans une session de navigateur qui n'a jamais touché à l'onglet Construire.

Flashage en un clic : service de flashage partiel et WebUSB

Au-delà du chemin standard « copier le code dans MakeCode », flashToMicrobit() tente de compiler le code généré via un service de compilation MakeCode et d'envoyer le fichier .hex résultant directement à la carte via Bluetooth, en utilisant le service de flashage partiel du micro:bit — une vraie fonctionnalité DAL (UUID e97dd91d-...) qui permet à une carte déjà flashée par USB d'accepter des mises à jour de programme via BLE sans câble :

const PFS_SERVICE = 'e97dd91d-251d-470a-a062-fa1922dfa9a8';
const PFS_CHAR    = 'e97d3b10-251d-470a-a062-fa1922dfa9a8';
const PFS_CMD = { REGION_INFO: 0x00, FLASH_DATA: 0x01, END_OF_TX: 0x02, STATUS: 0xEE, RESET: 0xFF };

Si l'étape de compilation échoue pour une raison quelconque, l'application n'abandonne pas — elle ouvre MakeCode dans un nouvel onglet pour que l'utilisateur puisse compiler et flasher manuellement. Un chemin séparé flashViaUSB() offre le même confort « flasher sans quitter le navigateur » via une connexion USB directe (WebUSB) plutôt que Bluetooth, pour les cartes pas encore appairées.

Se reconnecter proprement : le nettoyage des écouteurs BLE

Cette sous-section documente un vrai bug de reconnexion et sa correction (commit 26730c4) — utile si vous modifiez connectBle() vous-même.

Chaque appel à connectBle() fait :

notifyChar.addEventListener('characteristicvaluechanged', onNotify);

Il est tentant de penser que c'est sans risque à répéter — ajouter deux fois le même écouteur pour le même événement sur le même objet ne fait normalement rien la seconde fois. Le problème : Web Bluetooth renvoie un nouvel objet caractéristique enveloppé à chaque appel de getCharacteristic(), même pour la même caractéristique physique. Ce n'est donc jamais le même objet, et l'ajout d'écouteur n'est jamais un doublon inoffensif.

Avant la correction, rien n'appelait le removeEventListener() correspondant lors d'une déconnexion ou d'une reconnexion. Résultat : chaque clic sur « Connecter » après un firmware reflashé (ou toute autre coupure de la liaison) laissait un nouvel écouteur onNotify accroché à un nouvel objet caractéristique, sans jamais retirer les précédents. Une seule notification BLE réelle finissait par déclencher onNotify() plusieurs fois — une fois par écouteur périmé encore attaché — dupliquant et corrompant silencieusement le flux CFG reçu.

C'est ce qui explique un symptôme déroutant observé pendant le débogage du firmware ESP32 compagnon : le nombre de blocs CFG reçus dépassait parfois le total réel (par ex. 91 reçus pour ~60 attendus) après plusieurs reconnexions dans le même onglet, sans qu'aucun rechargement de page n'ait eu lieu entre elles.

La correction, dans connectBle() et onDisconnect() :

// au début de connectBle(), avant toute nouvelle connexion :
if (state.ble.notifyChar) {
  state.ble.notifyChar.removeEventListener('characteristicvaluechanged', onNotify);
}
if (state.ble.device?.gatt?.connected) {
  state.ble.device.gatt.disconnect();
}

// dans onDisconnect(), avant de réinitialiser state.ble :
if (state.ble.notifyChar) {
  state.ble.notifyChar.removeEventListener('characteristicvaluechanged', onNotify);
}

La leçon générale : sur une API dont la documentation ne précise pas explicitement l'identité des objets renvoyés, ne jamais supposer qu'un objet « équivalent » obtenu deux fois est le même objet aux yeux d'addEventListener(). Nettoyez explicitement l'écouteur précédent avant d'en attacher un nouveau.

Nordic UART sur BLE, mêmes UUID de service/caractéristique que le reste de cette famille d'applications (6e400001/2/3-...) :

App → micro:bitGETCFGDemande la configuration de disposition intégrée.
micro:bit → AppCFGBEGIN / CFG <chunk> / CFGENDLa disposition, renvoyée par blocs Base64 de 18 octets.

Langues

Traduction complète en anglais, français et arabe sur l'en-tête, le sélecteur de modèles, la barre d'outils du constructeur, la palette de widgets, le panneau de propriétés, la vue Jouer/exécution, le tutoriel, l'écran de chargement, la fenêtre de code, et les notifications pour chaque action principale — via un utilitaire tr(path, vars) qui fait une recherche par clé à points dans l'objet I18N (ex. tr('toast.sizeSet', {w, h})) avec interpolation de {placeholder} pour les valeurs dynamiques. L'arabe bascule toute la page en dir="rtl" et utilise le drapeau algérien, comme le reste de cette famille d'applications.

Contrairement à la détection automatique de la langue du navigateur utilisée au début, l'application démarre désormais directement en français à la première visite et ne change que sur choix explicite, mémorisé dans sa propre clé kid_lang du localStorage — comme Bit-Bot, Talking Robot et micro:bit Playground.

Volontairement laissés en anglais : les libellés de chaque champ du formulaire de propriétés des widgets (Width, Height, Min, Max, etc. — une centaine de chaînes réparties sur les 12 types de widgets) et le panneau « Helper Tools » réservé aux utilisateurs avancés (Group, Layers, Ruler, Align, Distribute, Canvas Background, Screenshot, Share — tous cachés derrière un bouton réservé au développement, jamais visibles pour les utilisateurs normaux), la même limite de périmètre que pour le panneau Commandes exclu de Bit-Bot.

Dépannage

SymptômeCause / solution
Impossible de se connecter au micro:bitVérifie que le Bluetooth est activé, que la carte affiche un ❤️ (prête), et qu'un seul appareil est connecté à la fois — rafraîchis et réessaie si une session précédente ne s'est pas déconnectée proprement.
La disposition reçue semble corrompue ou incomplète après plusieurs reconnexions dans le même ongletCorrigé dans le commit 26730c4 — voir Se reconnecter proprement plus haut. Sur une version à jour, chaque reconnexion nettoie l'écouteur BLE précédent ; sur une ancienne version, recharge la page entière plutôt que de simplement recliquer sur Connecter.
La connexion échoue toujours sur iPhone/iPadiOS n'a aucun support de Web Bluetooth dans Safari ni dans aucun autre navigateur iOS (tous basés sur WebKit) — c'est une limitation de la plateforme, pas un bug. L'application le détecte et indique le navigateur gratuit « Bluefy » (à chercher sur l'App Store) plutôt que de simplement afficher « Échec de connexion ».
Les widgets ne font rienVérifie que le code généré a bien été flashé, et que les ID de widgets dans le firmware correspondent aux ID affichés dans le panneau Code — régénère et reflashe après tout changement de disposition.
Le flashage Bluetooth en un clic échoueLe service de flashage partiel nécessite une carte qui exécute déjà un runtime MakeCode compatible suite à un flashage USB préalable ; si l'étape de compilation échoue franchement, l'application ouvre MakeCode dans un nouvel onglet pour flasher manuellement.
Le micro:bit se déconnecte aléatoirementReste à portée Bluetooth (~10m), vérifie la batterie, et réduis la fréquence d'appel de sendValue() si tu satures la liaison.
La croix directionnelle n'affiche aucune flècheRégénère le code après tout changement dans l'onglet Construire et reflashe — un firmware obsolète ne connaîtra pas un widget ajouté après coup.
