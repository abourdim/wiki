Overview

VideoCar is an enhanced firmware and web control page for the keyestudio ESP32-CAM Video Smart Car. It builds on keyestudio's stock sketch, adding a virtual joystick, a connection-loss failsafe, snapshot/video capture, a redesigned control UI, and a PlatformIO build system alongside the original Arduino IDE sketch.

Hardware assembly: the official keyestudio KS5017 tutorial covers the kit list, assembly steps, pinout, and the original stock code this project builds on. Start there for physical assembly; this repo picks up once the car is built and the stock sketch runs.
Vision features need internet: the default AP mode (ap = 1) hosts an isolated keyes1 network with no internet. Pose, Hand tracking, Facial expression, Plates, AI Vision, and the jsQR fallback all download models from a CDN on first use, so they fail to start on the car's own AP. Driving, video streaming, snapshots, and recording all work fine there. To use the model-backed features, set ap = 0 with your router's SSID/password and reflash. The exception is QR / Barcode on Chrome/Edge/Android Chrome, which uses the browser's built-in BarcodeDetector and needs no network at all.

Quick start

Arduino IDE (known-good baseline): open Codes/4_VideoCar/4_VideoCar.ino, select your esp32 board package version under Tools > Board > Boards Manager, enable Tools > PSRAM: Enabled, select the AI-Thinker ESP32-CAM board, and flash as usual.

PlatformIO:

./launch.sh

Walks you through checking/installing PlatformIO, building, flashing, and opening a serial monitor.

Once flashed, connect to the keyes1 WiFi network (password 88888888) and open http://192.168.4.1 in a browser.

New to this, or want to drive the car from your own scripts? ports.html in the repo is a step-by-step guide to both servers — what port 80 and port 81 each do, every endpoint with its value ranges, and the 500ms failsafe that catches people out the first time they try to drive it with curl. The full walkthrough below is adapted from it.

Step-by-step: clone, flash & test

This walkthrough takes you from a bare checkout to a car driving on the desk and both web servers verified working. No prior knowledge of HTTP assumed; nothing here requires editing or recompiling the firmware.

Put the car on blocks before any of the driving steps. A book under each side, wheels clear of the desk. You are about to send it commands by hand, and it is easy to send "forward" and then go looking for the stop command while it drives off the table.

1. Clone the repository

git clone https://github.com/abourdim/video-car.git
cd video-car

A car with the KS5017 kit already assembled per the official keyestudio tutorial, and a USB cable to the ESP32-CAM's FTDI adapter.

2. Pick a build system and flash

Option A — Arduino IDE (known-good baseline): open Codes/4_VideoCar/4_VideoCar.ino, select your esp32 board package version under Tools > Board > Boards Manager, enable Tools > PSRAM: Enabled, set Tools > Partition Scheme to one with enough app space (e.g. "Huge APP (3MB No OTA/1MB SPIFFS)"), select the AI-Thinker ESP32-CAM board, and click Upload.

Option B — PlatformIO:

./launch.sh

Walks you through checking/installing PlatformIO, selecting the 4_videocar app, building, flashing, and opening a serial monitor (menu options 0 through 8).

Watch the serial monitor (115200 baud) while it boots. A healthy boot looks like:

VideoCar v1.5.0  |  built Jul 26 2026 12:47:05  |  33fd730
Starting web server on port: '80'
Starting stream server on port: '81'
Camera Ready! Use 'http://192.168.4.1' to connect

3. Get on the same network as the car

Default (access point mode). The car makes its own WiFi network. On your phone or laptop, join:

network:  keyes1
password: 88888888

The car is then always at 192.168.4.1. It has no internet connection — it is a network of exactly two devices, you and the car. On a phone, expect (and ignore) a warning that the network has no internet.

If you reflashed with station mode (ap = 0), the car joins your router instead and the router decides its address — read the boot message on the serial console for the actual IP and use that in place of 192.168.4.1 below.

4. Open the control page — port 80

http://192.168.4.1/

No port number needed; the browser fills in 80 silently. You should see the dark control page, live video within a second or two, and a build stamp in the footer.

Blank page or a spinner forever? Confirm you typed http:// and not https:// — the car speaks plain HTTP only, and some browsers try HTTPS first and give up quietly.

5. Watch the raw video — port 81

Open a new tab and go to:

http://192.168.4.1:81/stream

You get the video on its own, filling the window, with no page around it — the same MJPEG data the control page wraps in an <img> tag. If this tab shows video, the camera and both servers are fine and any problem is in the page. The tab spinner never stops — that's correct, the response never finishes. Close this tab before driving; every open stream consumes one of the camera's limited frame buffers.

6. Take a single photo

http://192.168.4.1/capture

One JPEG taken the moment you ask, then the connection closes normally — the opposite of the stream. From a terminal:

# save one frame as shot.jpg
curl http://192.168.4.1/capture -o shot.jpg

7. Ask the car what it is doing

http://192.168.4.1/status

Returns JSON with every current setting plus firmware version, build time, and git revision:

{"framesize":5,"quality":10,"vflip":1,"hmirror":1,
 "speed":8,"trim":0,"flash":0,
 "version":"1.5.0","build":"Jul 26 2026 12:47:05","gitrev":"33fd730"}

This is what the control page itself calls on load to restore your sliders, and every two seconds after as a connection check.

8. Change a setting by hand

Settings use one endpoint with two parameters: var (what to change) and val (the new value). Try the headlight, which is harmless and obvious:

# half brightness
http://192.168.4.1/control?var=flash&val=128

# off again
http://192.168.4.1/control?var=flash&val=0

From a terminal, note the quotes — & means something special to most shells, so the URL must be quoted:

curl "http://192.168.4.1/control?var=flash&val=128"

The white LED on the front should come on, then off. Settings are saved to the car's flash and survive a reboot.

9. Drive it — and meet the failsafe

Driving uses the same endpoint with var=car:

val=1  forward     val=4  turn right
val=2  backward    val=5  stop
val=3  turn left
curl "http://192.168.4.1/control?var=car&val=1"

The wheels turn for about half a second and stop — nothing is broken. The firmware stops the motors if 500ms pass with no new command, so a dropped WiFi connection or a closed laptop can't leave it driving forever. One command is a lease, not an instruction — to keep moving, keep renewing it, which is exactly what the control page does every 100ms. To drive forward for three seconds from a terminal:

# macOS / Linux
end=$((SECONDS+3))
while [ $SECONDS -lt $end ]; do
  curl -s "http://192.168.4.1/control?var=car&val=1" > /dev/null
  sleep 0.1
done
curl -s "http://192.168.4.1/control?var=car&val=5" > /dev/null   # stop

10. Steer smoothly instead of in four directions

/control?var=car only knows four directions and stop. For proportional control — any direction, any speed — use the joystick endpoint (both values -100 to 100; x is steering, y is throttle):

http://192.168.4.1/joystick?x=0&y=100      full speed ahead
http://192.168.4.1/joystick?x=100&y=0      spin right on the spot
http://192.168.4.1/joystick?x=-50&y=60     forward, curving left
http://192.168.4.1/joystick?x=0&y=0        stop

The same 500ms failsafe applies — repeat it roughly ten times a second for as long as you want to move.

11. Run the quick test script

Checks both servers and reports what it finds (wheels on blocks — it drives briefly):

#!/bin/bash
CAR=http://192.168.4.1

echo "--- port 80: status ---"
curl -s $CAR/status || echo "NO RESPONSE on port 80"
echo

echo "--- port 80: still photo ---"
curl -s $CAR/capture -o /tmp/shot.jpg && ls -l /tmp/shot.jpg

echo "--- port 81: stream (first 2 seconds) ---"
curl -s --max-time 2 $CAR:81/stream -o /tmp/stream.bin
echo "received $(wc -c < /tmp/stream.bin) bytes of video"

echo "--- drive forward 1s, then stop ---"
end=$((SECONDS+1))
while [ $SECONDS -lt $end ]; do
  curl -s "$CAR/control?var=car&val=1" > /dev/null; sleep 0.1
done
curl -s "$CAR/control?var=car&val=5" > /dev/null
echo "done"

A healthy car gives you a line of JSON, a shot.jpg of a few kilobytes, tens of kilobytes of video, and one second of wheel movement. If the JSON arrives but the video doesn't, the stream server failed to start — check the serial console at boot for both port: '80' and port: '81' lines.

Full endpoint reference — port 80

RequestReturnsNotes
GET /HTML The control page. Sent with Cache-Control: no-store, so you always get the page belonging to the firmware that is actually running.
GET /statusJSON All current settings plus firmware version, build time and git revision.
GET /captureJPEG One still frame at the current resolution and quality.
GET /control?var=…&val=…empty Settings and basic driving. See the values table below.
GET /joystick?x=…&y=…empty Proportional driving. Both −100 to 100; out-of-range values are clamped, not rejected.

Values for /control:

varvalEffect
car1–5 1 forward, 2 backward, 3 left, 4 right, 5 stop. Subject to the 500ms failsafe — repeat to keep moving.
speed0–8 Overall speed cap. Multiplied by 31 internally, so 8 means a PWM ceiling of 248 out of 255.
trim−32–32 Corrects a car that drifts when it should go straight. Negative favours one motor, positive the other.
flash0–255 Front LED brightness.
framesize0–6 Resolution. 0 = 96×96, 1 = QQVGA, 2 = QCIF, 3 = HQVGA, 4 = 240×240, 5 = QVGA 320×240 (default), 6 = CIF. Bigger is slower.
quality10–63 JPEG quality, runs backwards: lower numbers look better and produce bigger frames.
vflip0 or 1Flip the picture vertically.
hmirror0 or 1Mirror the picture horizontally.

Everything except car is saved to the car's flash memory and survives a power cycle. Only car and /joystick reset the failsafe timer — changing a setting does not count as "I am still here".

Full endpoint reference — port 81

RequestReturnsNotes
GET :81/stream multipart/x-mixed-replace Endless JPEG frames. The only endpoint on this port.

Frames are separated by a fixed boundary marker, each with its own Content-Type: image/jpeg and length, and the server sends Access-Control-Allow-Origin: * so a web page on port 80 is allowed to read the pixels — which is how the vision features work.

Things that will trip you up

  • Only one device can join the car's WiFi. The access point is configured for a single client. An ungraceful disconnect can hold the slot for a minute or two — if you can't reconnect, wait, or power-cycle the car.
  • One stream viewer at a time, in practice. Nothing stops you opening two, but they compete for camera buffers and both suffer.
  • There is no password on any of this. Anyone on the network can drive the car, and every command is a plain URL. Treat the car's network as untrusted and don't leave it running unattended.
  • & needs quoting in a shell. An unquoted & tells most shells to run the command in the background, so only the first parameter arrives. Always quote the whole URL.
  • Don't write :80 explicitly. Some of the page's JavaScript builds the stream URL from the current address, and an explicit :80 turns into a broken :80:81. Just omit it.
  • Higher resolution is not free. framesize=6 quadruples the data over the same WiFi. If the stream turns into a slideshow, go back to 5.
  • Settings persist, so surprises persist too. If the car boots with the light on or the picture upside down, that's a saved setting from last time, not a fault.

Understanding the code (for newbie developers)

This section is for anyone who has flashed and driven the car and now wants to open the source and change something. It assumes no prior embedded/C++ experience. If you only want to use the car, you can skip this entirely — nothing below is required reading.

You don't need to understand any of this to build, flash, and drive the car. Everything in this section is here for when you're ready to start modifying the firmware, not before.

The three files that matter

The project has many files, but only three contain logic you're likely to touch. Everything else (build configs, the stock demo sketches) is boilerplate.

  4_VideoCar.ino   — the main program. Runs once at boot (setup),
        │             then forever in a loop (loop). The only file you compile
        │             and flash directly.
        │
        ├──includes──▶  SetMotor.h    — talks to the motor driver chip.
        │                 Five tiny functions: forward, backwards, left, right, stop.
        │                 Want a new driving behaviour (e.g. "spin in place")?
        │                 Start here.
        │
        └──includes──▶  app_server.h  — runs the website and the URL commands.
                          Defines every /endpoint (/status, /control, /capture...)
                          and the HTML control page itself.
                          Want a new URL or a new setting? Start here.

.ino is the entry point; the two .h files are libraries it pulls in with #include. This is a common Arduino project shape: keep setup()/loop() short and readable, push everything else into headers.

What happens once, at power-on: setup()

setup() runs exactly one time, right after the board powers up or resets. Here is the actual order of operations in 4_VideoCar.ino, with the real code and what each part is for:

  power on
     │
     ▼
  1 disable brownout detector  ──▶  2 init camera pins/config
     │                                        │
     ▼                                        ▼
  6 start web server  ◀──  5 connect WiFi  ◀──  4 load saved settings  ◀──  3 camera init (retry once if it fails)
     │
     ▼
  7 blink LED 5x ("ready")

1. Turn off the brownout detector — this is the very first line executed:

WRITE_PERI_REG(RTC_CNTL_BROWN_OUT_REG, 0);

The camera draws a brief current spike when it initializes. On a marginal power supply this can sag the voltage enough to trip the ESP32's built-in brownout safety reset. Disabling it lets a slightly weak supply still boot — but it only hides the symptom. If you still get camera failures, the real fix is a better 5V/2A supply, not code.

2–3. Configure and initialize the camera, with a fallback retry:

config.xclk_freq_hz = 20000000;
esp_err_t err = esp_camera_init(&config);
if (err != ESP_OK) {
  Serial.printf("Camera init failed at 20MHz (0x%x), retrying at 10MHz...\n", err);
  config.xclk_freq_hz = 10000000;
  err = esp_camera_init(&config);
}

This is a pattern you'll see throughout the codebase: try something, check the error code, retry once with a safer setting before giving up. Some camera modules don't reliably lock onto a 20MHz clock; dropping to 10MHz on the first failure recovers many of them without an infinite retry loop. If both attempts fail, the code drops into a visible-forever error state:

pinMode(LED_GPIO_NUM, OUTPUT);
while (true) {
  for (int i = 0; i < 3; i++) {
    digitalWrite(LED_GPIO_NUM, HIGH); delay(100);
    digitalWrite(LED_GPIO_NUM, LOW);  delay(100);
  }
  delay(800);
}

A fast triple-flash, repeating — so a camera fault is visible even with no laptop or serial cable attached. This is intentionally an infinite loop: setup() never returns and loop() never starts, because there is nothing useful the car can do without a working camera.

4. Load settings you saved earlier from flash memory (called NVS — Non-Volatile Storage), so Speed/Trim/Flip/Mirror/Quality survive a reboot instead of resetting every time:

prefs.begin("videocar", false);
s->set_framesize(s, (framesize_t)prefs.getInt("framesize", FRAMESIZE_QVGA));
vflipState = prefs.getInt("vflip", 1);
speed = prefs.getInt("speed", speed);

prefs.getInt("key", fallback) reads a saved value, or uses fallback if nothing was ever saved (e.g. a brand-new board). This is why the car "remembers" your settings after you close the browser tab — every /control request that changes a setting also calls the matching prefs.putInt(...) to write it back (covered below in How events flow through the code).

5. Connect to WiFi — either join a router, or create the car's own network, with a bounded timeout so it can never get stuck:

bool ap = 1;
const char* ssid = "keyes1";
const char* password = "88888888";

These three lines near the top of the file are the ones you'll edit most often. ap = 1 means "the car creates its own WiFi access point" (what the walkthrough above uses). Change it to ap = 0 and the car instead tries to join your router using the SSID/password you set here.

unsigned long staStart = millis();
while (WiFi.status() != WL_CONNECTED && (millis() - staStart) < STA_CONNECT_TIMEOUT_MS) {
  delay(500);
  Serial.print(".");
}
if (WiFi.status() != WL_CONNECTED) {
  Serial.println("Could not join the router within STA_CONNECT_TIMEOUT_MS.");
  ap = 1;  // fall back to standalone AP mode
}

Station mode waits up to STA_CONNECT_TIMEOUT_MS (20 seconds) for the router, then automatically falls back to AP mode if it can't connect — a wrong password or an out-of-range router can never leave the car unreachable.

6. Start the web server — a single call, startCameraServer(), whose internals are the subject of the next section. 7. Blink the LED 5 times as a simple "I'm ready" signal you can see without a serial monitor.

What happens forever, many times a second: loop()

Once setup() finishes, loop() runs over and over for as long as the car is powered. Here it is in full — it is deliberately short:

void loop() {
  // --- Safety failsafe: stop the car if the client has gone quiet ---
  if (actstate != stp && (millis() - lastCommandMillis > CONTROL_TIMEOUT_MS)) {
    Car_stop();
    actstate = stp;
    Serial.println("Failsafe: no command received recently, stopping car");
  }

  // --- Station mode: watch the WiFi link and reconnect if it drops ---
  if (!ap && WiFi.status() != WL_CONNECTED) {
    static unsigned long lastReconnectAttempt = 0;
    if (millis() - lastReconnectAttempt > WIFI_RECONNECT_INTERVAL_MS) {
      WiFi.disconnect();
      WiFi.begin(ssid, password);
      lastReconnectAttempt = millis();
    }
  }

  delay(50);
}
Important for beginners: loop() never drives the car. Driving happens entirely inside the web server's request handlers (next section), triggered by an incoming URL. loop() only ever stops it (the 500ms failsafe, if no command arrives in time) or reconnects WiFi. If you go looking for "where does forward/backward actually happen", it is not here.

How events flow through the code (request → handler)

This is the part most relevant if you want to add a new command or URL. The event model is simple: nothing "listens" continuously for your clicks. Each browser request is a one-off event that the ESP32's tiny web server hands to exactly one function, then forgets. There is no session and no queue — URL in, function call out.

Registering an event: the httpd_uri_t pattern

Every endpoint is declared the same way in app_server.h, inside startCameraServer():

httpd_uri_t cmd_uri = {
  .uri      = "/control",
  .method   = HTTP_GET,
  .handler  = cmd_handler,
  .user_ctx = NULL
};
...
httpd_register_uri_handler(camera_httpd, &cmd_uri);

Four fields: the URL path, the HTTP method, which function handles it, and an optional context pointer (unused here). Registering just tells the server "when a GET request for this path arrives, call this function." All five port-80 endpoints are registered this way, right before the server starts:

                         ┌──▶  /          index_handler     (the control page HTML)
                         ├──▶  /status    status_handler    (JSON of current settings)
  port 80 server ────────┼──▶  /control   cmd_handler       (settings + driving)
                         ├──▶  /capture   capture_handler   (one JPEG)
                         └──▶  /joystick  joystick_handler  (proportional driving)

  port 81 server ────────────▶  /stream    stream_handler    (endless JPEG frames)

Want a new endpoint? This diagram is literally the list of things to add to: write a new handler function, then add one more httpd_uri_t + httpd_register_uri_handler(...) pair for it.

Inside a handler: reading the event's data

Walking through cmd_handler — the function behind /control?var=...&val=... — in the order it actually runs:

buf_len = httpd_req_get_url_query_len(req) + 1;
buf = (char *)malloc(buf_len);
httpd_req_get_url_query_str(req, buf, buf_len);
httpd_query_key_value(buf, "var", variable, sizeof(variable));
httpd_query_key_value(buf, "val", value,     sizeof(value));

This block is the entire job of parsing ?var=car&val=1 out of the URL: get the raw query string, then pull the two named values (var, val) out of it into two small character buffers. Everything after this point is just "if variable equals X, do Y":

int val = atoi(value);
...
if (!strcmp(variable, "framesize")) {
  res = s->set_framesize(s, (framesize_t)val);
  prefs.putInt("framesize", val);
}
else if (!strcmp(variable, "flash")) {
  analogWrite(12, val);
  flashLevel = val;
  prefs.putInt("flash", val);
}
else if (!strcmp(variable, "car")) {
  lastCommandMillis = millis();
  if (val == 1) {           // Forward
    int speed1 = trimmed(speed, -trim);
    int speed2 = trimmed(speed, +trim);
    actstate = fwd;
    i2c_Write(M1_PWM, speed1); i2c_Write(M1_IN, 0);
    i2c_Write(M2_PWM, 0);      i2c_Write(M2_IN, speed2);
  }
  ...
}

atoi(value) turns the text "1" into the number 1. strcmp compares C-style strings (it returns 0 when they're equal, hence !strcmp(...) reads as "if equal"). Two things worth noticing before you add your own branch here:

  • lastCommandMillis = millis() is reset only inside the "car" branch. This is what tells loop()'s failsafe "a driving command just arrived, don't stop yet." If you add a new drive-like command, you must reset this timer too, or the 500ms failsafe will fight you and stop the car mid-command.
  • Most settings call prefs.putInt(...) right after applying the value. That's the save-to-flash half of the load-on-boot code from setup() above. Skip it and your new setting will reset to its default every time the car reboots.

At the very end, every successful request gets the same minimal response:

httpd_resp_set_hdr(req, "Access-Control-Allow-Origin", "*");
return httpd_resp_send(req, NULL, 0);

An empty 200 OK — the browser doesn't need any data back, only confirmation the command was received. The CORS header is what lets a page served from port 80 send requests without the browser blocking them.

The full request → response sequence

  Browser                                    ESP32
    │   GET /control?var=car&val=1
    ├──────────────────────────────────▶   cmd_handler() runs
    │                                         ├─ parses var="car", val="1"
    │                                         ├─ lastCommandMillis = millis()  (resets failsafe)
    │                                         ├─ i2c_Write(...) four times  ──▶  motor driver chip
    │                                         └─ builds empty 200 OK response
    │   ◀──────────────────────────────────  200 OK, empty body
    │
    │   (control page repeats this same request every 100ms while a direction is held)

Adding your own event — the mechanical steps

To add a brand-new setting or drive command (reusing /control):

  1. Add one more else if (!strcmp(variable, "yourname")) block in cmd_handler.
  2. If it changes something that should survive a reboot, call prefs.putInt("yourname", val).
  3. If it's a driving action, reset lastCommandMillis = millis() so the failsafe doesn't cut it short.

To add a brand-new URL / endpoint:

  1. Write a new handler function with the signature static esp_err_t my_handler(httpd_req_t *req).
  2. Declare an httpd_uri_t for it (copy the cmd_uri block above and change the .uri and .handler fields).
  3. Call httpd_register_uri_handler(camera_httpd, &your_uri) in startCameraServer(), alongside the existing ones.

This section only covers the mechanics of wiring up an event — what your new handler should actually do is up to your feature.

How a direction becomes motor motion: SetMotor.h

Once cmd_handler decides "forward", the actual driving is four calls to i2c_Write, which sends two bytes — which pin on the motor driver chip and what value to give it — over the I2C bus to a separate motor-driver board:

void i2c_Write(uint8_t motor, uint8_t pwmvalue) {
  Wire.beginTransmission(slave_addr);
  Wire.write(motor);
  Wire.write(pwmvalue);
  Wire.endTransmission();
}

void Car_forward() {
  i2c_Write(M1_PWM, 255); i2c_Write(M1_IN, 0);
  i2c_Write(M2_PWM, 255); i2c_Write(M2_IN, 0);
}

Each motor has two channels: a _PWM value (0–255, how fast) and an _IN value (which direction). Setting one motor's _IN high and the other's low, with both spinning at full _PWM, is what turns "both wheels forward" into "the car turns in place" — there is no separate turning mechanism, just the two wheels working against each other.

        FORWARD                BACKWARD               LEFT                   RIGHT
     ┌─────────────┐        ┌─────────────┐        ┌─────────────┐        ┌─────────────┐
     │  M1 ▲   ▲ M2 │        │  M1 ▼   ▼ M2 │        │  M1 ▼   ▲ M2 │        │  M1 ▲   ▼ M2 │
     │   (both      │        │   (both      │        │  (left back, │        │ (right back, │
     │   spin fwd)  │        │  spin back)  │        │  right fwd)  │        │  left fwd)   │
     └─────────────┘        └─────────────┘        └─────────────┘        └─────────────┘
        car body   ▲            car body   ▼         car spins  ↺           car spins  ↻

All five direction functions, side by side:

FunctionM1_PWMM1_INM2_PWMM2_INResult
Car_forward()25502550Both wheels spin forward
Car_backwards()02550255Both wheels spin backward
Car_left()02552550Left wheel back, right wheel forward — spins left
Car_right()25500255Right wheel back, left wheel forward — spins right
Car_stop()0000Both motors off

Note that cmd_handler's actual forward/left/right code (shown above) doesn't call these named functions directly — it inlines the same i2c_Write calls with a variable speed (speed1/speed2, adjusted by the trim setting) instead of the hardcoded 255 you see in SetMotor.h. The named functions in this file are the simple originals from the stock keyestudio sketch; Car_stop() is the one still called directly, from both cmd_handler and the failsafe in loop().

Adding a new movement (e.g. a diagonal creep, or a slow-spin) means writing a new function following this same four-line pattern, then wiring it up to a new var value as described in the "adding your own event" box above.

Features (vs. the stock keyestudio sketch)

PlatformIO (firmware/)

Each sketch is its own PlatformIO project under firmware/<name>/, all targeting env:esp32cam (AI-Thinker pinout).

Troubleshooting

SymptomCause / fix
Camera init failed with error 0x106 (PlatformIO only, works in Arduino IDE) ESP_ERR_NOT_SUPPORTED from the camera sensor probe — a toolchain/build-flag mismatch, not hardware. Run ./launch.sh option 8 (Clean) and confirm the pinned platform version roughly matches your Arduino IDE's esp32 core version.
Repeated resets right after a camera error Usually a marginal power supply — camera + WiFi init draws a current spike many FTDI adapters can't supply cleanly. Use a proper 5V/2A source.
Car doesn't stop when the browser tab closes / WiFi drops Shouldn't happen — check the build stamp in the footer; nogit or an unexpected commit means you may be running stock keyestudio firmware with no failsafe.
A Vision feature can't load, on the car's own WiFi Expected the first time — the car's AP has no internet. Join a router, enable the feature once so it caches, then return to the car's AP.
Video feed dies when a Vision/autonomy feature starts CORS mismatch between the page and port 81's stream. The page detects this and reconnects without CORS after two failures, falling back to /capture polling.
Line follower doesn't move at all Put the Speed slider at maximum — it multiplies with the mode's own cap. Raise LINE_SPEED in app_server.h if still stuck.
Line follower weaves or loses the line Lower LINE_KP rather than raising it (latency-dominated loop). Raise LINE_TURN_CUT if it misses corners.
No authentication on the control endpoints: known, unaddressed limitation carried over from the original sketch. Anyone on the keyes1 WiFi network (default password 88888888) can drive the car.
