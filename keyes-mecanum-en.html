This article covers the simple remote for the Keyestudio mecanum robot: one page, four files, a fixed layout. For the configurable widget version, with a drag-and-drop builder and a layout carried by the firmware itself, see Keyes 4WD Mecanum RXY.

Overview

One HTML page, one JavaScript file, one stylesheet, one MakeCode firmware. No build step, no dependencies, no server: open index.html and drive. The layout is fixed — an 8-way mecanum pad with a centre STOP, a speed slider, the head servo, two headlights, and telemetry (distance, three line sensors).

What makes this project worth documenting is not its size but what had to be fixed to make it work at all. Three traps, each silent, each covered below: the micro:bit's inverted UART UUIDs, the wrong MakeCode extension, and the LED matrix stealing the line-sensor pins.

Quick start

  1. Open index.html in Chrome or Edge — Chrome treats file:// as a secure origin, so no server is needed.
  2. Click ⚙ Firmware in the header, copy the code, paste it into makecode.microbit.org in JavaScript mode, add the listed extensions, and flash.
  3. Return to the page, click Connect micro:bit and pick the board.
  4. Drive with the pad or the keyboard: W A S D, diagonals Q E Z C, Space to stop.

Step-by-step: clone, flash & test

From a bare clone to a robot that drives, verifying at each stage rather than with one test at the end.

1. Clone the repository

git clone https://github.com/abourdim/keystudio_4wd_mecanum.git
cd keystudio_4wd_mecanum

2. Open the page

Double-click index.html. Unlike most Web Bluetooth apps this needs no local server: Chrome treats file:// as a potentially trustworthy origin. If you'd rather serve it, npx serve . works too.

3. Prepare the MakeCode project

Click ⚙ Firmware in the header. The dialog shows the version, the steps, the extension URL and the pxt.json Bluetooth block. In MakeCode, create a project, switch to JavaScript, then add:

ExtensionSource
mecanum_robot_v2github.com/keyestudio2019/mecanum_robot_v2
Bluetoothbuilt into MakeCode
Enable No Pairing Required in Project Settings. Without it Windows refuses GATT service access and the connection fails after you pick the board.

4. Paste and flash

Copy code in the Firmware dialog, Ctrl+A then Ctrl+V in MakeCode, Download, drop the .hex on the MICROBIT drive.

5. Verify the link, not yet the motors

Click Connect micro:bit. The chooser should list BBC micro:bit [xxxxx]. Once connected the header reads Connected · K4-v4: that string comes from the firmware itself, so it proves both that the link works and which build is actually flashed.

6. Verify app → robot

Open the browser console (F12) and press a direction. Every command the firmware parses is echoed back: [BLE] ack DRV. That is what separates "the command never arrived" from "the command arrived and did nothing" — two failures that look identical from across the room.

7. Verify robot → app

Without touching anything, the Telemetry card should show a distance in centimetres that changes when you put your hand in front of the sensor, and the three line indicators should react as the robot crosses a black stripe.

A working setup: the header reads Connected · K4-v4, the console logs an ack on every press, the wheels move in the direction of the pad, distance tracks your hand, and the three line lights come on one at a time as you slide the robot across a black stripe.

Trap 1: the micro:bit's UART UUIDs are inverted

The micro:bit reverses the usual Nordic convention. This was the most expensive failure in the project, because it doesn't look like a coding mistake at all:

UUIDNordic conventionOn micro:bit
6e400002-…RX (write)TX — notify (board → browser)
6e400003-…TX (notify)RX — write (browser → board)

Swapping them produces NotSupportedError: GATT Error: Not supported. at connect time — a message that suggests a pairing or driver problem, when in fact it is just startNotifications() called on a write-only characteristic.

Trap 2: the micro:bit does not advertise its UART service

Filtering requestDevice() on the UART service never matches anything: the micro:bit does not put that UUID in its advertisement. Filter by name and declare UART as an optional service:

device = await navigator.bluetooth.requestDevice({
  filters: [{ namePrefix: 'BBC micro:bit' }, { namePrefix: 'uBit' }],
  optionalServices: [UART_SERVICE]
});

app.js also wraps every setup call in a timeout, because getPrimaryService() can hang forever without resolving or rejecting, and tears down a half-open GATT server on failure — otherwise the next attempt fails at exactly the same step.

Trap 3: V1 and V2 are not the same extension

Keyestudio ships two extensions with near-identical APIs. Writing code for the wrong one compiles perfectly and moves nothing, because the motor driver sits at a different I2C address and never acknowledges:

V1 (mecanumRobot)V2 (mecanumRobotV2)
Stopstate(MotorState.stop)state(), no argument
Line sensorsP1, P2 (two)P3, P4, P10 (three)
Motors / headlightsI2C 0x47I2C 0x30
WS2812 stripP8 (documented)P7 (undocumented)
The signature symptom: Bluetooth connects, commands are acknowledged, distance and line sensors report real values — and absolutely nothing moves. It looks exactly like a flat battery. It isn't one.

Trap 4: the LED matrix steals the sensor pins

The V2's three line sensors are on P3, P4 and P10, which also drive the rows and columns of the 5×5 matrix. While the display is enabled those pins are multiplexed and a digital read returns noise. Hence, at firmware startup:

// The three line sensors are on P3, P4 and P10 -- all LED-matrix pins.
// This firmware never draws on the matrix, so switching it off is free.
led.enable(false)

The ultrasonic: why a hand-written read

The firmware reads the HC-SR04 with its own sequence rather than mecanumRobotV2.ultra(): a 15 µs trigger pulse instead of 10, and an explicit PullNone on the echo pin as well as the trigger. 10 µs is the datasheet minimum and clone modules are often marginal there. The extension's version stays as a fallback:

let cm = ultraRaw()
if (cm <= 0) cm = mecanumRobotV2.ultra()
if (cm > 0) bluetooth.uartWriteLine("DIST " + cm)

The Firmware dialog, and why the code is duplicated

The ⚙ Firmware button shows the full source with a copy button. It is embedded in index.html in a <script type="text/plain"> block rather than loaded with fetch(): the page normally opens from file://, where Chrome blocks fetch(). A runtime read would fail in exactly the situation the dialog is for — the robot in front of you and no server running.

The cost is a second copy of the firmware in the page, hence the regeneration tool, with a mode that reports drift:

node tools/embed-firmware.js          # rewrite index.html
node tools/embed-firmware.js --check  # exit non-zero if the two differ

The displayed version is parsed out of the embedded source (uartWriteLine("VER ...")) rather than hardcoded, so the dialog cannot claim a build the file is not.

One command, round trip, in order

Browser                                      micro:bit
    │                                             │
    │  pointerdown on ↑                           │
    │  drive('f') ─▶ send("DRV f 25")             │
    │ ─────────────────────────────────────────▶  │
    │                              onUartDataReceived
    │                              p = ["DRV","f","25"]
    │                              drive("f", 25)
    │                              wheels(1,1,1,1,25)
    │                                     │       │
    │  ◀───────────────────────── "ACK DRV"       │
    │                                             │
    │  pointerup ─▶ send("STOP")                  │
    │ ─────────────────────────────────────────▶  │
    │                              state()  (stop)
    │  ◀───────────────────────── "ACK STOP"      │
    │                                             │
    │        nothing for 1.5 s:                   │
    │        the watchdog stops the wheels        │

The watchdog runs in its own 200 ms loop, separate from the 1 s telemetry loop: a blocking ultrasonic read must never delay a motor stop.

Pin map and hardware traps

Read from the extension source, not inferred:

FunctionPinNote
Line sensors left / center / rightP3 / P4 / P10Matrix pins — require led.enable(false)
Ultrasonic trigger / echoP15 / P16Needs 5 V from the battery
Head servoP14Trim SERVO_OFFSET = 20
Motors, headlightsI2C 0x30Via Motor() / setLed()

Speed is on the extension's 0–100 scale, not a 0–255 PWM duty. Sending 200 is the same as sending 100: the whole top half of the slider then does nothing.

Troubleshooting

SymptomCause / fix
The Bluetooth chooser stays emptyFiltering on the UART service instead of the name — the micro:bit does not advertise that UUID. See trap 2.
NotSupportedError: GATT Error: Not supported.TX/RX UUIDs swapped. 6e400002 notifies, 6e400003 takes writes.
Connects and acknowledges, but nothing movesAlmost always the wrong extension: V1 code on a V2 board. Check the namespace is mecanumRobotV2.
Line sensors report nonsenseLED matrix still enabled. led.enable(false) is required: P3, P4 and P10 belong to it.
Distance always 0The HC-SR04 needs 5 V from the battery: the board's power switch must be on, USB alone is not enough. Also check the connector, which rides the moving servo head.
The top half of the speed slider does nothingThe extension expects 0–100; anything above is clamped.
The servo does not point straight at 90°Adjust SERVO_OFFSET in the firmware (20 by default on this chassis).
The Firmware dialog shows an old versionThe firmware was edited without re-running node tools/embed-firmware.js.
