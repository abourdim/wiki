This article covers rxy (Micro:bit Remote Builder), a no-code drag-and-drop tool for designing custom Bluetooth remote controllers for the BBC micro:bit — unique in this app family for generating its own MakeCode firmware on the fly, and for being able to flash that firmware straight from the browser over Bluetooth.

Overview

bit-rxy lets you design a custom Bluetooth remote — buttons, sliders, joysticks, gauges, whatever you need — by dragging widgets onto a canvas, then generates the matching MakeCode firmware for you automatically. Unlike Bit-Bot, Talking Robot, and micro:bit Playground (which all ship one fixed firmware protocol), here the protocol itself is generated per-design: every widget you place becomes a handler block in the exported code, and the whole layout is embedded into the firmware as a Base64 string so the micro:bit can hand its own configuration back to any app that asks for it.

It also goes a step further than the other apps in this family: instead of only offering "copy this code into MakeCode," it can compile the generated code and flash it to the board directly from the browser, either over Bluetooth (using the micro:bit's built-in Partial Flashing Service) or over WebUSB.

Quick start

  1. Open the live app in Chrome or Edge.
  2. On the ✏️ Build tab, drag widgets onto the canvas (or start from a template).
  3. Click 📄 Code, copy the generated MakeCode, paste it into makecode.microbit.org, and flash via USB — or use the in-app flash button to do it over Bluetooth/WebUSB instead.
  4. Switch to the ▶️ Play tab, tap 📡 Tap to Connect!, and start controlling your micro:bit.

Step-by-step: clone, flash & test

This walkthrough takes a bare checkout to a verified-working remote: one widget sent successfully in each direction.

1. Clone the repository

git clone https://github.com/abourdim/bit-rxy.git
cd rxy

2. Serve it locally

No build step, but Web Bluetooth/WebUSB refuse a bare file:/// path:

npx serve .

Open the printed http://localhost:... URL in Chrome or Edge (the live GitHub Pages copy works the same way with no setup).

3. Build a minimal remote

On the ✏️ Build tab, drag one Button widget and one LED widget onto the canvas. This is the smallest possible round-trip test: one input, one output.

4. Get and flash the code

Click 📄 Code to open the generated MakeCode. Either copy it into makecode.microbit.org and flash via USB the normal way, or try the in-app Flash button, which attempts to compile the code and push it straight to a connected board over Bluetooth or WebUSB (see Understanding the code for how this works, and its fallback path if compilation fails).

5. Test the input direction (app → micro:bit)

Switch to ▶️ Play, tap 📡 Tap to Connect!, pick your board, then press your Button widget. The micro:bit should react immediately (the default generated handler shows a heart icon).

6. Test the output direction (micro:bit → app)

In the MakeCode editor, add one line to send a value back: sendValue("your_led_id", "1") inside a button-press or forever block, reflash, and confirm your LED widget lights up in the app when triggered.

A working baseline looks like: the micro:bit shows a heart when you tap the Button widget, and the LED widget in the app lights up when the firmware calls sendValue() — both directions of the protocol confirmed independently.

Understanding the code (for newbies)

For anyone with the app running who wants to open the source and start changing something. Assumes basic JavaScript but nothing about this codebase specifically. Skip it if you only want to use the app.

System architecture, illustrated

┌─────────────────┐         Bluetooth          ┌─────────────────┐
│                 │  ◄───────────────────────► │                 │
│   📱 Your App   │         BLE UART           │  🔲 micro:bit   │
│   (Phone/PC)    │                            │                 │
└─────────────────┘                            └─────────────────┘
        │                                              │
        │  You press a widget                         │
        │  ─────────────────►  SET btn_fire 1         │
        │                                              │
        │                      firmware runs your      │
        │                      handleWidget() code,    │
        │                      can call sendValue():   │
        │  UPD led_status 1   ◄─────────────────      │
        │                                              │
        │  On connect: GETCFG ───────────────►        │
        │  CFGBEGIN / CFG.../ CFGEND ◄──────────      │
        │  (the layout you designed, replayed back     │
        │   from the firmware itself)                  │

The key difference from the other three apps in this family: the micro:bit isn't just a fixed remote peripheral — it's carrying its own configuration. Connect any copy of this app to a flashed board and it will faithfully redraw whatever layout was baked in at flash time.

The code generator: from canvas to firmware

generateDemoCode(cfg) takes the current widget list and, for each widget, emits a matching if (id == "...") handler block into a firmware template — a Button widget gets an "on press, show a heart" block; a Slider gets a "parse the value, plot a bar graph" block; and so on for all 12 widget types. Every generated handler is deliberately simple and commented // Add your code here! — it's meant to be a starting point you edit in MakeCode, not a finished program.

function generateDemoCode(cfg) {
  const b64 = btoa(unescape(encodeURIComponent(JSON.stringify(cfg))));  // Unicode-safe (handles emoji labels!)
  const buttons = cfg.widgets.filter(w => w.t === 'button');
  const sliders = cfg.widgets.filter(w => w.t === 'slider');
  // ...one filter per widget type...

  let buttonCode = buttons.map(w => `    if (id == "${w.id}" && val == "1") {
        basic.showIcon(IconNames.Heart)
        // Add your code here!
    }`).join('\n');
  // ...same pattern for every other widget type, then stitched into
  // the firmware template alongside the embedded CFG Base64 string...
}

How the layout survives on the micro:bit itself

The entire widget layout is JSON-stringified, Base64-encoded (via a Unicode-safe btoa(unescape(encodeURIComponent(...))) chain so emoji labels survive), and baked directly into the generated firmware as a string constant. The firmware then knows how to hand that string back over Bluetooth in 18-byte chunks whenever asked:

const CFG = "${b64}"   // baked in at generation time

bluetooth.onUartDataReceived(serial.delimiters(Delimiters.NewLine), function() {
    let cmd = bluetooth.uartReadUntil(serial.delimiters(Delimiters.NewLine))
    if (cmd == "GETCFG") {
        bluetooth.uartWriteLine("CFGBEGIN")
        for (let i = 0; i < CFG.length; i += 18) {
            bluetooth.uartWriteLine("CFG " + CFG.substr(i, 18))
        }
        bluetooth.uartWriteLine("CFGEND")
    } else if (cmd.indexOf("SET ") == 0) {
        let parts = cmd.substr(4).split(" ")
        handleWidget(parts[0], parts.slice(1).join(" "))
    }
})

18 bytes per chunk keeps every line comfortably under the ~20-byte BLE MTU used throughout this app family. On the browser side, the reassembled Base64 is decoded back into the exact widget layout you built — which is how the Play tab can render your remote correctly even in a browser session that never touched the Build tab.

One-click flashing: Partial Flashing Service and WebUSB

Beyond the standard "copy code into MakeCode" path, flashToMicrobit() attempts to compile the generated code via a MakeCode compiler helper and push the resulting .hex straight to the board over Bluetooth, using the micro:bit's Partial Flashing Service — a real DAL feature (UUID e97dd91d-...) that lets a previously-USB-flashed board accept program updates over BLE without a cable:

const PFS_SERVICE = 'e97dd91d-251d-470a-a062-fa1922dfa9a8';
const PFS_CHAR    = 'e97d3b10-251d-470a-a062-fa1922dfa9a8';
const PFS_CMD = { REGION_INFO: 0x00, FLASH_DATA: 0x01, END_OF_TX: 0x02, STATUS: 0xEE, RESET: 0xFF };

If the compile step fails for any reason, the app doesn't just give up — it falls back to opening MakeCode in a new tab so the user can compile and flash manually. A separate flashViaUSB() path offers the same "flash without leaving the browser" convenience over a direct USB (WebUSB) connection instead of Bluetooth, for boards that haven't been paired yet.

Bluetooth protocol reference

Nordic UART over BLE, same service/characteristic UUIDs as the rest of this app family (6e400001/2/3-...):

DirectionMessageMeaning
App → micro:bitSET widget_id valueA widget was interacted with.
micro:bit → AppUPD widget_id valueThe firmware pushed a new value to display.
App → micro:bitGETCFGRequest the embedded layout config.
micro:bit → AppCFGBEGIN / CFG <chunk> / CFGENDThe layout, streamed back as 18-byte Base64 chunks.

Languages

Full English, French, and Arabic translation across the header, template picker, builder toolbar, widget palette, props panel, Play/runtime view, tutorial, loading overlay, code modal, and the toasts for every core action — using a tr(path, vars) helper that does a dotted-key lookup into the I18N object (e.g. tr('toast.sizeSet', {w, h})) with {placeholder} interpolation for dynamic values. Arabic flips the whole page to dir="rtl" and uses the Algerian flag, matching the rest of this app family.

Unlike the browser-language auto-detection used early on, the app now defaults straight to French on first visit and only switches on an explicit choice, persisted under its own kid_lang localStorage key — matching Bit-Bot, Talking Robot, and micro:bit Playground.

Deliberately left in English: the widget Properties form's per-field labels (Width, Height, Min, Max, etc. — about 100 strings spread across the 12 widget types) and the hidden power-user "Helper Tools" panel (Group, Layers, Ruler, Align, Distribute, Canvas Background, Screenshot, Share — all gated behind a dev-only button, never shown to normal users), the same scope line drawn for Bit-Bot's excluded Commands panel.

Troubleshooting

SymptomCause / fix
Can't connect to micro:bitConfirm Bluetooth is on, the board shows a ❤️ (ready), and only one device is connected at a time — refresh and retry if a previous session didn't disconnect cleanly.
Connect always fails on iPhone/iPadiOS has no Web Bluetooth support in Safari or any other iOS browser (they're all WebKit under the hood) — this is a platform limitation, not a bug. The app detects this and points to the free "Bluefy" browser (search the App Store) instead of just saying "Connection failed."
Widgets don't do anythingConfirm the generated code was actually flashed, and that widget IDs in the firmware match the IDs shown in the Code panel — regenerate and reflash after any layout change.
One-click Bluetooth flash failsThe Partial Flashing Service requires a board that's already running a compatible MakeCode runtime from a prior USB flash; if the compile step fails outright, the app opens MakeCode in a new tab so you can flash manually instead.
micro:bit disconnects randomlyStay within Bluetooth range (~10m), check the battery, and reduce how often sendValue() is called if you're flooding the link.
D-Pad shows no arrowRegenerate the code after any Build-tab change and reflash — stale firmware won't know about a widget added afterward.
