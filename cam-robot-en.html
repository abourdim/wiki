This robot has no hosted app — it serves its own page. Join its Wi-Fi and open http://192.168.4.1. No install, no app store.

This article covers the ESP32-CAM Robot, revision m2: one camera, two motors, and a single chip running both. The robot hosts its interface inside its own firmware, which makes it self-contained — but it also forces the camera and the motors to share hardware, which is where the failure described below comes from.

For a rover where the app lives apart from the robot, see Workshop for under-14s · rxy-web. For the other camera robot, the one whose camera board does not drive the motors at all, see VideoCar. For the robot that came before this one, on the same camera but without an H-bridge, see m1.

Overview

The robot is its own server. There is nothing to install: the firmware carries the complete HTML page, serves it on port 80, and streams video on port 81. A phone, a tablet or a laptop opens one address and drives.

That is the fundamental difference from the rxy rovers, where a hosted app asks the robot for its layout. Here there is no app at all, so there is no app version to match — but the page rides in the robot's flash, and every interface change means reflashing.

The page is stored compressed. The HTML literal is 154 KB; tools/gzip_ui.py produces a 36 KB gzip copy in index_html_gz.h, and that is what goes over Wi-Fi — the same link carrying the video. Forget to re-run the script and the firmware notices at boot on its own: it compares the recorded length and hash against the literal it was built with, and falls back to serving the page uncompressed, saying so in the log.

One chip does everything: the camera, both motors, Wi-Fi and the web server. That is what makes this robot small and cheap, and it is also the source of its most confusing faults. See the LEDC timer bug.

Quick start

  1. Power the robot. The flash LED blinks three times: the CPU is running.
  2. It tries the configured Wi-Fi network for 10 seconds. If that fails, it opens its own access point.
  3. Join ESP32-Robot-XXXX, password 88888888. The XXXX comes from the MAC address, so several classroom robots do not collide.
  4. Open http://192.168.4.1. The picture appears, and the header shows the robot name and a Live pill.
  5. Press an arrow and hold it: the robot drives while you hold, and not half a second longer.

Step by step: clone, flash & test

The repository is an ordinary Arduino sketch at the root, with a PlatformIO project pointing at it. Both build the same file.

git clone https://github.com/abourdim/wdi_esp32_cam_robot_m2
cd wdi_esp32_cam_robot_m2
pio run -e esp32cam

Flashing goes through a 3.3 V USB-TTL adapter. This carrier board has no auto-reset: you must hold GPIO0 low while powering up to enter upload mode.

pio run -e esp32cam -t upload --upload-port COM31
pio device monitor -b 115200

Upload speed is deliberately pinned to 115200 in platformio.ini. A faster link often connects and then dies right after the baud switch, which shows up as a baffling failure halfway through a transfer.

A second environment, esp32cam-debug, produces a symbol-rich image. Use it only to reproduce a crash: PlatformIO's exception decoder needs the matching firmware.elf to translate a backtrace.

Arduino compiles every .ino file in one folder. Never leave two firmware versions side by side: the error it produces (redefinition of ssid) does not say where it came from.

The board and its pinout

The driver is a TB6612FNG (SparkFun ROB-14450 module). The important detail in the schematic, the one everything else in the motor firmware follows from: PWMA and PWMB are wired to the same pin, GPIO12.

The usual TB6612 arrangement puts PWM on the enable input and uses the direction inputs as plain on/off. That is impossible here without losing independent left and right speed control. So the firmware inverts the logic: GPIO12 is held high continuously, and PWM is applied to one direction input per motor. Direction is chosen by deciding which of the two inputs carries the duty cycle.

SignalPinRole
PWMA + PWMBGPIO12Shared enable, held high while moving
AIN1GPIO2Motor A / J6 — left, forward
AIN2GPIO13Motor A / J6 — reverse
BIN1GPIO15Motor B / J7 — right, forward
BIN2GPIO14Motor B / J7 — reverse
STBY+5 VHard-wired enabled
Flash LEDGPIO4Lighting and the boot blink

Starting is gradual: 16 steps of 12 ms up to the requested duty and never beyond it. When both motors start together, the second is staggered by five steps (about 60 ms) so the two inrush currents do not coincide. A direction change always passes through a stop with a 60 ms pause: slamming a loaded geared motor from forward into reverse punishes the gearbox and creates one more current spike.

The LEDC timer bug: when the camera clock steals a motor's PWM

This is the most instructive failure on this robot, and it held out for a long time because every symptom pointed at hardware.

The symptom. Any command that drove the left motor reset the board instantly: rst:0xc, no backtrace, no Guru Meditation. Sometimes the camera fell over first, with an SCCB_Write Failed followed by a sensor probe that got no answer at all. Commands that drove only the right motor ran indefinitely.

The false trail. An asymmetry like that looks like a seized motor or a weak supply. Changing the left motor's speed — from 71 to 146 out of 255 — made no difference whatsoever, which seemed to confirm a mechanical fault. It was in fact the decisive clue, misread.

The cause. The Arduino core has no LEDC channel allocator: group and timer are derived from the channel number and nothing else.

group = channel / 8        (0 = high speed, 1 = low speed)
timer = (channel / 2) % 4

And esp_camera_init() reprograms low-speed timer 0 to 20 MHz with a duty resolution of one single bit, to generate the sensor's XCLK. Channels 8 and 9 — the left motor — land on exactly that timer.

So from camera init onward, the left motor had one bit of resolution. Nothing failed loudly: ledcWrite() kept returning normally, but every non-zero value saturated the comparator and pinned the pin high. The soft start ramped through sixteen steps that were all already 100 %. The left motor therefore took a maximum current step, all at once, on every command — and the board collapsed.

This is also why changing the speed achieved nothing: 71 and 146 saturate one bit in exactly the same way. A setting with no effect is not proof of a mechanical fault; it can be proof that the setting never reaches the hardware at all.

The fix. The left motor moved to channels 12 and 13 (timer 2); the right stays on 10 and 11 (timer 1). The camera keeps timer 0, the flash LED keeps timer 3 of the high-speed group. Nothing overlaps any more.

Two guards stop the fault coming back. static_asserts on the channel numbers fail the build if a motor channel or the LED lands on the camera's timer. And verifyMotorLedcTimers() reads the two timers' real frequency back after every esp_camera_init() — at boot and after each in-place sensor recovery — then writes it to the log:

BOOT: Motor LEDC timers OK; left 1000 Hz, right 1000 Hz

If some future Arduino core or camera driver update moves a timer anyway, that line will say so, and the firmware stops the motors rather than leaving them at full power.

The lesson generalises: on any ESP32-CAM board, keep motor and servo PWM off channels 8 and 9. The failure is silent by construction.

Driving: hold, keepalive, and the dead man's switch

The arrows drive only while they are held. Every command is a fire-and-forget request, so any one of them can be lost — and the one that matters is the stop. A dropped stop used to leave a wheel turning until some later command happened to get through.

So the robot no longer relies on hearing the stop:

  • A held button repeats its command every 250 ms.
  • If the robot hears no motion command for 600 ms, it stops the motors itself and logs SAFETY: motion timeout; motors stopped.
  • The release sends stop twice, 150 ms apart.
  • Losing window focus, hiding the tab, or leaving the page also stops.

A lost packet, a closed laptop, a browser that never reported the release, a robot that drives out of range: they all end the same way, motors stopped within about half a second.

Keepalive repeats are not written to the event log — several entries a second would bury everything else — so a held button still shows as one command.

The video and its overlays

The MJPEG stream is served on port 81, VGA at quality 12 with two frame buffers when PSRAM is present, QVGA when it is not. Quality 12 rather than 10 because the Wi-Fi link, not the sensor, sets the frame rate.

  • The camera always hands over its newest frame. Queued frames would arrive a capture late, which looks like lag even when the frame rate is fine.
  • Wi-Fi modem sleep is switched off: left on, the radio parks between beacons and the picture stutters.
  • One viewer at a time. A second browser is told the stream is in use rather than left with a picture that never arrives.
  • The page reconnects on its own. A failed capture and a reboot both end the stream without any error the browser can see; the page notices within a few seconds.
  • The stream pauses while its tab is hidden, so a forgotten tab does not hold the single viewer slot.

The overlays are not burned into the image: they are page elements sitting beside it. So they stay upright at every display rotation, and anything that records the stream gets clean frames. Burning them in would mean decoding, drawing and re-encoding every frame on the ESP32, costing far more frame rate than the mark is worth.

Bottom right, three readouts at 30 % opacity at rest, coming up to full the moment one of them matters: the robot is moving (RIGHT 220/0, blue), the signal is at or below −75 dBm (amber — the earliest honest warning that you are driving out of range, since the video outlasts the commands), or the dead man's switch has just fired (TIMEOUT, red, three seconds).

The frame rate is measured on the robot: a browser reports a multipart image as loaded once, on the first frame, and cannot count them.

The web interface

Three views share the page, chosen in the header — Drive, Program and Games — with the video above all three.

Drive is the four arrows with STOP in the middle of them, one Speed control, and Light, in that order. The control a child uses every second sits directly under the thing they have to watch, so on a phone the picture and the arrows are on screen together and driving never means scrolling. Speed moves both motors and keeps whatever difference is set in Settings. Releasing an arrow stops the robot anyway, so STOP is the backup rather than the only way.

Settings → Robot holds everything that differs from one robot to the next: name, speed limit, wheel direction, motor trim (the Sync checkbox and the two per-motor sliders) and the measured wake-up numbers — the same set the robot keeps in NVS. Wheel direction is two checkboxes for a chassis assembled with a motor's leads the other way round.

A sticky header, and two collapsible sidebars. The split is by what you are doing: Settings is what you change on the robot, Debug is what you watch while driving it.

Settings gathers the camera (resolution from QQVGA to UXGA, display rotation, JPEG quality, brightness, contrast, saturation, flip and mirror), the robot (name, speed limit, measured wake-up numbers), Wi-Fi (scan and join), the USB serial console, and the OTA uploader.

Debug shows motion state, requested and actual left/right PWM, network mode, IP address, AP client count, RSSI, uptime, stream frame rate, and an exportable 64-event history.

Settings are split by who owns them. What describes the robot — camera settings, motor speeds, LED — lives in NVS on the robot and comes back after a power cycle. What describes your browser — display rotation, serial baud, which sections are open — stays in localStorage. Putting the former in the browser would break in two ways: a phone and a laptop would restore two different sets of values and overwrite each other, and a robot rebooted without the right browser open would come back on firmware defaults.

Flash writes are held for four seconds after the last change: the sliders send on every movement, and committing at that rate would be hundreds of writes for one drag.

The 0/90/180/270 rotation turns the stream in the browser. Vertical flip and horizontal mirror are sensor settings. The first is free; the second is applied by the camera.

Record and replay

The header offers two views of the same column, Drive and Program, with the video above both so a program can be watched while it runs.

Press Record, drive the robot by hand, press Stop. What you just did becomes a list of instructions:

1   0.0s   Forward
2   1.4s   Stop
3   0.6s   Right
4   0.5s   Stop

Play does it again. Change a pause, delete a line, play it again — that is the whole point. A child drives first and reads their own program second, which is a gentler route into programming than starting from an empty editor.

Three slots keep programs on the robot, not in the browser, so a program follows the robot around the classroom rather than the tablet that recorded it.

The safety comes from reuse: playback calls exactly the same functions the buttons do, so a replayed drive sends the same 250 ms keepalives and obeys the same 600 ms timeout. A program cannot drive the robot in a way a child could not. An interrupted replay always sends a stop.

Games: the camera as a sensor

Four activities in which the camera stops being a picture for a person and becomes the robot's only sensor. One at a time, because only one can drive the robot.

While a game runs, the strip of picture it is reading is drawn on the video, over the pixels it came from, with its reading in the telemetry line. That is the point of them rather than a debug aid: a child can see what the robot is deciding from, so “why did it turn there?” is answered by looking instead of by reading code.

Follow the torch. Reads a strip across the middle of the picture, compares the brightness of each half, and turns towards the brighter one. Dim the room and walk backwards with a phone torch.

How fast does it turn? The robot spins itself for two seconds each way and measures how far the picture slid between frames, which becomes degrees per second. Each run records the requested speed, the left rate, the right rate and the gap between them. The gap is the lesson. The two should match and will not, because the motors are not identical — the same truth the wake-up numbers teach, with the robot measuring itself this time.

Follow the line. Dark tape on a pale floor, read from a strip along the bottom of the picture — the floor just in front of the wheels. A checkbox handles a pale line on a dark floor. It stops rather than guessing and says which of four things it hit: too dark to see the floor, nothing that looks like tape, a dark patch too wide to be a line, or more than one patch and no way to tell which was meant.

Follow the card. Show it a brightly coloured card and it learns that colour, then turns towards it. A card and not a hand, on purpose: recognising a hand needs a model this page cannot load, and the shortcut people reach for instead — testing pixels for skin colour — works for some children and not others. A card works for everyone, and a child can disprove “it follows my hand” by hiding the card and waving.

A hand over the lens stops whichever game is running. A covered lens is dark, flat, and a change from a lit picture — all three, or an unlit room would stop the robot too.

Frames come from /capture on port 80 rather than the stream on port 81: the stream is a different origin, and drawing it into a canvas taints the canvas so the pixels cannot be read back. Every game sends its commands through the same path a held button does, at the same cadence and under the same 600 ms timeout — a game cannot ask the robot for anything a finger could not.

What they cannot do is forward speed. Driving forward makes the picture expand from the centre instead of sliding, and how fast it expands depends on how far away the furniture is. Metres per second would need the camera pointed at the floor, or one calibration drive over a known distance.

Finding the wake-up number

Settings → Robot → Measure them starts a guided activity. It powers one wheel at a time, starting at 20 out of 255, stepping up by 5, and asks whether the wheel is turning. When the child says it is, that number is the motor's starting threshold, and it is saved on the robot.

The two motors will disagree, often by 20 or 30. That difference is the lesson: identical parts are not identical, and it is why the robot pulls to one side.

The activity reuses the steering commands to run one wheel at a time: testing the left wheel goes through the right-turn command. It hides that detail, and restores the driving speeds it found when it started, so a class does not end up wondering why the robot got slow.

Networking: the fallback access point

At boot the robot tries the configured network for 10 seconds. If it succeeds, it runs as a station. If not, it opens its own access point: ESP32-Robot-XXXX, password 88888888, address 192.168.4.1. The XXXX comes from the base MAC address, so several classroom robots do not share a name.

A network picked in Settings → Wi-Fi is stored on the robot, so moving it between a workshop and a classroom no longer means reflashing it. The access point stays up throughout the attempt and after a failure, so it is not possible to lock yourself out of the robot from the robot's own interface.

Two behaviours are worth knowing, because they are counter-intuitive:

  • A scan disturbs the video. The scan and the access point share one radio. That is why scanning is a button and never something on a timer, and why the robot refuses to scan while it is moving: a scan blocks the control server for several seconds, which would starve the motion keepalive and trip the safety timeout mid-manoeuvre.
  • While any client is connected to the fallback AP, the retries stop, and the log says so once. They resume when the last client leaves. The consequence: if you stay connected to the AP, the robot will not rejoin the normal network on its own. Disconnect for a minute, or reboot it.

With nobody connected, retries back off from 30 seconds, doubling to a five-minute cap.

This is not a security control. 88888888 is both the AP password and the OTA password, the page is HTTP, and a Wi-Fi password typed into it travels in clear over the link. That is convenient for a classroom and unsuitable for an untrusted environment.

What the LED is telling you

GPIO4 is the module's flash LED and the robot's only indicator. Every status pattern runs at a few percent of full scale: it is painful to look at near full brightness, and this is a high-power LED on a board that browns out easily. The patterns differ by rhythm rather than by count — nobody reliably counts blinks across a room, and everybody notices fast against slow.

  • Three short flashes on power-up — the CPU is running. If these appear, the board booted and whatever goes wrong next is software.
  • A fast blip, four times a second — trying the configured Wi-Fi. This is the ten-second window, and the blip is the dot the serial console prints, for somebody without a cable.
  • Two long marks — joined the configured network.
  • Long, short, long — the network was unavailable and the fallback access point is up. The normal case in a workshop, not a fault.
  • Groups of short flashes — the last group of the address it was given, a digit at a time: 137 is one flash, three flashes, seven flashes. Zero is a single long mark.
  • One dim pulse a second — running, joined to the configured network.
  • One dim pulse every five seconds — running on the fallback access point.
  • A glow that rises steadily — firmware is being written. Do not cut the power. It is a glow rather than a blink so it cannot be mistaken for anything above.
The heartbeat yields to the light: switch the flash LED on from the page and the pulsing stops until you switch it off again. Boot status does not yield, because nobody has asked for the light yet at that point in the startup.

UART0 serial console

UART0 runs at 115200 8N1 on U0T / GPIO1 and U0R / GPIO3. Use a 3.3 V TTL adapter; never connect RS-232 voltage levels directly to the ESP32.

ESP32-CAMUSB-TTL adapter
U0T / GPIO1RX
U0R / GPIO3TX
GNDGND

Five commands: help, status, log, camera, and stop, which performs an emergency motor stop.

status is the robot's most useful diagnostic, because it prints the PWM actually applied left and right. Holding an arrow in the browser and typing status in the console while it is held separates a firmware fault from a hardware fault in one move.

Chrome's Web Serial requires a secure context, and a page opened at http://192.168.x.x is not one: COM port access from the robot's own interface may be blocked even though everything else works. Hence the standalone ESP32_Robot_USB_Serial_Console.html, served from localhost.

python -m http.server 8000

Updating over Wi-Fi

The Debug sidebar contains an OTA uploader. Password: 88888888. Motors are stopped before firmware writing, and the robot reboots after a successful transfer.

OTA requires the board to have been flashed once over USB with a partition scheme that reserves an update slot. The project uses min_spiffs.csv, the "Minimal SPIFFS (1.9MB APP with OTA / 190KB SPIFFS)" entry in the Arduino menu. The board default has no OTA slot, and the uploader would fail at Update.begin().

The file to send is the application alone, *.ino.bin — never *.bootloader.bin, *.partitions.bin or *.merged.bin.

The running firmware's build stamp is shown in the OTA card, deliberately: it is what tells you an upload actually took. Upload, wait for the reboot, check the date changed.

Troubleshooting

The board resets as soon as a motor starts

First note which motor. If it is always the same one, and the other runs indefinitely, this is almost never the supply: read the LEDC timer bug. Check the Motor LEDC timers OK line at boot — if a timer is reported at 20 MHz instead of 1000 Hz, the fault is back.

If both motors cause the reset, then yes, it is the supply: a soft 5 V rail, a thin ground, or a missing decoupling capacitor.

Only one motor runs, whatever the command

Hold the relevant arrow and type status in the serial console. If the silent motor's PWM is shown there, the firmware is doing its job and the fault is downstream: swap the J6 and J7 connectors. If the fault follows the connector it is the motor or its wiring; if it stays on the same channel it is the TB6612 or the drive pin.

The motor buzzes without turning

Duty below that motor's starting threshold. This is usable in class — see Finding the wake-up number — but do not leave a stalled motor powered for long.

The configured Wi-Fi is never joined

Check the SSID spelling, the password, that a 2.4 GHz band exists, the signal level, and the router's security compatibility. The log gives the reason: SSID not found, authentication failed, connection lost. Remember too that staying connected to the fallback AP suspends the retries.

High resolutions fail

Confirm PSRAM is detected at boot. Without it only the small resolutions work, and a resolution saved on a board with PSRAM is deliberately not restored onto a board without it: the allocation would fail and take the stream with it.

The log reports a stale UI asset

tools/gzip_ui.py was not re-run after an interface change. The robot then serves 154 KB uncompressed instead of 36 KB, over the same link as the video. The command is python tools/gzip_ui.py, and the generated header is committed.

USB upload fails after the baud switch

Reduce the speed to 115200. This carrier board has no auto-reset: hold GPIO0 low while powering up.

Forward and backward are swapped

That chassis has a motor's leads the other way round. Left and right are swapped too, because the turn commands share the forward polarity — it is easy to miss on a table, where a pivot looks plausible either way. Lift the wheels, press forward, and tick whichever wheel turns the wrong way under Settings → Robot → Wheel direction. The flag is stored on the robot, so the fix follows the robot rather than the browser that made it.

A game says it cannot see anything

Each refusal names its own cause. Too dark to see the floor wants more light. More than one dark patch is usually the lens vignette rather than tape, and more contrast between tape and floor fixes it. Cannot see the card after the room has changed means the camera has re-balanced its colours: press Show it the card again, which is normal during a session rather than a fault.
